Processes & System Calls

Process states, fork/exec/wait, the difference between a function call and a system call, traps, and the PCB that ties it all together.

Quick revision — the 60 second version

  • Process = memory image (code+data+heap+stack) + saved CPU context, identified by a PID
  • States: Ready, Running, Blocked/Sleeping, Zombie (exited, not yet reaped)
  • fork() → 0 in child, child's PID in parent. exec() → replaces the memory image. wait() → reaps a zombie child
  • # processes after N forks = 2N

  • System call: jump via trap instruction through the IDT, save context on the kernel stack — never trust the user stack
  • Trapframe = the saved CPU snapshot on the kernel stack when a trap fires
  • return-from-trap restores context, drops privilege, and may switch to a different process entirely

§1 What is a Process?

A process is a program that's running. The OS allocates memory, initializes CPU context, and starts it in User Mode — until a system call, interrupt, or fault switches it to Kernel Mode.

Each process has a PID, code + data (from the executable), and space for a stack and heap allocated at runtime. When paused, its execution context (register values) is saved in memory; when resumed, it's restored.

Process States

StateMeaning
ReadyCan run, but the scheduler hasn't picked it (only 1 process runs per core at a time)
RunningCurrently executing on the CPU
Blocked / Sleeping / SuspendedWaiting on some event; context saved until the event occurs
ZombieExited, but not yet reaped — its exit code is still available for the parent to inspect
§ Why zombies exist

A zombie lets another process (the parent) examine the exit code (0 = success, non-zero = failure) before the OS reclaims its memory. The parent calls wait() to both read that status and tell the OS to clean up.

§2 System Calls, POSIX & ABI

A system call is a function call into OS code that runs at a higher privilege level — the API for managing processes and resources. Some are blocking (read() from disk), some return instantly (getpid()).

POSIX

A standard set of system calls + C library functions for portability. POSIX-compliant programs run on any POSIX-compliant OS (recompilation for architecture may still be needed). printf internally calls the write() syscall.

ABI

Application Binary Interface — the compiled-level equivalent of an API. An API says what functions exist and their argument order; an ABI says how — which registers, stack layout, calling convention.

The Core Process System Calls

CallWhat it does
fork()Creates a new child process by duplicating the parent's memory image
exec()Replaces the calling process's memory image with a new executable
exit()Terminates the process (doesn't clean up memory by itself)
wait()Blocks the parent until a child terminates, then reaps it

fork()

  • Creates a new process with a new PID; the parent's memory image is copied into the child
  • Parent and child run independent copies of the same code from the point of the fork onward
  • fork() returns 0 in the child, and the child's PID in the parent
  • Changes to the parent's data after the fork don't affect the child (and vice versa)
  • Number of processes after N forks = 2N

exit() & wait()

  • exit() switches the process out permanently, but does not clean up memory — the process becomes a zombie
  • wait() reaps a zombie child: cleans its memory, returns its exit status. If the child is still running, the parent blocks until it exits
  • If a parent never calls wait(), zombies pile up and can exhaust system memory
  • waitpid() waits for a specific PID
  • If a parent exits before its child, the child becomes an orphan, gets adopted by init, and is reaped when init eventually cleans it up

exec()

  • Switches the calling process to run a different program entirely — new code, data, heap, and stack
  • 6 Linux variants: execl, execlp, execle, execv, execvp, execvpe
  • Any code written after a successful exec() call never runs — the whole memory image is replaced
? Why fork + exec instead of just "run this program"?

Splitting process creation (fork) from program replacement (exec) lets the shell tweak the child's environment — redirecting file descriptors, changing directory, setting up pipes — before the new program's code starts running, without touching the shell's own state.

How it all pans out: bootup to shell

  • After boot, init spawns a shell (bash/zsh)
  • The shell reads a command, forks a child, execs the command, waits for it, then reads the next command
  • The shell forks rather than exec-ing directly, because it must not terminate itself
  • cd is special: it calls chdir() directly on the parent (the shell) — no child is forked, since we want the shell's own working directory to change

Foreground / Background & I/O Redirection

  • By default commands run in the foreground; the shell blocks until they finish
  • & runs a command in the background — the shell doesn't wait
  • Every process has STDIN, STDOUT, STDERR open by default as file descriptors
  • Output redirection: close STDOUT, then open a regular file — it reclaims the freed low-numbered descriptor
coutput redirection
close(STDOUT_FILENO);
open("./redir_output.txt", O_CREAT|O_WRONLY|O_TRUNC, S_IRWXU);
// open() always uses the first available file descriptor -> STDOUT here

§3 Function Call vs System Call

§ The two key differences

1. Jump target trust — in a function call, the address is known and baked into the executable; the CPU can just call it. In a system call, the user cannot be trusted to jump to the correct OS address, so a special trap instruction is used instead, which looks the address up in a table the user can't touch.

2. Which stack — a function call saves register context on the user stack. A system call cannot use the user stack (a hostile process could have pushed malicious return addresses onto it), so it uses a separate, protected kernel stack.

Kernel Stack & the IDT

  • Every process has its own kernel stack — part of its PCB, in kernel memory, inaccessible from user mode
  • Context is pushed onto it during a trap, popped when the trap is serviced
  • The Interrupt Descriptor Table (IDT) / Trap Table is set up by the OS at boot and holds the addresses of kernel handler code for each event type
IDT layout (xv6-style) 0 - 31 : System traps & exceptions 31 - 127 : Device interrupts 128 : int80 syscall interface 129 - 255 : other interrupts

The Hardware Trap Instruction

When user code wants a syscall, it invokes a trap instruction with an argument identifying the type. E.g. in xv6:

asminvoking fork (syscall #1)
movl $SYS_fork, %eax       # SYS_fork = 1, placed in EAX
int  $T_SYSCALL            # triggers the software interrupt (usually 64)
ret

When the trap fires, the CPU:

  1. Moves to a higher privilege level
  2. Shifts the stack pointer to this process's kernel stack
  3. Saves the register context onto the kernel stack
  4. Looks up the OS handler's address in the IDT and jumps the PC there
  5. Runs OS code, now on a secure stack

Trapframe

The trapframe is the saved snapshot of every register, flag, and segment selector at the moment of the trap, stored on the kernel stack.

asmxv6 alltraps
alltraps:
  pushl %ds
  pushl %es
  pushl %fs
  pushl %gs
  pusha                # push all general registers
  movw $(SEG_KDATA<<3), %ax
  movw %ax, %ds        # switch to kernel data segments
  movw %ax, %es
  pushl %esp           # pointer to trapframe, so C code can find it
  call trap             # call C function trap(tf)
  addl $4, %esp

Return-from-trap

Once the OS finishes handling the syscall/interrupt, a special instruction (iret on x86) does the reverse: restores CPU context from the kernel stack, drops privilege back to user mode, and resumes the PC where the trap happened. The user code has no idea it was ever suspended.

⚠ It doesn't always return to the same process

Before returning to user mode, the OS checks whether it should switch to a different process instead — because the current one exited/faulted, made a blocking call, or has simply run too long. That decision is the scheduler's job (next chapter).

§4 The PCB — struct proc in xv6

cxv6 proc.h (essentials)
struct context {
    uint edi, esi, ebx, ebp, eip;
};

enum procstate { UNUSED, EMBRYO, SLEEPING, RUNNABLE, RUNNING, ZOMBIE };

struct proc {
    uint sz;                     // size of process memory (bytes)
    pde_t* pgdir;                // page table
    char* kstack;                // bottom of kernel stack for this process
    enum procstate state;        // process state
    int pid;                     // process ID
    struct proc* parent;         // parent process
    struct trapframe* tf;        // trap frame for current syscall
    struct context* context;     // swtch() here to run process
    void* chan;                  // if non-zero, sleeping on chan
    int killed;                  // if non-zero, process has been killed
    struct file* ofile[NOFILE];  // open files
    struct inode* cwd;           // current directory
    char name[16];               // process name, for debugging
};

Notice this struct is the union of everything we just discussed: a page table (memory), a kernel stack + trapframe (trap handling), a state (scheduling), and a file table (the subject of chapter 7).

§5 Rapid-fire Recall

? Common questions

Q: What does fork() return in the parent vs. the child?
A: Child's PID in the parent, 0 in the child.

Q: Why can't a system call reuse the user stack for saving context?
A: The user (or malicious code) could have corrupted stack values; the kernel needs a trusted, private stack.

Q: What happens to a process's memory when it calls exit()?
A: Nothing is freed immediately — it becomes a zombie until a parent calls wait().

Q: What's the difference between an orphan and a zombie?
A: An orphan is a running child whose parent died (gets adopted by init). A zombie is an exited child waiting to be reaped.

Q: How does the CPU know where to jump on a trap?
A: It looks up the handler address in the IDT using the trap's numeric argument.
