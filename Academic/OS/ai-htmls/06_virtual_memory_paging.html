Virtual Memory & Paging

From base-and-bound to multi-level page tables and TLBs, then demand paging, page replacement, and how malloc actually gets its memory.

22 minread

Quick revision — the 60 second version

  • Every process sees a private virtual address space; MMU translates VA → PA on every access
  • Base & bound → segmentation (per-region base/bound) → paging (fixed-size chunks)
  • Page table: array indexed by VPN, PTE holds frame number + valid + present + dirty bits
  • Multi-level page tables trade a small lookup cost for massively less wasted memory
  • TLB = MMU's cache for VA->PA; flushed on context switch
  • Present bit = 0 → page fault; valid bit = 0 → segfault
  • malloc/free is userland, built on top of brk/sbrk/mmap; free list tracks + splits/coalesces chunks

§1 Virtual Memory: the Illusion

Processes believe they own the entire address space, but they only ever see their virtual memory space. On a 32-bit machine that's 232 = 4 GB max. All CPU register/pointer accesses, all loads and stores, operate purely on virtual addresses (VAs).

§ The OS lives inside every address space

The OS is not a separate process with its own address space — it's mapped into the high addresses of every process's virtual address space (so a trap can jump straight to OS code). There's still only one physical copy of the OS in RAM, loaded at boot.

Address Translation: Base & Bound

Simplest scheme: place the whole memory image contiguously starting at a base address B. PA = B + VA, and it must satisfy PA <= N (the bound). The MMU does this addition on every access using two registers.

✕ The problem

Lots of unused space between heap and stack still occupies physical memory — wasteful.

Segmentation

Split the address into an explicit segment field + offset (e.g. top 2 bits = segment: 00 code, 01 heap, 11 stack).

csegmented address check
if (offset >= bounds[segment]) {
    RaiseException(PROTECTION_FAULT);
} else {
    PhysAddr = base[segment] + offset;
    Register = AccessMemory(PhysAddr);
}

Still costly for the OS: it must map contiguous VA space onto separate physical segments and re-map when the heap grows.

§2 Paging

Chop memory into fixed-sized pieces instead. Still has some internal fragmentation, but is far simpler to manage.

§ Internal vs external fragmentation

Internal: the allocated region is bigger than what's needed, wasting space inside it. External: free space is broken into scattered small chunks, so no single region can satisfy a bigger request even though total free space is enough.

The Page Table

Each process gets a page table mapping VA → PA — an array where entry i holds the physical frame number for the process's i-th page. The MMU always has a register pointing at the current process's page table (updated on every context switch).

VA = (Virtual Page Number)(Offset) PTE[VPN] = { Valid, Physical Frame Number, ... } if (!valid) -> trap else -> PA = PhysicalFrameNumber + Offset
? Why is the page table a fixed array, not a dynamic structure?

The MMU is hardware — it needs constant-time, deterministic lookup billions of times per second. A dynamic/pointer-based structure would need search logic and variable latency, which hardware can't afford. (The wasted space this causes is fixed separately, with multi-level page tables.)

PTE fields

  • Valid bit = 1 if the page is actually part of the process
  • Present bit = 1 if it's currently in RAM; 0 means swapped out, unallocated, or illegal → triggers a page fault
  • Also: dirty bit, protection bits, etc.

The size problem

32-bit VA space = 4GB. With 4KB pages (212), that's 220 = 1M PTEs. At 4 bytes each, that's 4MB of page table per process — clearly too much to keep flat.

Multi-level Page Tables

Split the flat 1M-entry table into 1024 chunks of 1024 entries each: one outer table points to 1024 inner tables. The MMU walks each level in turn during translation.

? Worked example: 48-bit VA, 4KB pages, 8-byte PTEs — how many levels?

4KB pages → 12 offset bits, leaving 36 bits for page numbers. Each 4KB page-table block holds 4096/8 = 512 = 29 entries, so each level covers 9 bits. ceil(36 / 9) = 4 levels required.

TLB — Translation Lookaside Buffer

A hardware cache for VA → PA mappings inside the MMU. Without it, a multi-level walk means touching memory once per level for every single access — brutally slow. TLB is flushed on every context switch (mappings belong to the outgoing process).

Steps
TLB hitMMU finds the PTE in the TLB → computes PA directly → access memory once
TLB missMMU walks the page table in memory → populates the TLB → computes PA → access memory

Page-level security

Each PTE also carries permissions (user/kernel accessible, read/write). The MMU traps to the OS on any violation, so user programs can only touch memory they're actually permitted to.

Inverted Page Table

Instead of one page table per process, keep a single table with one entry per physical frame, storing which process and VA maps to it (via a hash table). Saves huge amounts of memory, but a linear scan would be expensive — hence the hash table.

§3 Demand Paging

Not all pages of all processes need to sit in RAM simultaneously — most programs don't touch all of their address space at once, and total virtual memory across processes can vastly exceed physical RAM (the OS overcommits memory on purpose).

  • Some pages aren't allocated at all (invalid)
  • Some valid pages are in physical frames; others are temporarily parked in swap space on disk and brought back in when accessed
§ Valid vs Present, combined

Valid=1, Present=1: page is in DRAM. Valid=1, Present=0: page exists but lives in swap space. Valid=0: not part of the process at all.

Page Fault Handling

MMU walks PTE during translation, finds something unexpected -> trap (page fault) | +-- valid bit not set -> segmentation fault, terminate process +-- illegal access (e.g. write to read-only) -> terminate process +-- valid set, present not set -> OS allocates a frame, updates PTE, restarts the instruction

What if memory is full?

OS evicts a victim page to swap space, freeing its frame for the faulting page. It updates both PTEs and restarts the process. In practice, the OS doesn't wait for memory to be literally full — it uses low/high watermarks and a background swap/page daemon to reclaim memory proactively.

File-backed vs Anonymous, Dirty vs Clean

TypeMeaning
File-backedBacked by a file on disk (e.g. executable code)
AnonymousNot backed by any file (e.g. stack, heap)
DirtyContent differs from its on-disk copy

Eviction only needs to write a victim page back to swap if it's dirty — clean pages can just be dropped and re-fetched later.

Thrashing

Every process has a working set: the frequently-used pages it needs resident to make progress. If assigned memory is smaller than the working set, page faults become constant. Thrashing = the system spends more time servicing page faults than doing real work. Fix: reduce working sets, or the OS reclaims/terminates processes.

Page Replacement Policies

PolicyIdeaWeakness
FIFOEvict the oldest-loaded pageMay evict hot pages; suffers Belady's Anomaly — hit rate can get worse with a bigger cache
Optimal (Belady's)Evict the page not needed for the longest time in the futureImpossible to know the future — only useful as a theoretical upper bound
LRUEvict the Least Recently Used page (temporal locality)OS isn't involved in every memory access, so tracking "recently used" has real overhead
§ Approximating LRU: the Clock Algorithm

The MMU sets an accessed bit on every PTE it touches. Periodically, the OS scans pages: if the accessed bit is 1, clear it (give it a second chance); the first page found with the bit still 0 becomes the victim. Dirty pages are avoided when possible, since evicting them costs an extra disk write.

§4 Memory From the User's Point of View

How does a process actually get more memory as it runs?

CallWhat it does
brk() / sbrk()Moves the "program break" (end of the data segment) — increasing it allocates memory, decreasing frees it
mmap()Maps new memory (anonymous or file-backed) directly into the process's virtual address space; unmapped with munmap()

mmap memory is contiguous in the virtual address space, not necessarily in physical memory, and is allocated lazily — on first touch, a page fault brings in the real frame.

§ malloc doesn't talk to the kernel every time

User code calls malloc/calloc/realloc from the C library, which internally uses brk/sbrk/mmap only when its existing heap pool runs out — not on every allocation.

The Free List

A linked list tracking free chunks in the heap. malloc searches it for a fit; freed chunks are added back.

  • Splitting: a small request may carve a piece out of a larger free chunk
  • Coalescing: adjacent freed chunks are merged back into one bigger chunk
  • Headers: each allocated chunk stores metadata (size, a "magic" guard value) invisible to the caller, so free() knows how much to reclaim and can detect overflow corruption
  • Embedded free list: the "next free chunk" pointer is stored inside the free chunk itself — the allocator only needs to remember the head

Choosing a chunk: fit strategies

StrategyPicks
First fitThe first free chunk big enough
Best fitThe closest-sized chunk (minimizes leftover waste)
Worst fitThe largest chunk (leaves a bigger, more reusable remainder)

Scaling it up

  • Segregated free lists: separate lists per popular chunk size — avoids split/coalesce overhead for common sizes
  • Slab allocator: pre-allocated slabs of a fixed chunk size, ready to hand out instantly
  • Buddy allocation: always allocate in powers of two, so two adjacent "buddy" blocks can always cleanly merge back into the next size up

§5 Rapid-fire Recall

? Common questions

Q: Difference between the valid bit and the present bit in a PTE?
A: Valid = page belongs to the process at all. Present = page is currently resident in RAM (vs. swapped out).

Q: Why do multi-level page tables save memory over a flat table?
A: Unused regions of the address space never need their inner-level table allocated at all — only outer entries that are actually in use point anywhere.

Q: What's Belady's Anomaly?
A: With FIFO replacement, increasing the number of available frames can, counter-intuitively, increase the number of page faults.

Q: Why does eviction only sometimes require a disk write?
A: Only dirty pages need to be written back to swap/disk; clean pages can simply be dropped since an unmodified copy already exists on disk (or nowhere, if never used).

Q: What's the point of the "magic number" in a malloc chunk header?
A: To detect heap corruption — if a previous chunk overflowed into this one, the magic value will have been clobbered.
