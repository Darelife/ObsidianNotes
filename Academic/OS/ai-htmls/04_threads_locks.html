Threads & Locks

Threads vs processes, why race conditions happen, and how mutual exclusion is actually built from hardware atomics upward.

15 minread
Threads.md + Locks.mdsource
5topics

Quick revision — the 60 second version

  • Threads share code/data/heap, but each has its own stack, PC, and CPU context
  • Concurrency = illusion of parallelism via switching; parallelism = truly simultaneous (needs multiple cores)
  • Race condition = unfortunate interleaving breaks atomicity of a shared-data update
  • Locks need an atomic hardware primitive: Test-and-Set or Compare-and-Swap
  • Naive spin locks waste CPU; futex-based queued locks are fairer and faster
  • Spinlock → short critical sections. Sleeping mutex → long critical sections. Two-phase lock = best of both

§1 Threads: Lightweight Processes

A process might want to run multiple copies of itself in parallel across CPU cores. Forking copies the entire memory segment; threads instead all share the same code, data, and heap of their parent process, but each gets its own stack. Each thread also has its own PC and CPU context during execution.

Concurrency vs Parallelism

Concurrency

Rapidly switching between threads/processes, giving the illusion of simultaneity. Useful even on a single core — if one thread blocks on I/O, another can keep the CPU busy.

Parallelism

Actually running things at the same time — bounded by the number of physical cores.

POSIX Threads (pthreads)

cpthread lifecycle
#include <pthread.h>

int pthread_create(
    pthread_t *restrict thread,
    const pthread_attr_t *restrict attr,
    void *(*start_routine)(void *),
    void *restrict arg
);

int pthread_join(pthread_t thread, void **retval);
cminimal example — compile with -lpthread
void *mythread(void *arg) {
    printf("%s\n", (char *) arg);
    return NULL;
}

int main(int argc, char *argv[]) {
    pthread_t p1, p2;
    printf("main: begin\n");
    pthread_create(&p1, NULL, mythread, "A");
    pthread_create(&p2, NULL, mythread, "B");
    pthread_join(p1, NULL);   // join waits for the thread to finish
    pthread_join(p2, NULL);
    printf("main: end\n");
    return 0;
}
// "A" and "B" can print in either order — the scheduler decides

§2 Race Conditions

cthe classic broken counter
int counter;

void *incrementBy100000() {
    for (int i = 0; i < 100000; i++) counter++;
}
// two threads run this. final counter value?
✕ Not 200,000

counter++ is not atomic — it's a read, then an increment, then a write. If T1 reads counter (say, 0) into a register and gets context-switched out before writing it back, T2 can run the entire increment and store 1. When T1 resumes, it still has the stale value 0 in its register, increments to 1, and overwrites T2's update. The final value ends up less than 200,000, and it's non-deterministic exactly how much less.

The fix is mutual exclusion via a lock (mutex):

cfixed with a mutex
int counter;
pthread_mutex_t m;

void *incrementBy100000() {
    for (int i = 0; i < 100000; i++) {
        pthread_mutex_lock(&m);      // acquire
        counter++;                    // critical section
        pthread_mutex_unlock(&m);    // release
    }
}

§3 Building a Lock

Goals of any lock implementation: mutual exclusion, fairness, low overhead.

Attempt 1 — Disable Interrupts

Lock = disable interrupts, unlock = re-enable. Only trustworthy inside the kernel itself. Fails on multi-core (another core can still touch the lock), and delays important interrupts like DMA completion.

Attempt 2 — Naive Spin Wait

cbroken — has a race of its own
int is_locked = 0;

void acquire_lock() {
    while (is_locked == 1);   // wait till free
    is_locked = 1;
}

void release_lock() { is_locked = 0; }
✕ Still racy

If a context switch happens right after the while check passes but before is_locked = 1 executes, another thread can slip in — the check and the set aren't atomic. Also wastes CPU cycles spinning.

Attempt 3 — Test-and-Set (hardware atomic)

A single hardware instruction that writes a new value and returns the old value, atomically, in one step (SPARC: ldstub, x86: locked xchg).

cTAS-based spinlock
typedef struct __lock_t { int flag; } lock_t;

void init(lock_t *lock) { lock->flag = 0; }

void lock(lock_t *lock) {
    while (TestAndSet(&lock->flag, 1) == 1);   // 1 = already held, keep spinning
}

void unlock(lock_t *lock) { lock->flag = 0; }

Compare-And-Swap (CAS)

Takes address, expected old value, and new value. Writes the new value only if the current value matches expected; always returns the actual old value.

cCAS-based lock
void lock(lock_t *lock) {
    while (CompareAndSwap(&lock->flag, 0, 1) == 1);
}
⚠ Not fair

None of the above guarantees fairness — there's no ordering of who gets the lock next. Linux uses futex-based locks with a built-in wait queue to fix both fairness and wasted spinning (the kernel wakes a specific waiting thread when the lock is released, instead of everyone racing).

Yielding while spinning

cspin + yield
void lock() {
    while (TestAndSet(&flag, 1) == 1) yield();
}
void unlock() { flag = 0; }

§ Two-Phase Locks

Phase 1: spin for a short while. Phase 2: fall back to a sleeping mutex if it's still not free. This hybrid is almost always the best practical choice.

§5 Locking Discipline & Counters

  • Protect each data structure with (at least) one lock
  • Locks can be coarse-grained (one big lock) or fine-grained (many small locks) — coarse is simpler, fine-grained scales better
  • Lock for both reads and writes of shared state
ca thread-safe counter
typedef struct __counter_t {
    int value;
    pthread_mutex_t lock;
} counter_t;

void init(counter_t *c) {
    c->value = 0;
    pthread_mutex_init(&c->lock, NULL);
}

void increment(counter_t *c) {
    pthread_mutex_lock(&c->lock);
    c->value++;
    pthread_mutex_unlock(&c->lock);
}

int get(counter_t *c) {
    pthread_mutex_lock(&c->lock);
    int rc = c->value;
    pthread_mutex_unlock(&c->lock);
    return rc;
}

§6 Rapid-fire Recall

? Common questions

Q: What do threads of the same process share, and what's private to each?
A: Shared: code, data, heap. Private: stack, PC, CPU registers/context.

Q: Why can't while(is_locked); is_locked=1; ever be a correct lock?
A: The check and the set are two separate instructions — a context switch between them lets two threads both think they got the lock.

Q: When would you prefer a spinlock over a sleeping mutex?
A: When critical sections are very short — the cost of a context switch would exceed the cost of just spinning briefly.

Q: What's the actual hardware guarantee Test-and-Set gives you?
A: The read-and-write of the flag happens as one indivisible step — no interleaving is possible.
