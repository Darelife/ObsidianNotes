File Systems, Storage & IPC

The fd-to-inode chain, how a simple file system is laid out on disk, the physical mechanics of storage devices, and every major IPC mechanism.

Quick revision — the 60 second version

  • File/dir = low-level name (inode number) + user-readable name pairs stored in directory data blocks
  • fd table (per-process) → Open File Table (system-wide, has offset+refcount) → inode
  • fork() shares OFT entries (shared offset); open() twice creates independent OFT entries

  • IPC = pipes, message queues, shared memory, sockets, signals — pick based on speed vs simplicity vs relation
  • Disk: platter → track → sector; LBA abstracts CHS complexity away for the OS

§1 Files & Directories — the Interface

A file is a linear array of bytes with a low-level name: an inode number. A directory is also identified by an inode number, and its contents are simply a list of <user-readable-name, inode-number> pairs — each entry can itself be a file or another directory.

Core syscalls

copen / read / write / lseek
int fd = open("foo", O_CREAT|O_WRONLY|O_TRUNC, S_IRUSR|S_IWUSR);
ssize_t read(int fd, void *buf, size_t count);
ssize_t write(int fd, const void *buf, size_t count);
off_t   lseek(int fd, off_t offset, int whence);
// whence: SEEK_SET (absolute), SEEK_CUR (relative), SEEK_END (from EOF)
// SEEK_HOLE / SEEK_DATA (Linux 3.1+) jump to the next hole/data region

A successful write() can transfer fewer bytes than requested (disk full, interrupted blocking write on a socket/pipe) — callers must be ready to retry.

The fd → OFT → inode chain

Process FD table [fd] --> Open File Table entry (struct file*) --> inode in memory (private per process) (system-wide, has offset + refcount)
cxv6 structs
struct file {
    enum { FD_NONE, FD_PIPE, FD_INODE } type;
    int ref;            // reference count
    char readable, writable;
    struct pipe *pipe;
    struct inode *ip;
    uint off;            // current offset — lives HERE, not in the fd table
};

struct proc {
    ...
    struct file *ofile[NOFILE];   // this process's fd table
};
? Why does the offset live in the Open File Table, not the fd table?

Because offset needs to be shared when a descriptor is duplicated (via fork() or dup()) but independent when the same file is opened twice separately. Process A opening file1 twice gets two OFT entries, each with its own offset; process A forking after one open() gives child and parent an fd pointing to the same OFT entry — advancing the offset in one advances it for both.

Useful extras

dup(oldfd) / dup2New fd pointing at the same OFT entry as oldfd

Hard links vs. Symbolic links

Hard link

Another directory entry pointing at the same inode. Not a copy — genuinely the same file under two names. Cannot span filesystems or point at directories. Won't overwrite an existing newpath.

Symbolic link

A file of its own (a different type), whose contents are just the path string to the target. Deleting the target leaves a dangling reference.

§2 Designing a Simple File System

Two questions drive every FS design: what on-disk data structures organize data/metadata, and what access methods map open/read/write onto those structures efficiently?

Overall layout (vsfs example)

| Superblock | inode bitmap | data bitmap | Inode Table (5 blks) | Data Region (56 blks) | 1 blk 1 blk 1 blk 80 inodes @ 256B user data Superblock stores: #inodes, #data blocks, where the inode table begins, a magic number (FS type)
  • One block size for the whole simple FS (e.g. 4KB)
  • Most blocks go to the data region
  • Reserve blocks for the inode table — inodes are small (128–256B), so a 4KB block holds many
  • Reserve allocation structures: a free list (points to the first free block, chained) or a bitmap (1 bit per block/inode: free=0, used=1)

mkfs -t type device size writes an empty filesystem (with a root dir) onto a device. mount -t type device target_dir "pastes" that filesystem onto an existing directory in the unified tree — accesses to that directory transparently redirect to the mounted FS.

Inode

Referred to by an i-number. Inode 0 = NULL (no inode). Inode 1 = tracks bad blocks. Inode 2 = the root directory, by Unix convention.

blk = (inumber * sizeof(inode_t)) / blockSize sector = ((blk * blockSize) + inodeStartAddr) / sectorSize

Inode → data blocks

ApproachTrade-off
Direct pointers1 pointer per block, simple, only works for small files
Multi-level indexing (indirect / double / triple)An indirect pointer points to a block full of pointers instead of data — recursively for double/triple. Most flexible, but more metadata per file
ExtentsA start pointer + length. More compact, less flexible; needs contiguous free space (ext4, XFS)
Linked list (FAT)Each block points to the next; an in-memory File Allocation Table makes random access fast without touching disk repeatedly
? Worked example: 12 direct + 1 indirect + 1 double-indirect + 1 triple-indirect, 4KB blocks, 64-bit addresses — max file size?

Pointers per block = 4KB / 8B = 512. Total pointers = 12 + 512 + 512² + 512³ = 134,480,396. Max size = that × 4KB ≈ 500.97 GB.

Directory organization & free space

  • A directory's data block holds <filename, inode#, reclen, strlen> entries — could be a flat list, a linked list, or a B-Tree (XFS uses B-trees for O(log n) lookups)
  • On deletion the entry's reclen stays, letting a smaller filename reuse that slot later
  • Free space tracked via bitmaps (can check for N contiguous free blocks), a free list, or B-trees (XFS)

What actually happens on read/write/create

open("/foo/bar")

Read root's inode (predefined #2) → read its data, find foo's inode# → read foo's data, find bar's inode# → read bar's inode → permission check → allocate an fd in the OFT.

read(fd, buf, count)

First block found via the inode → update last-accessed time → advance in-memory OFT offset for next read. Repeats per block.

⚠ Every new-block write costs 5 I/Os

Read data bitmap → write data bitmap → read inode → write inode (new block + metadata) → write the actual data block. Creating a brand-new file costs roughly 10 I/Os: read/write inode bitmap, write new inode, read/write directory data, write directory inode.

§ Reducing I/O cost: caching

Static partitioning: fixed % of memory reserved for a block cache (simple, predictable, can waste memory). Dynamic/unified page cache: VM and FS share the same page pool (harder to implement, better utilization). Writes can be write-through (synchronous, safe, slow) or write-back (buffered 5–30s, faster, riskier — fsync() forces a flush when durability actually matters, e.g. databases).

mmap() recap

Maps a file (or anonymous memory) directly into a process's address space; pages load lazily on first access (a page fault), tying straight back into demand paging from the previous chapter. MAP_SHARED writes propagate back to the file/other processes; MAP_PRIVATE is copy-on-write and never touches the underlying file.

§3 Storage Devices

The file system's abstractions ultimately sit on top of physical hardware with its own quirks.

TermMeaning
PlatterRigid rotating disk where data is physically stored; all platters spin in sync on a shared spindle
R/W headFlies nanometers above the platter surface to read/write; positioning precision is extreme
TrackA concentric ring on the platter
SectorSmallest addressable unit, typically 512 or 520 bytes (even a 1-byte write occupies a full sector)
CylinderThe same track number across all platters, stacked
  • Zoned Data Recording: outer tracks physically hold more sectors than inner ones, since outer circumference is bigger — outer tracks can be up to ~2× faster
  • Sequential vs random reads: contiguous sectors on the same/adjacent tracks read in one rotation; scattered sectors need multiple, much slower
  • CHS addressing (Cylinder-Head-Sector) is drive-specific and complex; LBA (Logical Block Addressing) abstracts it into one flat number range implemented by the drive controller
  • The controller runs firmware, exposes the simple LBA view upward, and silently remaps bad blocks to hidden reserved sectors — this remapping is what causes drive fragmentation over time
  • Queueing: the drive reorders I/O requests to minimize head movement and rotational latency

§4 Inter-Process Communication

Five main mechanisms: Unix domain sockets, message queues, pipes, shared memory, and signals.

Message Queues

An internal linked list in kernel space, identified by an IPC key. msgget() creates it, msgsnd()/msgrcv() send/receive, msgctl() deletes it. Messages are buffered until retrieved.

? How do you build a full-duplex reply channel over one queue?

Clients send with a fixed mtype (e.g. 1) carrying their PID in the body; the server replies with mtype = client_pid. Each client then reads only messages matching its own PID as the type — this lets many clients safely share one server-side queue.

Shared Memory

The fastest IPC — other mechanisms copy data sender → kernel → receiver twice; shared memory maps the same physical region into both address spaces directly, so a write by one process is instantly visible to the other. Needs external synchronization (semaphores) since the kernel doesn't order the accesses for you.

csynchronized reader/writer over shared memory
sem_writer (init 1)   // writer may write
sem_reader (init 0)   // reader waits for data

writer: sem_wait(sem_writer);  write();  sem_post(sem_reader);
reader: sem_wait(sem_reader);  read();   sem_post(sem_writer);

Pipes

Unidirectional FIFO byte channels. pipe(p) returns two fds: p[0] (read end), p[1] (write end). Bidirectional communication needs two pipes.

  • Anonymous pipes — only between related processes (parent/child); open the pipe before forking so both share the same underlying pipe structure, then each side closes the end it doesn't use
  • Named pipes (FIFOs) — for unrelated processes, created with mkfifo(path, mode) and opened by pathname; still unidirectional, and writing with no reader present is an error
§ How the shell wires up cat file | grep x

The shell creates a pipe, forks the first child (cat) and dup2()s the pipe's write end onto its STDOUT, forks the second child (grep) and dup2()s the pipe's read end onto its STDIN, then closes its own copies of both pipe fds. dup2(old, new) closes new first, then makes it refer to the same open-file-description as old — this survives exec(), since exec replaces code/data/heap/stack but leaves the fd table untouched.

Blocking vs. Non-blocking & Signals

  • Blocking send/receive suspend the caller until the op completes (buffer full → sender blocks; buffer empty → receiver blocks)
  • Non-blocking versions return an error instead — critical for a server juggling many slow clients without stalling everyone else
  • Signals are lightweight, dataless notifications — like interrupts, but for user processes. Sent via kill(pid, signum), caught via signal()/sigaction()
  • Process groups: Ctrl+C sends SIGINT to an entire foreground process group at once (e.g. every stage of a piped command shares one group ID, though each has a distinct PID)

§5 Rapid-fire Recall

? Common questions

Q: Where does a file's current read/write offset actually live?
A: In the Open File Table entry, not the per-process fd table — so fork()'d processes share a live offset via the same fd, but two separate open() calls get independent offsets.

Q: Why is creating a file more expensive (I/O-wise) than writing to an existing block?
A: Creation touches the inode bitmap, a new inode, the directory's data block, and the directory's inode — a new-block write only touches the data bitmap, the file's inode, and the data block itself.

Q: Fastest IPC mechanism, and why?
A: Shared memory — no double-copy through the kernel; both processes read/write the same physical pages directly.

Q: What's the difference between a hard link and a symlink at the inode level?
A: A hard link's directory entry points straight at the target's inode (same file, two names). A symlink is its own file whose contents are the target's path string.

Q: Why does lseek(fd, x, SEEK_END) for x > 0 not immediately grow the file on disk?
A: It just moves the logical offset past EOF — a "hole" is only actually created once a write happens there.
