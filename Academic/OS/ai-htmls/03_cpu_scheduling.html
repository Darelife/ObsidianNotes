CPU Scheduling

Policy vs mechanism, the anatomy of a context switch, and the lineup of scheduling algorithms from FCFS to Linux's CFS.

13 minread

Quick revision — the 60 second version

  • Scheduling = policy (who runs next) + mechanism (context switch), decoupled from each other
  • Non-preemptive: only switches on block/exit. Preemptive: can switch anytime via timer interrupt
  • FCFS → convoy effect. SJF → needs burst time, non-preemptive. SRTF → preemptive SJF
  • Round Robin: fixed quantum, good response time, worse turnaround
  • CFS = weighted fair queuing using vruntime + a red-black tree, tunable via nice value
  • Context switch = save context of A on its kernel stack, switch ESP to B's kernel stack, restore B

§1 The OS Scheduler

The OS keeps all active PCBs in a list — added on fork(), removed after wait() cleans them up. The scheduler is the code that periodically loops over this list and decides what runs next.

Scheduler outline ------------------ 1. Save context of whatever is currently running, into its PCB 2. Loop over ready/runnable processes, pick one to run next 3. Restore that process's context from its PCB, hand it the CPU 4. Repeat, forever, as long as the system runs

Scheduling has two independent halves: the policy (which process to run) and the mechanism (how to actually switch to it). This chapter is mostly policy — chapter 2 already covered the trap/context-switch mechanism.

Non-preemptive (cooperative)

Polite scheduler — only switches when the running process blocks or terminates.

Preemptive (non-cooperative)

Can switch anytime, even mid-execution, using periodic timer interrupts to check if the process has run too long.

§2 Context Switching, Precisely

Say process A is in kernel mode (already trapped in) and can't continue (e.g. it's waiting on a disk read). The scheduler picks process B to run instead.

  • OS saves A's kernel context (PC, registers, kernel stack pointer) onto A's own kernel stack
  • Note there are two contexts saved at different times: the user context (where execution stopped in user mode — saved by the trap instruction) and the kernel context (where execution stopped in kernel mode — saved by the context-switch code)
  • The actual switch: OS moves ESP from A's kernel stack to B's kernel stack
  • B's kernel stack already holds whatever the OS stored there the last time B was switched out — both its kernel and user context
  • OS restores B's kernel context, resumes B in kernel mode at the point it gave up the CPU, then pops B's user context and resumes B in user mode exactly where it originally trapped in

In xv6

  • Every CPU runs a dedicated scheduler thread
  • It loops over the process list, looking for a runnable one
  • swtch() performs the actual switch: saves registers into a context struct on the old process's kernel stack, switches ESP to the new process's context struct, and pops its registers

§3 Goals of CPU Scheduling

  • Maximize CPU utilization
  • Minimize completion / turnaround time
  • Minimize response time
  • Fairness across processes
  • Low overhead — the decision itself shouldn't take long, and shouldn't trigger excessive context switches (each switch costs roughly a microsecond)

§4 Scheduling Policies

FIFO / FCFS

Simplest: processes run in arrival order, non-preemptively, until they exit or block.

✕ Convoy effect

A short process stuck behind a long one drags average turnaround time way up.

Shortest Job First (SJF)

Assumes CPU burst time is known in advance. Always picks the process with the smallest burst next, typically via a heap. Still non-preemptive — once a long job starts, a shorter one that arrives mid-way must wait.

Shortest Remaining Time First (SRTF)

a.k.a. STCF / Preemptive SJF. Fixes SJF's blind spot by allowing preemption when a shorter job arrives.

Round Robin

  • Every process gets a fixed time quantum (not too big, not too small)
  • A timer interrupt enforces periodic switching
  • Good response time, fair — but worse turnaround time, since every process must wait its turn repeatedly
  • xv6 uses this

Weighted Fair Queuing (WFQ)

  • Round Robin, but with weights/priorities — time slice is proportional to weight
  • Real schedulers can't perfectly enforce a time slice (timer interrupts don't align perfectly, processes may block early)
  • Practical fix: track actual run time, favor whichever process has used the least fraction of its fair share, and compensate excess/deficit in future slices

Linux Completely Fair Scheduler (CFS)

A refined WFQ variant. Tracks vruntime (virtual runtime) per process and always picks the process with the lowest vruntime to run next — the goal is to divide CPU time evenly.

ParameterMeaningTypical value
sched_latencyHow long a process should run before a switch is considered; divided by the # of runnable processes to get each one's time slice~48 ms
min_granularityFloor on the time slice, so scheduling overhead doesn't dominate when there are too many processes~6 ms
§ Niceness & weight

nice ranges -20 to +19 (default 10); lower = higher priority. It maps to a weight, and the time slice for process k is:

time_slice_k = ( weight_k / sum(weight_i for all i) ) * sched_latency Nice : -20 -15 -10 -5 0 5 10 15 Weight: 88761 29154 9548 3121 1024 335 110 36

CFS stores runnable processes in a red-black tree ordered by vruntime, giving O(log n) operations — far better than scanning a flat list every few milliseconds.

§5 Rapid-fire Recall

? Common questions

Q: What's the fundamental weakness of pure SJF?
A: It's non-preemptive — a job already running blocks a shorter arriving job until it finishes.

Q: Why does Round Robin have good response time but bad turnaround time?
A: Every process is served quickly (low response time) but must repeatedly wait its turn to finish (high turnaround).

Q: What data structure does CFS use to pick the next process, and why?
A: A red-black tree keyed by vruntime — O(log n) insert/find-min, scales far better than a linear scan.

Q: What are the two pieces of context saved during a switch between A and B?
A: A's kernel context is saved on A's kernel stack; when B resumes, both its kernel and user context (saved earlier) are restored from B's kernel stack.
