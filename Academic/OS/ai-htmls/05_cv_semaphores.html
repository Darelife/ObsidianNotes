Condition Variables & Semaphores

Waiting for state changes correctly, the classic producer/consumer problem solved two ways, and the semaphore as a general synchronization primitive.

20 minread
CV_s_and_Semaphores.mdsource
6topics

Quick revision — the 60 second version

  • CV = an explicit wait queue for "state isn't right yet"; always paired with a mutex
  • Always use while, never if, around a CV wait — recheck the condition after waking
  • Producer/consumer needs two CVs (empty, fill), not one shared CV
  • Semaphore = integer counter + down(wait)/up(signal); blocks on negative, wakes on <= 0
  • Lock via semaphore → init to 1. Ordering (wait-for-child) → init to 0
  • Down never releases other locks it's holding → watch for deadlock ordering

§1 Condition Variables

Say T2 must run only after T1 finishes some task. Polling periodically wastes CPU. Adding T2 to T1's lock wait-queue is also wrong — wait queues are for locks/critical sections, not arbitrary ordering, and would block unrelated threads too.

A condition variable is an explicit queue threads put themselves on when the current state isn't what they want. A thread calls wait(cv) and blocks; another thread calls signal(cv) to wake one waiter.

Why wait/signal must be atomic with the check

T1T2 (broken interleaving)
if (!done) then context switch
done = true; signal(cv)
wait(cv) — sleeps forever, the signal already fired

The fix: lock around the check-and-wait, and lock around the update-and-signal.

T1T2
lock(mutex); if (!done) wait(cv, mutex)
lock(mutex); done=true; signal(cv); unlock(mutex)
unlock(mutex)
  1. T2 holds the lock, checks the condition, calls wait — the pthread implementation of wait() atomically releases the lock and adds itself to the queue, then reacquires the lock before returning
  2. T1 must also acquire the same lock before signaling, so signal can never happen in the gap between T2's check and T2's wait
  3. When T1 signals, T2 leaves the CV queue and tries to reacquire the mutex; if T1 still holds it, T2 waits on the mutex's queue instead until T1 unlocks
cpintos-style implementation (Mesa semantics)
void cond_wait (struct condition *cond, struct lock *lock) {
  struct semaphore_elem waiter;
  sema_init (&waiter.semaphore, 0);
  list_push_back (&cond->waiters, &waiter.elem);
  lock_release (lock);
  sema_down (&waiter.semaphore);
  lock_acquire (lock);
}

void cond_signal (struct condition *cond, struct lock *lock) {
  if (!list_empty (&cond->waiters))
    sema_up (&list_entry(list_pop_front(&cond->waiters),
                          struct semaphore_elem, elem)->semaphore);
}
§ Mesa vs Hoare semantics

This is Mesa-style: signal and wake-up aren't atomic — a signaled thread merely becomes runnable, it doesn't run immediately. That's exactly why you must re-check the condition (with while, not if) after waking.

§2 Producer / Consumer with CVs

✕ What's wrong with this code? (buffer size 1)
cbroken producer/consumer
void *producer(void *arg) {
    for (int i = 0; i < loops; i++) {
        Pthread_mutex_lock(&mutex);
        if (count == 1)                       // BUG 1: should be while
            Pthread_cond_wait(&cond, &mutex); // BUG 2: shared cond
        put(i);
        Pthread_cond_signal(&cond);
        Pthread_mutex_unlock(&mutex);
    }
}

Bug 1: if instead of while — after being woken, execution proceeds without re-verifying the state is actually usable. Bug 2: producer and consumer share one CV — a producer waking another producer (instead of a consumer) is pointless and can deadlock the system.

ccorrect — two condition variables (MAX = buffer size)
cond_t empty, fill;
mutex_t mutex;

void *producer(void *arg) {
    for (int i = 0; i < loops; i++) {
        Pthread_mutex_lock(&mutex);
        while (count == MAX) Pthread_cond_wait(&empty, &mutex);
        put(i);
        Pthread_cond_signal(&fill);
        Pthread_mutex_unlock(&mutex);
    }
}

void *consumer(void *arg) {
    for (int i = 0; i < loops; i++) {
        Pthread_mutex_lock(&mutex);
        while (count == 0) Pthread_cond_wait(&fill, &mutex);
        int t = get();
        Pthread_cond_signal(&empty);
        Pthread_mutex_unlock(&mutex);
    }
}

Signal vs Broadcast: signal wakes exactly one waiter; broadcast wakes all of them (they all recheck the condition) — more expensive but sometimes necessary when multiple threads could proceed.

§3 Worked Problem: Batch Processing

Wait for N requests to accumulate, process them together as a batch, then wait for the next batch.

crequest thread / batch processor thread
// request thread
lock(mutex)
count++
if (count == N) signal(cv_batch_processor)
while (!batch_started) wait(cv_request, mutex)
unlock(mutex)

// batch processor thread
lock(mutex)
while (count < N) wait(cv_batch_processor, mutex)
batch_started = true
signal_broadcast(cv_request)
unlock(mutex)

Two separate CVs again — one for requesters waiting on the batch to start, one for the processor waiting on enough requests.

§4 Semaphores

FeatureSemaphoreCondition Variable
Integer counterYesNo
Resource countingYesNo
Works alone (no external lock)YesNo — always needs a mutex

Typical useBounded buffers, resource countingWaiting on an arbitrary state change

Two operations: down/wait/P decrements and blocks if the result is negative. up/signal/post/V increments and wakes one blocked thread if needed.

wait(S): S.value = S.value - 1 if S.value < 0: block the calling thread signal(S): S.value = S.value + 1 if S.value <= 0: wake up one blocked thread
§ Reading the sign of S

If S > 0: that many resources are free. If S == 0: no free resources, but nobody is waiting. If S < 0: |S| threads are currently blocked waiting. The <= 0 check in signal exists because after incrementing from -1 to 0, there's still exactly one thread that needs waking — it was the last one queued.

Semaphore as a lock (binary semaphore)

cinit to 1 for locking
sem_t m;
sem_init(&m, 0, 1);       // X = 1: willing to hand the lock out immediately

sem_wait(&m);              // acquire
// critical section
sem_post(&m);              // release

Semaphores for ordering (parent waits for child)

cinit to 0 for ordering
sem_t s;

void *child(void *arg) {
    printf("child\n");
    sem_post(&s);
    return NULL;
}

int main() {
    sem_init(&s, 0, 0);     // X = 0: nothing to give away yet
    pthread_t c;
    pthread_create(&c, NULL, child, NULL);
    sem_wait(&s);            // parent blocks until child posts
    printf("parent: end\n");
}
? Why 0 here but 1 for locking?

With a lock, we're fine handing it out immediately (init 1). With ordering, there's nothing to hand out at the start — we must force the parent to block until the child actively produces the signal, so it starts at 0.

Threads waiting for each other (barrier of 2)

Both T1 and T2 must finish step 1 before either starts step 2. Use two semaphores T1done, T2done, both init 0 — and always up before down in each thread, or you deadlock (the count could never rise).

T1 (step 1)T2 (step 1)
up(T1done)up(T2done)
down(T2done)down(T1done)

Generalizing to N threads: the barrier

cbarrier for N threads
int count = 0;
sem_t mutex, barrier;
int N = <number of threads>;

sem_init(&mutex, 0, 1);    // protects updates to count
sem_init(&barrier, 0, 0);  // blocks everyone till all N arrive

void barrier_point() {
    sem_wait(&mutex);
    count++;
    if (count == N)
        for (int i = 0; i < N; i++) sem_post(&barrier); // release everyone
    sem_post(&mutex);
    sem_wait(&barrier);   // each thread waits its turn to pass
}

§5 Producer/Consumer with Semaphores

cunsafe first draft
// Producer                         // Consumer
down(sem_empty);                    down(sem_filled);
produce item                        consume item
up(sem_filled);                     up(sem_empty);
✕ Not safe

Nothing stops two producers from touching the buffer simultaneously — a plain mutex is still needed.

ccorrect ordering of mutex vs empty/filled
// Producer                         // Consumer
down(sem_empty);   // OUTSIDE       down(sem_filled); // OUTSIDE
down(mutex);                        down(mutex);
produce item                        consume item
up(mutex);                          up(mutex);
up(sem_filled);                     up(sem_empty);
⚠ Lock ordering matters

If down(mutex) came before down(sem_empty), a full buffer would deadlock the system: the producer holds the mutex while blocked on sem_empty, but only a consumer (which needs the mutex to run) can ever post sem_empty.

Guidelines: down~wait, up~signal — but semaphores have no broadcast equivalent. Use separate semaphores for signaling vs. mutual exclusion. Down never releases any lock it's already holding, so watch dependency ordering carefully. Choosing the right initial value is half the design.

§6 Rapid-fire Recall

? Common questions

Q: Why must a CV wait always be wrapped in while, not if?
A: Mesa-style signaling only makes the thread runnable — by the time it actually runs, another thread may have changed the state again. Re-checking is mandatory.

Q: Give the one-line intuition difference between a semaphore and a CV.
A: A semaphore is a gatekeeper that counts slots and wakes automatically; a CV is a doorbell you still have to check after answering.

Q: What should a semaphore used purely as a mutex be initialized to?
A: 1.

Q: What should a semaphore used purely for ordering (wait-for-event) be initialized to?
A: 0.

Q: In the producer/consumer semaphore solution, why must the buffer-availability down happen before the mutex down?
A: Otherwise a producer can hold the mutex while blocked waiting for space, but only a consumer — who needs the mutex to run — can free that space: deadlock.
