# Distributed File System

We have a client file system, and its networking layer.
We also have a file server, and its networking layer.
The file server is connected to the disks, and the client networking layer is connected to the server networking layer.

On the client side, there are apps which access files and directories through its FS. The apps issue normal sys calls. Thus DFS is transparent.

When the client does a read() $\Rightarrow$ Req to File Server to read the block $\Rightarrow$ Res back via the network, where the client can also cache it, avoiding future calls for the same block.

# Stateful Protocol

In this, the client fs opens a file, and requests for a fd from the server. The file server opens the file locally, and returns a fd. The subsequent reads use the fd. 
This complicates crash recovery. If the server reboots, there won't be any mapping from the fd to the file (OFT gone). If the client goes down, the file won't be closed on the server.

# NFS uses Stateless Protocol

Clients will still use POSIX APIs, which are stateful.

NFS requests have a file handle, that literally tell its users to "Read this exact file at this offset".

File handle: `<volume identifier, inode number, generation number>`

Volume identifier = Which partition?
Inode Number = basic os
Generation Number = A number the FS writes to each file, and it changes when the file is deleted, or its inode is freed, or the inode is later reused for a new file.

File A $\rightarrow$ inode = 42
File A gets deleted
File B $\rightarrow$ inode = 42

Without a generation number, the old client handle will still be valid, and could access the wrong file. 
With a generation number, 
Old file: (inode = 42, gen = 1)
New file:(inode = 42, gen = 2)

If there's a mismatch, it denies access.

| NFS Procedure        | Arguments                                              | Returns                          |
|---------------------|--------------------------------------------------------|----------------------------------|
| NFSPROC_GETATTR     | file handle                                            | attributes                       |
| NFSPROC_SETATTR     | file handle, attributes                                | attributes                       |
| NFSPROC_LOOKUP      | directory file handle, name of file/dir to look up     | file handle                      |
| NFSPROC_READ        | file handle, offset, count                             | data, attributes                 |
| NFSPROC_WRITE       | file handle, offset, count, data                       | attributes                       |
| NFSPROC_CREATE      | directory file handle, name of file, attributes        | file handle                      |
| NFSPROC_REMOVE      | directory file handle, name of file to be removed      | —                                |
| NFSPROC_MKDIR       | directory file handle, name of directory, attributes   | file handle                      |
| NFSPROC_RMDIR       | directory file handle, name of directory to be removed | —                                |
| NFSPROC_READDIR     | directory handle, count of bytes to read, cookie       | directory entries, cookie        |
LOOKUP protocol is used to obtain the file handle.

If an application opens the file `/a`, the client FS sends a lookup request to the server, passing it as the root file handle, and the name `a`. If it's successful, the file handle, and the file attributes will be returned.

If we need to read `/a/b/c`, we'll first have to look up `a` in `/`, then, `b` in `a`, and then finally, `c` in `b`.

When read is called, the client looks up the OFT with the fd, finds the file handle, uses its current position as the offset, and sends READ(FH, offset=0, count = MAX). 

The server will receive the read req, use the FH to get the volume & inode. Reads from disk/cache, and returns it.

The client receives it, updates the file position by the number of bytes read (here, MAX), and returns the data to the application.

# Handling Server Failures

If the server crashes, or the messages get dropped by the network.

As long as ops are idempotent (doesn't matter if we call them multiple times or once. Doesn't change the file system's state). 
`MKDIR` isn't idempotent. `LOOKUP`, `READ`, `WRITE`(as the offset is specified) , etc are idempotent.

The client keeps trying to run after a certain time interval.
For non idempotent ops, on the client side, duplicate errors get detected, and are sometimes still treated as a success (like, duplicate `MKDIR` can be treated as a success). Prefer using idempotent ops, instead of non-idempotent ones. Like, using `write(offset, length)`, instead of `append(length)`. In requests, use versioning and timestamps. It applies it only if the version matches.

# Client Side Caching

NFS Client side FS caches the file data, and meta data. It's also like a temporary buffer for writes.

## Cache Consistency

C1 reads F and caches it, C2 edits F and buffers it, C3 hasn't read F yet.

Solutions:
1. Flush on close. As soon as the client closes the file, it will flush all of its changes to the server, so that all the other clients can see the final changes at once
2. Check last modified time. Before using a cached block, the client will do a GETATTR, and will check the last modified time. If it's different, it will know that the file changed. We can also have a cache for this, with a small TTL, to reduce the number of requests to the file server.
