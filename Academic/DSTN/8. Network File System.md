# Distributed File System

We have a client file system, and its networking layer.
We also have a file server, and its networking layer.
The file server is connected to the disks, and the client networking layer is connected to the server networking layer.

On the client side, there are apps which access files and directories through its FS. The apps issue normal sys calls. Thus DFS is transparent.

When the client does a read() $\Rightarrow$ Req to File Server to read the block $\Rightarrow$ Res back via the network, where the client can also cache it, avoiding future calls for the same block.

# Stateful Protocol

In this, the client fs opens a file, and requests for a fd from the server. The file server opens the file locally, and returns a fd. The subsequent reads use the fd. 
This complicates crash recovery. If the server reboots, there won't be any mapping from the fd to the file (OFT gone). If the client goes down, the file won't be closed on the server.

# NFS uses Stateless Protocol

Clients will still use POSIX APIs, which are stateful.

NFS requests have a file handle, that literally tell its users to "Read this exact file at this offset".

File handle: `<volume identifier, inode number, generation number>`

Volume identifier = Which partition?
Inode Number = basic os
Generation Number = A number the FS writes to each file, and it changes when the file is deleted, or its inode is freed, or the inode is later reused for a new file.

File A $\rightarrow$ inode = 42
File A gets deleted
File B $\rightarrow$ inode = 42

Without a generation number, the old client handle will still be valid, and could access the wrong file. 
With a generation number, 
Old file: (inode = 42, gen = 1)
New file:(inode = 42, gen = 2)

If there's a mismatch, it denies access.

| NFS Procedure        | Arguments                                              | Returns                          |
|---------------------|--------------------------------------------------------|----------------------------------|
| NFSPROC_GETATTR     | file handle                                            | attributes                       |
| NFSPROC_SETATTR     | file handle, attributes                                | attributes                       |
| NFSPROC_LOOKUP      | directory file handle, name of file/dir to look up     | file handle                      |
| NFSPROC_READ        | file handle, offset, count                             | data, attributes                 |
| NFSPROC_WRITE       | file handle, offset, count, data                       | attributes                       |
| NFSPROC_CREATE      | directory file handle, name of file, attributes        | file handle                      |
| NFSPROC_REMOVE      | directory file handle, name of file to be removed      | —                                |
| NFSPROC_MKDIR       | directory file handle, name of directory, attributes   | file handle                      |
| NFSPROC_RMDIR       | directory file handle, name of directory to be removed | —                                |
| NFSPROC_READDIR     | directory handle, count of bytes to read, cookie       | directory entries, cookie        |
LOOKUP protocol is used to obtain the file handle.

If an application opens the file `/a`, the client FS sends a lookup request to the server, passing it as the root file handle, and the name `a`. If it's successful, the file handle, and the file attributes will be returned.

If we need to read `/a/b/c`, we'll first have to look up `a` in `/`, then, `b` in `a`, and then finally, `c` in `b`.

When read is called, the client looks up the OFT with the fd, finds the file handle, uses its current position as the offset, and sends READ(FH, offset=0, count = MAX). 

The server will receive the read req, use the FH to get the volume & inode. Reads from disk/cache, and returns it.

The client receives it, updates the file position by the number of bytes read (here, MAX), and returns the data to the application.

# Handling Server Failures

If the server crashes, or the messages get dropped by the network.

As long as ops are idempotent (doesn't matter if we call them multiple times or once. Doesn't change the file system's state). 
`MKDIR` isn't idempotent. `LOOKUP`, `READ`, `WRITE`(as the offset is specified) , etc are idempotent.

The client keeps trying to run after a certain time interval.
For non idempotent ops, on the client side, duplicate errors get detected, and are sometimes still treated as a success (like, duplicate `MKDIR` can be treated as a success). Prefer using idempotent ops, instead of non-idempotent ones. Like, using `write(offset, length)`, instead of `append(length)`. In requests, use versioning and timestamps. It applies it only if the version matches.

# Client Side Caching

NFS Client side FS caches the file data, and meta data. It's also like a temporary buffer for writes.

## Cache Consistency

C1 reads F and caches it, C2 edits F and buffers it, C3 hasn't read F yet.

Solutions:
1. Flush on close. As soon as the client closes the file, it will flush all of its changes to the server, so that all the other clients can see the final changes at once
2. Check last modified time. Before using a cached block, the client will do a GETATTR, and will check the last modified time. If it's different, it will know that the file changed. We can also have a cache for this, with a small TTL, to reduce the number of requests to the file server.



## Core Design Problem

How do you share files across machines with Unix semantics while tolerating network failures and server crashes?

## Key Concepts

- **Stateless Protocol**: Each request contains full file handle (volume ID, inode number, generation number). Server maintains no client state.
    
- **Idempotent Operations**: LOOKUP, READ, WRITE can be safely retried. MKDIR is not idempotent.
    
- **File Handle**: Instead of file descriptor that would be lost on server crash.
    
- **Client Caching**: Cache data + attributes. Use GETATTR to validate freshness (compare mtime).
    
- **Close-to-Open Consistency**: On close, flush writes; on open, check attributes.

Why does NFS still have a "cache consistency window" (typically 3-30 seconds) instead of immediately invalidating on every write? What performance problem would immediate invalidation cause?

## 1. What is NFS?

### Definition
> NFS (Network File System) is an **open protocol** developed by Sun Microsystems in 1986 that provides **transparent, remote access** to file systems over a network. It is designed to be **portable** across operating systems and machine architectures.

### The Core Question
> Why not just let clients use their local disks?

| Local Disk Only | NFS (Shared Storage) |
|-----------------|---------------------|
| Data isolated on each machine | Easy sharing across clients |
| Centralized backup impossible | Centralized administration |
| Security management per machine | Data servers in locked room |
| Wasted capacity (some disks full, some empty) | Pooled storage |

### High-Level View

```
┌─────────────────────────────────────────────────────────────────────┐
│                           CLIENTS                                    │
│  ┌─────────────────────────────────────────────────────────────┐    │

│  │          (open, read, write, close - normal syscalls)        │    │

│  │         - Caches file data and attributes                    │    │
│  │         - Buffer writes                                      │    │
│  └───────────────────────────┬─────────────────────────────────┘    │
└──────────────────────────────┼──────────────────────────────────────┘
                               │ (Network - RPC over UDP/TCP)
                               ▼
┌─────────────────────────────────────────────────────────────────────┐
│                           NFS SERVER                                 │

```

### Transparency
> To client applications, NFS looks like a local file system. No special APIs needed.
> - `open()`, `read()`, `write()`, `close()` work normally
> - The VFS (Virtual File System) layer handles the translation

## 3. The VFS/Vnode Abstraction

### What is VFS?
> An **interface layer** in the UNIX kernel that separates **generic file system operations** from **specific file system implementations**.

```
┌─────────────────────────────────────────────────────────────┐
│                      System Calls                            │
│              (open, read, write, close, etc.)                │
└───────────────────────────┬─────────────────────────────────┘
                            │
                            ▼
┌─────────────────────────────────────────────────────────────┐
│                    Virtual File System (VFS)                 │
│         - Generic operations (independent of FS type)       │
│         - Dispatches to specific FS implementation          │
└───────────────────────────┬─────────────────────────────────┘
                            │
        ┌───────────────────┼───────────────────┐
        │                   │                   │
        ▼                   ▼                   ▼
┌───────────────┐   ┌───────────────┐   ┌───────────────┐
│    ext4 VFS   │   │    NFS VFS    │   │    tmpfs VFS  │
│   Operations  │   │  Operations   │   │  Operations   │
└───────────────┘   └───────────────┘   └───────────────┘
```

### Vnode (Virtual Node)
> Represents a file within the VFS. Similar to inode but file-system agnostic.

| Vnode Field | Purpose |
|-------------|---------|
| `v_op` | Pointer to vnode operations table (read, write, close, etc.) |
| `v_data` | Pointer to file-system specific data (e.g., inode) |
| `v_count` | Reference count |
| `v_flag` | Status flags |

## 4. Stateless Protocol (The Key Design Decision)

### The Problem with Stateful Protocols
Early NFS versions used file descriptors (like local UNIX). Problems:

| Problem | Scenario |
|---------|----------|
| **Server crash** | Server reboots, loses mapping from fd → file. Client gets "bad fd" error |
| **Client crash** | File never closed on server. Resource leak |
| **Network partition** | Cannot distinguish server down from slow network |

### NFS Stateless Solution
> Each NFS request contains **all information needed** to execute it. The server maintains **no client-specific state**.

**File Handle (the replacement for file descriptor):**
```
┌─────────────────────────────────────────────────────────────┐
│                        File Handle                           │
├───────────────────────┬──────────────┬──────────────────────┤
│   Volume Identifier   │  Inode Number │ Generation Number   │
│ (which file system)   │ (which file)  │ (stale detection)   │
└───────────────────────┴──────────────┴──────────────────────┘
```

| Component | Purpose |
|-----------|---------|
| **Volume Identifier** | Tells server which exported file system the request refers to |
| **Inode Number** | Tells server which file within that partition |
| **Generation Number** | Incremented when inode reused. Old handles fail safely |

### Why Generation Number is Critical
```
1. File with inode 100 is deleted
2. Inode 100 is reused for a new file (different generation)
3. Client holds old file handle (inode 100, gen 1)
4. Client sends request to new file (inode 100, gen 2)
5. Server sees generation mismatch → rejects request (safe)
   Without generation: Client would access wrong file (DANGEROUS!)
```

## 5. NFS Protocol Operations

### Core NFS Procedures

| Procedure | Input | Output | Idempotent? |
|-----------|-------|--------|-------------|
| `NFSPROC_GETATTR` | File handle | Attributes | Yes |
| `NFSPROC_SETATTR` | File handle, attributes | Attributes | No |
| `NFSPROC_LOOKUP` | Directory handle, name | File handle, attributes | Yes |
| `NFSPROC_READ` | File handle, offset, count | Data, attributes | Yes |
| `NFSPROC_WRITE` | File handle, offset, count, data | Attributes | Yes |
| `NFSPROC_CREATE` | Directory handle, name, attributes | File handle, attributes | No |
| `NFSPROC_REMOVE` | Directory handle, name | Status | No |
| `NFSPROC_MKDIR` | Directory handle, name, attributes | File handle, attributes | No |
| `NFSPROC_RMDIR` | Directory handle, name | Status | No |
| `NFSPROC_READDIR` | Directory handle, count, cookie | Directory entries, cookie | Yes |

### The LOOKUP Operation (Pathname Traversal)
```
Client wants to open /home/user/foo.txt

Step 1: Client has root file handle (from mount protocol)
Step 2: LOOKUP(root_fh, "home") → home_fh
Step 3: LOOKUP(home_fh, "user") → user_fh
Step 4: LOOKUP(user_fh, "foo.txt") → foo_fh
Step 5: READ/OPEN using foo_fh
```

### Idempotency Explained
> An operation is **idempotent** if performing it multiple times has the same effect as performing it once.

| Operation | Idempotent? | Why |
|-----------|-------------|-----|
| READ (offset 100) | Yes | Reading same offset repeatedly returns same data |
| WRITE (offset 100, data X) | Yes | Writing same data to same offset is same effect |
| MKDIR | No | Second attempt fails because directory already exists |
| CREATE | No | Second attempt fails (file exists) |

**Why idempotency matters:** Client can safely retry after timeout without knowing if server executed the request.

## 6. Failure Handling in NFS

### The Retry Mechanism

```
Client sends RPC request
         │
         ▼
    Timeout (no response)
         │
         ▼
Client retries (same request, same file handle)
         │
         ▼
   (Repeat until server responds or too many retries)
```

### Crash Scenarios

| Failure | Server State | Client Action | Result |
|---------|--------------|---------------|--------|
| **Network packet loss** | Request never received | Retry | Success on retry |
| **Server crash before execution** | No state | Retry | Server re-executes |
| **Server crash after execution, before reply** | Completed | Retry | Idempotent: no problem |
| **Server crash during execution** | Partial state | Retry | Idempotent: replay safe |
| **Non-idempotent operation after crash** | Directory created but reply lost | Retry | MKDIR fails (EEXIST) |

### The Non-Idempotent Problem

```
Client sends MKDIR("foo")
        │
        ▼
Server creates directory "foo" (success)
        │
        ▼
Server sends reply (but packet lost)
        │
        ▼
Client times out, retries MKDIR("foo")
        │
        ▼
Server returns EEXIST (failure!)
        │
        ▼
Client sees failure but directory WAS created
```

**Application must handle this** (check if directory exists after failure).

## 7. Client-Side Caching (Performance Optimization)

### Why Cache?
> Network is slow. Caching reduces RPCs and improves apparent performance.

### What is Cached?

| Cache Type | Contents | Purpose |
|------------|----------|---------|
| **Data cache** | File data blocks | Reduce READ RPCs |
| **Attribute cache** | File metadata (size, mtime, owner) | Reduce GETATTR RPCs |
| **Write buffer** | Dirty data not yet sent | Decouple application from network latency |
| **Name cache** | Directory lookup results | Reduce LOOKUP RPCs |

### The Consistency Problem

```
┌─────────┐         ┌─────────┐         ┌─────────┐
│ Client A│         │ Server  │         │ Client B│
└────┬────┘         └────┬────┘         └────┬────┘
     │                   │                   │
     │ read file F       │                   │
     │──────────────────►│                   │
     │←──────────────────│ data (cached at A)│
     │                   │                   │
     │                   │◄──────────────────│ write file F
     │                   │ (update from B)   │
     │                   │                   │
     │ read file F       │                   │
     │──────────────────►│                   │
     │←──────────────────│ UPDATED data      │
     │                   │                   │
     BUT if A's cache is stale, it returns old data without asking!
```

### NFS Solutions

**1. Attribute Revalidation (Close-to-Open Consistency)**
```
Client wants to read cached file F:
    │
    ▼
Client sends GETATTR to server (fetch current mtime)
    │
    ▼
If server mtime == cached mtime:
    Use cached data
Else:
    Invalidate cache, fetch fresh data from server
```

**2. Attribute Cache (Reduces GETATTR traffic)**
- Cache attributes for a few seconds (3-30 seconds)
- Within window, assume file unchanged
- After window, revalidate

**3. Write Buffering + Flush-on-Close**
```
Application writes to file:
    │
    ▼
Client buffers writes (does NOT send to server immediately)
    │
    ▼
Application calls close():
    │
    ▼
Client flushes ALL dirty data to server
    │
    ▼
Client waits for server acknowledgement
    │
    ▼
close() returns (data now on server)
```

### Trade-offs of Close-to-Open

| Pro | Con |
|-----|-----|
| Reduces RPCs dramatically | Other clients may see stale data until file closed |
| Good for read-mostly workloads | Not suitable for real-time sharing |
| Simple to implement | Applications must close frequently |

## 8. NFS vs Local File System (Performance Comparison)

### Same Workload, Different Behavior

| Workload | Local ext4 | NFS (over 1GbE) | Why? |
|----------|------------|-----------------|------|
| Sequential read (1GB) | 2 seconds | 10 seconds | Network bottleneck (100 MB/s max) |
| Random 4KB reads (1000 I/Os) | 0.2 seconds | 2+ seconds | RPC overhead (microseconds vs milliseconds) |
| File creation (10,000 files) | 2 seconds | 30+ seconds | Each file = multiple RPCs (LOOKUP + CREATE) |
| Write + fsync | 5 ms | 10+ ms | NFS forces server write before ACK |

### The Metadata Problem
> Every file operation that touches metadata becomes an RPC.

```
Creating a file in NFS:
1. LOOKUP(dir_fh, "newfile") → check if exists
2. CREATE(dir_fh, "newfile") → create file
3. GETATTR(newfile_fh) → get attributes
4. SETATTR(newfile_fh) → set permissions (if needed)

= 4 RPCs for one file creation!
```

**Optimization:** NFSv4.1 adds COMPOUND operations (batch multiple RPCs into one).

## 9. NFS Versions Comparison

| Feature | NFSv2 (1989) | NFSv3 (1995) | NFSv4 (2000) | NFSv4.1+ |
|---------|--------------|--------------|--------------|----------|
| **Protocol** | UDP only | UDP + TCP | TCP only | TCP only |
| **File size** | 32-bit (2GB max) | 64-bit (large files) | 64-bit | 64-bit |
| **Write size** | 8KB max | 64KB+ (negotiated) | 64KB+ | 1MB+ |
| **State** | Stateless | Stateless | Stateful (leases) | Stateful |
| **Delegations** | No | No | Yes | Yes |
| **COMPOUND** | No | No | Yes | Yes |
| **Parallel NFS** | No | No | No | Yes (pNFS) |

### NFSv4's Stateful Additions

| Feature | What it does |
|---------|--------------|
| **Leases** | Client holds lock for finite time; must renew; server revokes if not renewed |
| **Delegations** | Server delegates authority to client (reading/writing) without contacting server |
| **COMPOUND** | Multiple operations in one RPC (e.g., LOOKUP + OPEN + READ) |
| **Open/Close state** | Server knows which files are opened (for byte-range locks) |

## 10. NFS vs Other Distributed File Systems

| Feature | NFS | GFS | Lustre |
|---------|-----|-----|--------|
| **POSIX compliance** | Yes (close-to-open) | No (record append) | Yes (full) |

| **Failure recovery** | Client retry | Shadow masters | Active/passive |
| **Target use** | General enterprise | Web-scale, batch | HPC |

> [!question] NFSv3 is stateless. A client writes 1MB of data to a file and receives an acknowledgement. Before the server can flush the data to disk, the server crashes. After reboot, the client reads the same file. What data does it see? Is this acceptable for a database workload? For a web server log?
>
> **What happens:**
>
> ```
> Client: WRITE(offset 0, 1MB data) → Server acknowledges
> Server: Data in page cache (not yet on disk)
> Server: CRASH (data in cache lost)
> Server: Reboots (clean file system due to journaling)
> Client: READ(offset 0, 1MB) → Server returns OLD data (or zeros)
> ```
>
> **For Database Workload:**
> - NOT acceptable
> - Database assumes durable writes after ACK (Durability in ACID)
> - This violates durability guarantee → possible transaction loss, corruption
> - Databases use `fsync()` or direct I/O to force disk writes
>
> **For Web Server Log:**
> - Acceptable (mostly)
> - Logs tolerate some data loss
> - Better than no logging
> - Typical web servers flush logs periodically, not per-write
>
> **NFSv3 Solution:** Application must use `fsync()` before assuming durability
> **NFSv4 Solution:** Delegations + lease-based recovery provide better guarantees

> [!question] Walk through the path of `open("/home/user/foo.txt", O_RDONLY)` in NFSv3. How many RPCs are required if nothing is cached? How many if the directory is cached? What happens if the server crashes after step 3?
>
> **Cold cache (no caching):**
>
> ```
> Step 1: Client has root file handle from mount
> Step 2: LOOKUP(root_fh, "home") → returns home_fh
> Step 3: LOOKUP(home_fh, "user") → returns user_fh
> Step 4: LOOKUP(user_fh, "foo.txt") → returns foo_fh
> Step 5: GETATTR(foo_fh) → get attributes (for open checks)
> Step 6: ACCESS(foo_fh, O_RDONLY) → check permissions (optional)
>
> Total RPCs: 5-6
> ```
>
> **Warm cache (directory entries cached):**
>
> ```
> Step 1: Client has root_fh (cached)
> Step 2: Client cached mapping "home" → home_fh (no RPC)
> Step 3: Client cached mapping "user" → user_fh (no RPC)
> Step 4: LOOKUP(user_fh, "foo.txt") → returns foo_fh (1 RPC)
> Step 5: GETATTR may be cached or fresh (0-1 RPC)
>
> Total RPCs: 1-2
> ```
>
> **Server crash after step 3 (before LOOKUP for foo.txt):**
>
> ```
> Step 1-3 succeed, client has user_fh in cache (valid)
> Server crashes
> Server reboots (different generation number for inodes)
> Client sends LOOKUP(user_fh, "foo.txt")
> Server: user_fh has wrong generation number → returns NFS3ERR_STALE
> Client: Evicts user_fh from cache, starts over from root
> Result: Operation eventually succeeds, but extra RPCs
> ```

> [!question] Compare NFS's close-to-open consistency with GFS's consistency model. A file is updated by Client A, then read by Client B. In both systems, describe the scenarios where Client B sees stale data. Which system has stronger consistency?
>
> **NFS Close-to-Open:**
>
> ```
> Client A: write to file (buffered)
> Client A: close file (flushes to server)
> Client B: open file (sends GETATTR, sees new mtime)
> Client B: reads → fresh data (CONSISTENT)
>
> But if Client A's writes are still buffered (not closed):
> Client A: write (buffered locally)
> Client A: continues working (no close)
> Client B: open file (GETATTR shows old mtime)
> Client B: reads stale data (INCONSISTENT)
> ```
>
> **GFS Defined Regions:**
>
> ```
> Client A: append record
> Client B: read last chunk
>
> If chunk lease still valid on Client A's primary:
> No inconsistency (primary serializes)
>
> But if crash occurs during append:
> Client B may see duplicate record or padding
> GFS accepts this as "defined" (not POSIX consistent)
> ```
>
> **Comparison table:**
>
> | Consistency aspect | NFS (close-to-open) | GFS |
> |--------------------|--------------------|-----|
> | **Without close** | Stale data possible | Append order defined by primary |
> | **After crash** | Stateless retry safe | Duplicates possible (at-least-once) |
> | **Concurrent writes** | Locks (v4) or corruption (v3) | Primary determines order |
> | **Overwrites** | POSIX consistent | Not supported |
> | **Strength** | Weaker (close needed) | Weaker (duplicates possible) |
>
> **Which is stronger?** Neither is strictly stronger; they optimize for different goals:
> - NFS: Trades off write-close-read consistency for performance
> - GFS: Trades off exactly-once for high-concurrency appends

> [!question] An NFS server exports a directory with 1 million files. A client runs `ls -l` on this directory over a 1 Gbps network. Estimate the number of RPCs, network bytes transferred, and approximate time. How does this compare to a local `ls -l`? What optimization would help?
>
> **Assumptions:**
> - 1 million files
> - Each READDIR returns 100 entries (typical NFSv3 limit)
> - Each file needs GETATTR for `ls -l` (size, owner, permissions, timestamps)
> - File names average 15 bytes
> - NFS READDIR reply ~8KB (100 entries + attributes)
>
> **RPC count:**
> ```
> READDIR RPCs = 1,000,000 / 100 = 10,000 RPCs
> GETATTR RPCs = 1,000,000 (one per file)
> Total RPCs ≈ 1,010,000
> ```
>
> **Network bytes:**
> ```
> READDIR replies: 10,000 × 8KB = 80 MB
> GETATTR replies: 1,000,000 × ~200 bytes = 200 MB
> Total ≈ 280 MB
> ```
>
> **Time estimate:**
> - RPC latency: ~1ms per RPC round trip (LAN)
> - 1,010,000 × 1ms = 1,010 seconds ≈ 17 minutes
> - Network transfer: 280 MB at 100 MB/s = 2.8 seconds (negligible)
> - **Bottleneck: RPC latency, NOT bandwidth!**
>
> **Local `ls -l` time:** ~5-10 seconds (scans directory inode, reads from disk once)
>
> **Optimizations:**
>
> 1. **NFSv4 COMPOUND RPC:**
>    - READDIR + GETATTR in single RPC (retrieve all attributes at once)
>    - 10,000 RPCs instead of 1,010,000 → 10 seconds
>
> 2. **Directory readahead:**
>    - Client prefetches next READDIR while processing current
>    - Overlaps network latency with computation
>
> 3. **Attribute caching:**
>    - Don't re-GETATTR files whose attributes haven't changed
>    - But `ls -l` wants current attributes, so this doesn't help
>
> 4. **Server-side directory indexing (extents/B-trees):**
>    - Not standard NFS, but Lustre supports

> [!question] NFS clients cache file attributes for a fixed time (e.g., 30 seconds). What is the worst-case inconsistency window if Client A writes to a file and Client B reads the same file 1 second later? How would you design a lease-based system to reduce this window without increasing RPCs significantly?
>
> **Worst-case inconsistency:**
>
> ```
> t=0:   Client A writes to file (write buffered, not flushed)
>        Client A's write not yet sent to server
> t=1:   Client B opens file
>        Client B's attribute cache says: mtime = t-10 seconds (old)
>        Client B caches the old attributes (within 30-second window)
>        Client B reads stale data
> t=5:   Client A closes file (flushes write to server)
> t=31:  Client B's attribute cache expires
>        Client B revalidates with GETATTR, sees new data
>
> Inconsistency window: 1 to 31 seconds (or longer!)
> ```
>
> **Lease-based solution (NFSv4):**
>
> ```
> Client A: opens file for write → acquires WRITE lease
>            (lease = 30 seconds, must renew)
> Client B: tries to read → server sees Client A has WRITE lease
>            Server does NOT grant B's read lease immediately
>            Server sends lease recall to Client A
> Client A: renews lease or releases
> Client B: eventually gets lease
>
> Worst-case window: time for recall + renewal (~100ms)
> ```
>
> **Trade-off analysis:**
>
> | Aspect | Fixed cache (NFSv3) | Leases (NFSv4) |
> |--------|---------------------|----------------|
> | **RPC overhead** | Low (GETATTR every 30s) | Higher (lease renewals, recalls) |
> | **Consistency window** | Up to 30 seconds | Milliseconds to seconds |
> | **Server state** | None (stateless) | Yes (lease state) |
> | **Recovery on server crash** | Simple (retry) | Complex (lease expiration, recall) |
> | **Best for** | Read-mostly, no sharing | Active sharing, real-time |
>
> **Hybrid approach (not in NFS):** Short lease for writers (1s), long lease for readers (30s)

> [!question] Connect NFS's stateless design to RAID's write hole problem (Slide 17). An NFS server has its backing storage on a RAID 5 array without NVRAM. A client writes a file and gets ACK. Then RAID controller loses power during the RAID 5 parity update. The NFS server reboots but the client still has a valid file handle. What happens when the client reads the file? Who detects the inconsistency?
>
> **The problem chain:**
>
> ```
> Client: WRITE(file handle, offset, data) → Server ACK
> Server: Forwards write to RAID controller
> RAID: Write data disk (success)
> RAID: Power fails before parity disk write (Write Hole!)
> RAID: Data and parity inconsistent
> NFS Server: Crashes (due to RAID inconsistency or power loss)
> Server reboots, fsck runs (fixes local file system)
> Client: Has valid file handle (no generation change)
> Client: READ(file handle) → Server returns data from RAID
> RAID: Data correct (data disk was written), parity wrong (but not used on read)
> Client: Gets correct data (luckily)
> But: If data disk also failed later, parity cannot recover (silent corruption)
> ```
>
> **Who detects inconsistency?**
> - Not NFS (NFS assumes backing storage is reliable)
> - Not RAID controller (no NVRAM, no journal → doesn't know)
> - Not file system (thinks parity is correct)
> - **Nobody! Silent data corruption!**
>
> **Solutions:**
> 1. RAID controller with NVRAM (journals parity updates)
> 2. NFS server fsync() before ACK (forces RAID to complete parity)
> 3. Use RAID 10 instead of RAID 5 (no parity, no write hole)
> 4. File system checksums (detect corruption, but not fix at RAID level)
>
> **Lesson:** Stateless protocols don't guarantee storage consistency; they only guarantee protocol resilience.

> [!question] You have 1000 NFS clients all reading the same 1GB file repeatedly. NFSv3 with attribute cache (30s) is used. Compare the load on the NFS server with no client caching vs with caching. How many GETATTR RPCs per second does the server see? What if the file's mtime never changes?
>
> **Without client caching (read from server every time):**
> - Each client reads 1GB at 100 MB/s = 10 seconds to read
> - Each client issues 1GB / (max read size 64KB) ≈ 16,000 READ RPCs
> - 1000 clients × 16,000 = 16,000,000 READ RPCs per 10 seconds
> - READ RPC rate = 1,600,000 RPCs/second (impossible!)
> - **Server collapses immediately**
>
> **With client data caching (but no attribute cache):**
> - Client caches data locally
> - Before using cached data, client must GETATTR (every read operation)
> - 1000 clients each re-reading continuously
> - Each client issues GETATTR every 10 seconds (when done reading)
> - GETATTR rate = 1000/10 = 100 RPCs/second (easily handled)
> - **This works!**
>
> **With attribute cache (30 seconds):**
> - Client caches attributes for 30 seconds
> - If file mtime never changes, client reuses cached attributes
> - GETATTR RPC rate = 1000/30 ≈ 33 RPCs/second (even less)
> - **But**: If file does change, clients may see stale data for up to 30 seconds
>
> **If mtime never changes:**
> ```
> Client caches attribute at t=0
> Client reuses attribute at t=10 (still valid)
> Client reuses attribute at t=20 (still valid)
> Client revalidates at t=30 (GETATTR)
> GETATTR rate = 33 RPCs/second (as above)
> ```
>
> **Load on server with caching:**
> - GETATTR: 33 RPCs/sec (tiny)
> - READ: 0 (all cached)
> - Result: Server nearly idle, clients fast
>
> **Key insight:** Attribute caching is critical for scalability. Without it, NFS fails.

> [!question] Compare the failure recovery of NFSv3 (stateless) and GFS (stateful with leases). A server crashes while processing a write from Client A. Describe recovery in both systems. Which recovers faster? Which has higher chance of data loss?
>
> **NFSv3 (Stateless) Recovery:**
>
> ```
> Client A: sends WRITE(offset, data)
> Server: receives, executes write to disk
> Server: crash (before sending reply)
> Client A: timeout, retries WRITE (idempotent)
> Server: rebooted, receives WRITE
> Server: writes same data again (idempotent, harmless)
> Server: sends ACK
>
> Recovery time: seconds (timeout + retry)
> Data loss chance: Low (if write was durable before crash)
> ```
>
> **GFS (Stateful with Leases) Recovery:**
>
> ```
> Client A: pre-pushes data to replicas
> Client A: sends write request to primary
> Primary: writes data, forwards to secondaries
> Primary: crash (before sending ACK to client)
> Master: detects primary dead via heartbeat timeout (60s)
> Master: grants lease to new primary (different chunkserver)
> Client A: times out, asks master for new primary
> Client A: retries write to new primary
> New primary: may have partial data, must reconcile
>
> Recovery time: 60+ seconds (lease timeout + failover)
> Data loss chance: May lose data if primary crashed after writing only some replicas
> ```
>
> **Comparison table:**
>
> | Aspect | NFSv3 | GFS |
> |--------|-------|-----|
> | **Recovery time** | Seconds | Minutes (lease timeout) |
> | **Data loss risk** | Low (if write durable) | Medium (partial replication) |
> | **Client awareness** | None (transparent) | Client must retry, get new primary |
> | **State on server** | None | Lease state, primary role |
> | **Recovery complexity** | Trivial (retry) | Complex (lease revocation, reconciliation) |
> | **Idempotency requirement** | Yes (for retry safety) | No (primary ensures ordering) |
>
> **Which recovers faster?** NFSv3 (seconds vs minutes)
> **Which has lower data loss?** Depends on replication. NFSv3 durability depends on backing storage; GFS replication provides redundancy but crash during write may lose data.
>
> **Irony:** Stateless protocols are simpler and recover faster, but provide weaker semantics. Stateful protocols provide stronger ordering but pay complexity and recovery time.

> [!question] A company uses NFSv3 for their home directories (1,000 users, each with 10,000 small files). The server is slow during morning login (8-9 AM) when everyone compiles code. Using Darshan-like analysis, you discover 10,000 GETATTR RPCs per second. What is the bottleneck? Propose three optimizations.
>
> **Bottleneck analysis:**
> - 10,000 GETATTR RPCs/sec
> - Each GETATTR: ~200 bytes request + ~200 bytes reply = 400 bytes
> - Network bandwidth: 10,000 × 400 bytes = 4 MB/s (tiny, not bottleneck)
> - Server CPU: Handling 10,000 RPCs/sec is high (context switches, protocol parsing)
> - Server disk: GETATTR reads from MDT (inode metadata)
> - **Bottleneck: Server CPU or MDT IOPS (not network!)**
>
> **Optimization 1: Attribute Cache Tuning**
> ```
> Increase attribute cache timeout from 30s to 300s
> Effectiveness: 10,000 GETATTRs → 1,000 GETATTRs (10x reduction)
> Trade-off: Changes to files take 5 minutes to be visible
> Works for home directories where files rarely change during login
> ```
>
> **Optimization 2: NFSv4 COMPOUND with OPEN**
> ```
> Instead of LOOKUP + GETATTR per file, use OPEN (returns attributes)
> Reduces RPC count by 50% (one RPC instead of two)
> Also client can batch multiple OPENs in one COMPOUND
> ```
>
> **Optimization 3: Client-Side Metadata Prefetch**
> ```
> When user logs in, compile script touches thousands of headers
> Client can send LOOKUP for all headers in one RPC (NFSv4 COMPOUND)
> Example: COMPOUND(LOOKUP "header1", LOOKUP "header2", ..., GETATTR all)
> Reduces RPCs from 10,000 to 10 (1000 files per COMPOUND)
> ```
>
> **Optimization 4: Server-Side Directory Indexing**
> ```
> Use filesystem with B-tree directories (XFS, ext4 with dir_index)
> Reduces LOOKUP time from O(n) to O(log n)
> Not RPC count, but latency per RPC
> ```
>
> **Hardware Solution:**
> - Move MDT to faster storage (NVMe instead of HDD)
> - Add more NFS servers (split home directories across multiple exports)

## QUICK REFERENCE CARD

| Concept | Key Points |
|---------|-----------|
| **VFS/Vnode** | Standard interface for multiple file system types |
| **Stateless** | Each request has all info; no server-side client state |
| **File Handle** | Volume ID + Inode Number + Generation Number |
| **Idempotent** | READ, WRITE, LOOKUP (safe to retry); MKDIR, CREATE (not safe) |
| **Close-to-Open** | On close, flush to server; on open, revalidate attributes |
| **Attribute Cache** | Reduce GETATTR RPCs (30s default) |
| **Write Buffering** | Decouple application from network latency |
| **NFSv4** | Stateful with leases, COMPOUND operations, delegations |
| **Failure Recovery** | Client retry (stateless); different from GFS leases |

**Key NFSv3 RPCs:**
- LOOKUP (directory → file handle)
- GETATTR (file handle → attributes)
- READ (file handle + offset + count → data)
- WRITE (file handle + offset + data → attributes)
- CREATE (dir handle + name → file handle)
- REMOVE (dir handle + name → status)
- READDIR (dir handle + cookie → entries)

**Failure Handling:** Client retries after timeout. Idempotent operations safe; non-idempotent may return false errors.
