# Distributed Shared Memory

Procs can share virtual address spaces across machines.

> [!question] Can we store a part of the virtual space in 1 machine, and another part in another machine?
> Yes, since we do paging

If the page is on the machine, then, it can be quickly fetched, but if it's not, a page fault will occur, then the page handler will find the machine that has the page, and will send a message to the other machine to fetch the page. The machine will get the page, and update its page table, following which the execution resumes.

It's not popular today though, as it has a lot of failure points.
In a distributed system:
- Machines can crash
- Network can fail
- What if a machine holding a page dies?
- What if you had the _only valid copy_ of data?

# Remote Procedural Call (RPC)

We've to call functions on other PCs.

So, instead of writing
```c
send(socket, request);
recv(socket, response);
```

we can just do 
```c
result = add(5, 3);
```
…but `add()` is actually running on another machine.

## Client Side

- Client function
- Client Stub (fake function that we call)
- Sockets (network layer)

Client calls `add(5,3)`. 
It then goes to the client stub (not the actual function).
```c
int add(int a, int b) {
    // NOT real logic...just the function on the client side
    serialize(a, b);
    send_request("add", a, b);
    int res = receive_response();
    return res;
}
```
Stub sends the request via the sockets.

## Server side:

- Server stub (skeleton) → receives request
- Actual server function
- Sockets

## Entire Process

1. Client calls add(5,3)
2. Goes to the client stub (not the actual function)
3. Stub sends the request via a socket
4. Request travels over the network
5. Server stub receives the request
6. Calls the actual server function
7. Gets the result
8. Sends the result back
9. Client stub receives the result
10. Returns the result to the client.

## Client Stub

1. Makes the message buffer (allocates the space for the request)
2. Packs the arguments (marshalling & serialization)
   Eg: add(5,3) $\Rightarrow$ `[Function=add][arg1=5][arg2=3]` in bytes
3. The message is sent via the socket
4. Wait for a reply (usually blocking)
5. Unpack the response (unmarshalling & deserialization)
6. Return the result

## Server Stub

1. Recv the message from the socket.
2. Unpack the arguments (decode bytes to parameters)
3. Call the actual function
4. Package the result.
5. Send the reply

Instead of 1 request at a time, we use many worker threads, which help in improving the throughput

RPCs usually use UDP, with their own reliability layer. Uses timeouts, retries, and acks.

If there are large arguments, fragmentation and reassembly is done.

Synchronous and Asynchronous RPC : Either block until we receive an output, or just continue execution with a promise data structure, until we actually need the value, and if the value still hasn't been updated.


# gRPC

Uses protocol buffers: Efficient binary serialization (A compact, binary format to encode structured data)

> [!question] RPC hides network communication behind a function call. List three things the RPC runtime must handle that a local function call does not. For each, give a scenario where the naive approach fails.
> 
> - 1. Network failures: Caller may wait forever. Solution: Timeout + retry.
>         
> - 2. Server crashes: Retry may hit rebooted server that lost state (if server is stateful). Solution: Idempotent operations or stateless design.
>         
> - 3. Marshaling differences: Different endianness or structure padding. Solution: Standard serialization (XDR, Protobuf).
>         

> [!question] Comparing RPC to file system system calls (from slide 6): A local read() system call involves a trap into the kernel but no network. How does the failure model differ? If an RPC call returns -1, what does that mean compared to a local read() returning -1?
> 
> - Local read(): -1 means kernel error (bad fd, disk failure, etc.). The relationship between caller and kernel is trusted.
>     
> - RPC: -1 could mean server rejected request, network timeout, server crashed, reply lost, or actual operation failed. Ambiguity is fundamental.
>     

> [!question] Connect RPC to NFS (slide 13). NFS uses stateless protocol where each request carries full file handle. How does this design choice simplify RPC failure handling compared to a stateful protocol (like early NFS with file descriptors)? What advantage does stateful have that NFS traded away?
> 
> - Stateless: Server can crash and reboot. Client retries with same file handle. No "reopen" needed. Idempotent operations work.
>     
> - Stateful: Better performance (no repeated lookups), but crash requires recovery protocol (re-establish state).
>     
> - NFS traded state for simplicity and crash tolerance.
>     

> [!question] Distributed Shared Memory (DSM) allows processes on different machines to share a virtual address space via page faults over the network. Compare this to GFS (slide 14). DSM handles fine-grained (page-level) sharing; GFS handles coarse-grained (file/chunk-level) sharing. Why did DSM largely fail while GFS succeeded for Google's workloads?
> 
> - DSM: False sharing, page thrashing, network round-trip on every page fault (~microseconds vs nanoseconds for local). Failure of one machine kills all.
>     
> - GFS: Coarse granularity (64MB chunks) amortizes network cost. Applications are batch-oriented, not fine-grained sharing.
>     
> - Lesson: Matching abstraction to workload is critical. DSM fine for tightly-coupled clusters (rare); GFS for loosely-coupled commodity clusters.

## 1. What is a Distributed System?

### Definition
> A distributed system is a collection of **independent computers** that appear to users as a **single coherent system**. The computers communicate via a network and coordinate their actions by passing messages.

### The Fundamental Challenge
> **Components fail independently.** The network is unreliable. There is no shared clock. Yet the system must appear coherent.

### Why Distribute?

| Reason | Explanation |
|--------|-------------|
| **Scalability** | Add more machines as workload grows |
| **Fault tolerance** | No single point of failure |
| **Geography** | Place data near users |
| **Economics** | Many cheap computers vs one expensive supercomputer |
| **Resource sharing** | Pool storage, compute, devices |

---

## 2. The Unreliable Communication Problem

### The Core Reality
> Communication over a network is **fundamentally unreliable**.

### Types of Failures

| Failure Type | Cause | Manifestation |
|--------------|-------|---------------|
| **Packet loss** | Buffer overflow in router, congestion, bit errors | Message never arrives |
| **Packet corruption** | Electrical noise, interference | Bits flipped; detected by checksum |
| **Packet reordering** | Different routes, different delays | Messages arrive out of order |
| **Packet duplication** | Retransmission without acknowledgment | Same message arrives twice |
| **Node crash** | Power failure, OS panic, hardware fault | No response ever |
| **Network partition** | Switch/link failure | Two groups of nodes cannot reach each other |

### The Two Hard Problems

| Problem | Description |
|---------|-------------|
| **Failures are indistinguishable** | Did the server crash, or is the network slow? |
| **No global clock** | How do you order events across machines? |

## 3. UDP: Unreliable Datagram Protocol

### How UDP Works
> Sender sends a datagram. Receiver may or may not receive it. No guarantee. No retransmission. No ordering.

```
Sender                                     Receiver
   │                                           │
   │  send(datagram)                           │
   ├──────────────────────────────────────────►│
   │                                           │
   │  (no acknowledgment)                      │
   │                                           │
   │  datagram may be LOST                     │
   │  datagram may arrive CORRUPTED            │
   │  datagram may arrive OUT OF ORDER         │
   │  datagram may be DUPLICATED               │
```

### UDP Features

| Feature | Status |
|---------|--------|
| Checksum for corruption detection | Yes |
| Acknowledgment | No |
| Retransmission | No |
| Ordering guarantee | No |
| Congestion control | No |
| Connection setup | No |

### When to Use UDP

| Use Case | Why |
|----------|-----|
| Streaming media | Lost packets OK; retransmission would cause delay |
| DNS queries | Single request-response; retry at application level |
| Gaming | Fast is better than reliable |
| Real-time monitoring | Old data useless anyway |

### UDP Sockets API

```c
// Sender
int sock = socket(AF_INET, SOCK_DGRAM, 0);
struct sockaddr_in server_addr;
sendto(sock, buffer, len, 0, (struct sockaddr*)&server_addr, sizeof(server_addr));

// Receiver
int sock = socket(AF_INET, SOCK_DGRAM, 0);
bind(sock, (struct sockaddr*)&addr, sizeof(addr));
recvfrom(sock, buffer, sizeof(buffer), 0, (struct sockaddr*)&client_addr, &client_len);
```

## 4. TCP: Reliable Transmission Protocol

### How TCP Works
> Provides the abstraction of a **reliable byte stream** over an unreliable network.

### The Three-Way Handshake (Connection Setup)

```
Client                                    Server
   │                                         │
   │  SYN (seq=x)                            │
   ├────────────────────────────────────────►│
   │                                         │
   │                    SYN-ACK (seq=y, ack=x+1)
   │◄────────────────────────────────────────┤
   │                                         │
   │  ACK (seq=x+1, ack=y+1)                 │
   ├────────────────────────────────────────►│
   │                                         │
   │              CONNECTION ESTABLISHED      │
```

### Reliable Transmission Mechanism

| Problem | TCP Solution |
|---------|--------------|
| Packet loss | Timeout + retransmission |
| Duplicate packets | Sequence numbers deduplicate |
| Out-of-order packets | Sequence numbers reorder |
| Corrupted packets | Checksum + retransmit |
| Flow control | Sliding window (receiver advertises space) |
| Congestion control | Slow start, congestion avoidance |

### Sequence Numbers (How Duplicates Are Detected)

```
Sender sends: seq=100, data="Hello"
Sender sends: seq=116, data="World"

If first ACK lost, sender retransmits:
Sender sends: seq=100, data="Hello" again

Receiver: Already received seq=100, discards duplicate
Receiver: Sends ACK for seq=116
```

### TCP vs UDP

| Feature | UDP | TCP |
|---------|-----|-----|
| Reliability | No | Yes |
| Ordering | No | Yes |
| Congestion control | No | Yes |
| Connection state | None (stateless) | Connection state (stateful) |
| Header size | 8 bytes | 20 bytes |
| Latency | Lower (no setup) | Higher (3-way handshake) |
| Throughput | As fast as network | Adjusts to congestion |

### When to Use TCP

| Use Case | Why |
|----------|-----|
| File transfer | Cannot lose data |
| Web (HTTP) | Need reliable transmission |
| Email (SMTP) | Cannot lose messages |
| Database replication | Must be consistent |
| SSH | Need ordered reliable stream |

## 5. Remote Procedure Call (RPC)

### The Problem
> Distributed systems need to call functions on remote machines. Sending raw messages (send/receive) is too low-level.

### What RPC Does
> Makes a remote function call look like a **local function call** to the programmer.

### RPC Architecture

```
┌─────────────────────────────────────────────────────────────────────┐
│                           CLIENT                                    │
│  ┌─────────────────────────────────────────────────────────────┐    │
│  │                    Client Code                              │    │
│  │                                                             │    │
│  │    result = remote_function(arg1, arg2);  ← looks local!    │    │
│  └───────────────────────────┬─────────────────────────────────┘    │
│                              │                                      │
│  ┌───────────────────────────▼─────────────────────────────────┐    │
│  │                    Client Stub                              │    │
│  │    - Marshals arguments (pack into message)                 │    │
│  │    - Sends message to server                                │    │
│  │    - Waits for reply                                        │    │
│  │    - Unmarshals result                                      │    │
│  └───────────────────────────┬─────────────────────────────────┘    │
└──────────────────────────────┼──────────────────────────────────────┘
                               │ (Network)
                               ▼
┌─────────────────────────────────────────────────────────────────────┐
│                           SERVER                                    │
│  ┌─────────────────────────────────────────────────────────────┐    │
│  │                    Server Stub                              │    │
│  │    - Unmarshals arguments                                   │    │
│  │    - Calls actual remote_function()                         │    │
│  │    - Marshals result                                        │    │
│  │    - Sends reply                                            │    │
│  └───────────────────────────┬─────────────────────────────────┘    │
│                              │                                      │
│  ┌───────────────────────────▼─────────────────────────────────┐    │
│  │                    Actual Function                          │    │
│  │                    remote_function()                        │    │
│  └─────────────────────────────────────────────────────────────┘    │
└─────────────────────────────────────────────────────────────────────┘
```

### Marshaling (Serialization)
> Converting data structures into a byte stream that can be sent over the network.

| Challenge | Solution |
|-----------|----------|
| Different endianness | Standard format (e.g., network byte order, Protocol Buffers) |
| Different structure padding | Explicit serialization format |
| Pointers | Must dereference and send pointed-to data |
| Large data | Fragmentation and reassembly |

### RPC Steps (Client Side)

```
1. Client calls remote_function(arg1, arg2)
2. Client stub marshals arguments → message
3. Client sends message to server
4. Client waits (blocks) for reply
5. Reply arrives, stub unmarshals result
6. Client function returns with result
```

### RPC Steps (Server Side)

```
1. Server receives message
2. Server stub unmarshals arguments
3. Server stub calls actual remote_function()
4. Function returns, stub marshals result
5. Server sends reply
```

### RPC Design Challenges

| Challenge | Problem | Solution |
|-----------|---------|----------|
| **Network latency** | RPC is slower than local call | Async RPC, batching |
| **Failure handling** | Server crash, network loss | Timeout + retry |
| **Duplicate requests** | Retry may cause double execution | Idempotent operations, sequence numbers |
| **Large arguments** | Message too big | Fragmentation, streaming |
| **Locating server** | Where is the service? | Service registry, naming service |
| **Binding** | Which version of function? | Interface definition language (IDL) |

### RPC Failure Modes

| Failure | Client Sees | Correction |
|---------|-------------|------------|
| **Request lost** | Timeout | Retransmit request |
| **Server crashed before execution** | Timeout | Retry (safe if idempotent) |
| **Server crashed after execution, before reply** | Timeout | Retry (may duplicate work) |
| **Reply lost** | Timeout | Retry (server may re-execute) |
| **Server slow** | Timeout (false positive) | Retry, may get duplicate execution |

### At-Least-Once vs At-Most-Once vs Exactly-Once

| Semantics | Meaning | How to achieve |
|-----------|---------|----------------|
| **At-least-once** | Operation may execute 1+ times | Retry on timeout. Simple. |
| **At-most-once** | Operation executes 0 or 1 times | Server remembers executed request IDs. |
| **Exactly-once** | Operation executes exactly once | Combination of at-most-once + retry until success. Very hard. |

### RPC Implementation Optimizations

| Optimization | How it works | Benefit |
|--------------|--------------|---------|
| **Thread pool** | Multiple worker threads handle RPCs | Server handles concurrent requests |
| **Asynchronous RPC** | Client continues working, checks later | Overlap computation with communication |
| **Batching** | Combine multiple RPCs into one message | Reduce network overhead |
| **Protocol buffers** | Efficient serialization | Smaller messages, faster parsing |

## 6. gRPC (Google RPC)

### What is gRPC?
> A high-performance, open-source RPC framework developed by Google. Uses **Protocol Buffers** for serialization and **HTTP/2** for transport.

### Protocol Buffers (Protobuf)

```protobuf
// Define the service and messages
service FileService {
  rpc ReadFile(ReadRequest) returns (ReadResponse);
  rpc WriteFile(WriteRequest) returns (WriteResponse);
}

message ReadRequest {
  string filename = 1;
  int64 offset = 2;
  int32 length = 3;
}

message ReadResponse {
  bytes data = 1;
  int64 actual_length = 2;
}
```

### Why Protocol Buffers?

| Feature | Benefit |
|---------|---------|
| Language-neutral | Generate code for Java, C++, Python, Go, etc. |
| Binary format | Smaller than JSON/XML |
| Backward compatible | New fields ignored by old clients |
| Strong typing | Compile-time type checking |
| Fast serialization | Much faster than reflection-based |

### gRPC vs Traditional RPC

| Aspect | Traditional RPC (Sun RPC) | gRPC |
|--------|--------------------------|------|
| **Transport** | UDP or TCP | HTTP/2 |
| **Serialization** | XDR (external data representation) | Protocol Buffers |
| **Streaming** | Request-response only | Bidirectional streaming |
| **Language support** | Limited | Wide (C++, Java, Python, Go, etc.) |
| **Load balancing** | Custom | HTTP/2 load balancing |
| **Deadlines/timeouts** | Application handles | Built-in |

### gRPC Streaming Types

| Type | Description |
|------|-------------|
| **Unary** | Single request, single response (traditional RPC) |
| **Server streaming** | Single request, stream of responses |
| **Client streaming** | Stream of requests, single response |
| **Bidirectional streaming** | Stream of requests, stream of responses |

## 7. Distributed Shared Memory (DSM)

### What is DSM?
> An abstraction that allows processes on different machines to share a **single virtual address space**.

### How DSM Works

```
Machine A                              Machine B
┌─────────────────┐                   ┌─────────────────┐
│ Process P       │                   │ Process Q       │
│ ┌─────────────┐ │                   │ ┌─────────────┐ │
│ │ Virtual     │ │                   │ │ Virtual     │ │
│ │ Address     │ │                   │ │ Address     │ │
│ │ Space       │ │                   │ │ Space       │ │
│ └──────┬──────┘ │                   │ └──────┬──────┘ │
│        │        │                   │        │        │
│   Page fault    │                   │   Page fault    │
│        │        │                   │        │        │
└────────┼────────┘                   └────────┼────────┘
         │                                     │
         │ (page from remote)                  │ (page from remote)
         ▼                                     ▼
┌─────────────────┐                   ┌─────────────────┐
│ DSM Page Manager│◄─────Network─────►│ DSM Page Manager│
│ (fault handler) │                   │ (fault handler) │
└─────────────────┘                   └─────────────────┘
```

### DSM Page Fault Handling

```
Process on Machine A accesses address 0x1000
        │
        ▼
Page is not in A's physical memory (page fault)
        │
        ▼
DSM fault handler determines which machine has the page
        │
        ▼
DSM sends message to that machine requesting the page
        │
        ▼
Remote machine sends the page contents
        │
        ▼
Local machine installs page in memory
        │
        ▼
Process continues execution
```

### Why DSM Failed (Not Popular)

| Problem | Explanation |
|---------|-------------|
| **False sharing** | Two unrelated variables on same page cause unnecessary page transfers |
| **Thrashing** | Multiple machines repeatedly requesting same page |
| **Granularity** | Page is too large (4KB) for fine-grained sharing; too small for efficient transfer |
| **Failure handling** | If one machine fails, all machines lose access to its pages |
| **Performance** | Page fault over network: milliseconds vs nanoseconds for local |
| **Consistency** | Maintaining cache coherence across machines is expensive |

### When DSM Might Work

| Use Case | Why |
|----------|-----|
| Tightly-coupled clusters | Low-latency network (InfiniBand) |
| Read-mostly data | Few writes, so few invalidations |
| Large pages | Reduce fault frequency |
| Scientific computing | Regular access patterns |

### DSM vs Message Passing (MPI)

| Aspect | DSM | MPI |
|--------|-----|-----|
| **Abstraction** | Shared memory (loads/stores) | Message passing (send/receive) |
| **Programming model** | Easier (looks like multithreading) | Harder (explicit communication) |
| **Performance** | Hard to predict (page faults) | Predictable (explicit transfers) |
| **Scalability** | Poor (false sharing, thrashing) | Good (explicit control) |
| **Failure tolerance** | Poor (single machine failure affects all) | Better (processes independent) |
| **Popularity** | Low (research only) | High (HPC standard) |

## 8. Failure Detection and Handling

### The Fundamental Problem
> In a distributed system, you cannot distinguish between a crashed node and a slow network.

### Failure Detection Mechanisms

| Mechanism | How it works | Problem |
|-----------|--------------|---------|
| **Timeout** | Wait T seconds; if no response, assume failed | What is the right T? Too short → false positives; Too long → slow detection |
| **Heartbeat** | Nodes periodically send "I am alive" messages | Same timeout problem |
| **Ping-pong** | Send "are you alive?"; wait for "yes" | Network loss causes false failure |
| **Lease** | Node given authority for finite time; must renew | Still need timeout for renewal |

### The Timeout Dilemma

```
If T is too small:
    Network hiccup → false failure → system wastes time recovering a live node

If T is too large:
    Real failure → system waits T seconds before recovery → service unavailable during T

Optimal T depends on network conditions, which vary!
```

### Handling Different Failure Types

| Failure | Detection | Handling |
|---------|-----------|----------|
| **Message loss** | Timeout + no ACK | Retransmit (with idempotency) |
| **Node crash** | Heartbeat timeout | Failover to replica; client retries |
| **Network partition** | Both sides lose heartbeats | Split-brain prevention (quorum, leases) |
| **Byzantine (malicious)** | Cryptographic signatures | Very hard; not covered in basic DS |

## 9. RPC vs Message Passing vs Shared Memory

| Aspect | Message Passing (UDP/TCP) | RPC | Shared Memory (DSM) |
|--------|--------------------------|-----|---------------------|
| **Abstraction** | Send/receive | Function call | Load/store |
| **Programmer view** | Explicit communication | Looks local | Looks local |
| **Error handling** | Manual (check return codes) | Automatic (timeout + retry in stub) | Page faults (automatic) |
| **Performance** | High (direct control) | Moderate (marshaling overhead) | Low (page faults over network) |
| **Complexity** | High (manual all) | Moderate (IDL, stubs generated) | Low (programming model) |
| **Failure visibility** | Visible to programmer | Hidden (stub handles) | Hidden (DSM handles) |
| **Use case** | Systems programming, games | Web services, microservices | Research only |

## HARD DESIGN QUESTIONS

> [!question] You are designing a distributed key-value store. Clients send PUT and GET requests to a server. The network drops 1% of packets. Compare implementing on UDP vs TCP. What additional logic does the UDP version require? Which has lower latency under 0.1% packet loss? Which under 10% packet loss?
>
> **UDP Implementation Requirements:**
>
> ```
> Client sends PUT request:
>     Start timer
>     Send request
>     If no response within timeout:
>         Retransmit (same request)
>         Start timer again
>     (Repeat until success or max retries)
>
> Server must handle duplicate requests:
>     Track sequence numbers per client
>     Discard already-processed requests
>     Return cached response for duplicates
> ```
>
> **Comparison:**
>
> | Aspect | UDP | TCP |
> |--------|-----|-----|
> | **Additional logic** | Timeout, retransmit, sequence numbers, duplicate detection, reordering | None (TCP handles) |
> | **Connection setup** | None (0 RTT) | 3-way handshake (1.5 RTT) |
> | **Per-request overhead** | Low (8 byte header) | Higher (20 byte header + state) |
> | **Head-of-line blocking** | No (independent datagrams) | Yes (lost packet blocks later packets) |
>
> **Latency comparison:**
>
> | Packet loss | UDP | TCP | Winner |
> |-------------|-----|-----|--------|
> | 0.1% | 1 RTT (typical) | 1.5 RTT (setup) + retransmission | UDP |
> | 10% | Many retransmits, no congestion control | Exponential backoff, better congestion control | TCP |
>
> **Recommendation:** UDP for low-loss networks (data center). TCP for high-loss networks (internet).

> [!question] RPC makes remote calls look like local calls. List three ways this abstraction **leaks** (fails to hide the network). For each, give a concrete scenario where a programmer expecting local semantics would be surprised.
>
> **Leak 1: Latency**
>
> ```
> Local function call: 0.1 microseconds
> Remote RPC: 1 millisecond (10,000x slower)
>
> Surprise: A loop that calls remote_function() 1000 times takes 1 second,
>         not 0.0001 seconds. Programmer must batch calls.
> ```
>
> **Leak 2: Partial failures**
>
> ```
> Local function call: Either returns result or crashes process
> Remote RPC: May time out (server slow?), may get duplicate execution, may get no response
>
> Surprise: Character count = remote_count_chars("file.txt");
>          // Could return wrong count if retry causes duplicate?
>          // Could hang indefinitely if server dead?
> ```
>
> **Leak 3: Reference arguments**
>
> ```
> Local: void increment(int* x) { (*x)++; }
>        increment(&a);  // a changes
>
> RPC: Cannot pass pointers! Pointer is meaningless on remote machine.
>      Must copy data (marshaling) and send.
>      Changes to pointed-to data after call won't be seen.
> ```
>
> **Other leaks:**
> - Global variables (different on server vs client)
> - Exception handling (RPC errors are network errors, not logic errors)
> - Threading (RPC stub may block calling thread)

> [!question] In distributed shared memory (DSM), what is false sharing? Give a concrete example. Two processes on different machines access different 4-byte integers that happen to be on the same 4KB page. Machine A writes to int1; Machine B writes to int2. How many page transfers occur? How many are necessary? How would you redesign the data structure to avoid false sharing?
>
> **False sharing defined:**
> > Two unrelated variables on the same cache line/page cause unnecessary coherence traffic when different processors write to different variables.
>
> **Concrete example:**
>
> ```c
> struct data {
>     int counter_for_cpu0;  // offset 0, accessed only by CPU0
>     int counter_for_cpu1;  // offset 4, accessed only by CPU1
>     // rest of page (up to 4096 bytes)
> };
> ```
>
> **Page transfers (page size=4KB, Linux default):**
>
> ```
> Initial: Page on Machine M
>
> Machine A writes to counter_for_cpu0:
>     Page fault → transfer page from M to A
>     A writes to its copy
>
> Machine B writes to counter_for_cpu1:
>     Page fault → transfer page from A to B (or M to B, depending on protocol)
>     B writes to its copy
>
> Machine A writes again:
>     Page fault → transfer page from B to A (again!)
>
> Result: Each write causes a page transfer! Hundreds of unnecessary transfers.
> ```
>
> **Necessary transfers:**
> - Zero if the two integers were on different pages
> - Only when the page's data is actually needed (which never happens if each CPU only touches its own variable)
>
> **Redesign to avoid false sharing:**
>
> ```c
> struct data {
>     int counter_for_cpu0;
>     char padding[4096 - sizeof(int)];  // Force to separate page
> };
> struct data per_cpu_data[MAX_CPUS];
>
> // OR: Align to page boundary
> struct __attribute__((aligned(4096))) data {
>     int counter;
> };
> ```
>
> **Lesson:** DSM forces programmers to think about physical memory layout, defeating the "shared memory abstraction."

> [!question] You are building a distributed system where servers must process client requests exactly once (no duplicates, no misses). The network can drop, reorder, or duplicate packets. Servers can crash and reboot. Describe a protocol using sequence numbers and persistent storage that achieves exactly-once semantics. What is the performance cost?
>
> **Exactly-Once Protocol:**
>
> ```
> Client state (persistent):
>     next_seq = 0
>     pending_requests = map<seq, request>
>
> Server state (persistent):
>     last_completed_seq[client_id] = last_seq
>     completed_results[seq] = response (cached)
>
> Client sends request:
>     seq = next_seq++
>     Store request in pending_requests[seq]
>     Send (client_id, seq, request, checksum)
>     Start timer
>
> Server receives request (client_id, seq, request):
>     if seq <= last_completed_seq[client_id]:
>         // Already processed
>         Reply with cached completed_results[seq]
>     else if seq == last_completed_seq[client_id] + 1:
>         // Expected next request
>         Process request
>         Store result in completed_results[seq]
>         Update last_completed_seq[client_id] = seq
>         Reply with result
>     else if seq > last_completed_seq[client_id] + 1:
>         // Out of order; buffer or reject (client will retransmit)
>         Send NAK with expected_seq
>
> Client receives reply:
>     if reply is for seq:
>         Remove pending_requests[seq]
>     else if reply contains expected_seq:
>         Adjust next_seq = expected_seq, retransmit from there
>
> On timeout:
>     Client retransmits all pending_requests
> ```
>
> **Performance cost:**
>
> | Cost | Explanation |
> |------|-------------|
> | **Persistent storage write** | Server must fsync() before replying (milliseconds) |
> | **Sequence number management** | Overhead per request (small) |
> | **Storage for completed results** | Must cache responses until client acknowledges (memory/disk) |
> | **Recovery time** | Server must reload last_completed_seq from disk |
> | **Throughput** | fsync() limits to ~100-1000 requests/sec (vs 100K+ without) |
>
> **Optimization:** Batch multiple requests into one fsync(). Group commit (like ext3 journaling).

> [!question] Compare the failure detection mechanisms in GFS (heartbeats + leases) and NFSv3 (timeout + retry). Which detects failure faster? Which is more resilient to network delays? Which requires more state on the server?
>
> **Comparison table:**
>
> | Aspect | GFS (Leases + Heartbeats) | NFSv3 (Timeout + Retry) |
> |--------|---------------------------|-------------------------|
> | **Detection mechanism** | Heartbeat from server to master | Client timeout waiting for response |
> | **Who detects** | Master (centralized) | Each client (distributed) |
> | **Detection time** | 60 seconds (configurable) | Client-dependent (typically 1-5 seconds) |
> | **Resilience to network delay** | Poor (masters declares false death on slow network) | Better (each client adjusts timeout) |
> | **State on server** | Lease state per chunk | None (stateless) |
> | **False positive cost** | Master fails over, version increments | Client retries (idempotent, cheap) |
> | **Scalability** | Master must track all chunks (memory) | No central tracking |
>
> **Which detects failure faster?** NFSv3 (clients detect in seconds vs GFS master's 60 seconds)
>
> **Which is more resilient to network delays?** NFSv3 (each client has own timeout) better than GFS (fixed heartbeat timeout)
>
> **Which requires more state?** GFS (master stores lease state, version numbers)
>
> **Design trade-off:**
> - GFS: Centralized detection, stronger semantics (ordered writes), but slower failover
> - NFSv3: Distributed detection, weaker semantics (close-to-open), but faster client-side failure response

> [!question] A distributed system uses at-least-once RPC semantics. A client calls `transfer_money(from_account, to_account, amount)`. The server executes the transfer, commits to database, then crashes before sending reply. Client retries. What happens? Why is idempotency important? How would you redesign the RPC to be idempotent?
>
> **What happens:**
>
> ```
> Client: transfer_money(A, B, $100)  // RPC call
> Server: Executes transfer (A -= 100, B += 100)
> Server: Commits to database
> Server: CRASH before sending reply
> Client: Times out, retries
> Server (after reboot): Executes transfer AGAIN (A -= 100, B += 100)
> Result: $200 transferred! Double deduction.
> ```
>
> **Why idempotency is important:**
> > Idempotent operation: performing it multiple times = performing it once.
>
> `transfer_money` is NOT idempotent. Second execution changes state again.
>
> **Redesign for idempotency:**
>
> **Option 1: Include transaction ID**
>
> ```c
> struct TransferRequest {
>     uint64_t txn_id;        // Unique per request
>     int from_account;
>     int to_account;
>     int amount;
> };
>
> Server state (persistent):
>     completed_txns = set<txn_id>
>
> On transfer_money(request):
>     if request.txn_id in completed_txns:
>         return SUCCESS (idempotent)
>     // Execute transfer exactly once
>     completed_txns.insert(request.txn_id)
>     return SUCCESS
> ```
>
> **Option 2: Make transfer operation commutative**
>
> ```c
> // Instead of debit/credit, record pending transfer
> struct PendingTransfer {
>     uint64_t txn_id;
>     int from_account;
>     int to_account;
>     int amount;
> };
>
> // Idempotent: inserting same pending transfer twice has same effect as once
> ```
>
> **Option 3: Use "test-and-set" with version numbers**
>
> ```c
> On transfer(version_from, version_to, amount):
>     if current_version_from != version_from:
>         return RETRY  // Client must re-read
>     // Execute transfer
>     version_from++; version_to++;
> ```
>
> **Lesson:** At-least-once RPC requires application-level idempotency or duplicate detection.

> [!question] gRPC uses HTTP/2 and Protocol Buffers. Compare gRPC with a traditional RPC system (like Sun RPC over UDP). Consider: connection management, serialization efficiency, error handling, streaming support.
>
> **Comparison table:**
>
> | Aspect | Sun RPC (UDP) | gRPC (HTTP/2) |
> |--------|---------------|---------------|
> | **Connection** | Connectionless (UDP) | Persistent TCP connection |
> | **Setup overhead** | None (0 RTT) | 1.5 RTT (TCP) + HTTP/2 (minimal) |
> | **Serialization** | XDR (external data representation) | Protocol Buffers |
> | **Serialization speed** | Moderate | Fast (code-generated) |
> | **Message size** | Small | Small (binary) |
> | **Streaming** | No (request-response only) | Yes (bidirectional) |
> | **Error handling** | Application must implement | HTTP status codes + trailers |
> | **Load balancing** | Custom (client must implement) | HTTP/2 load balancing (native) |
> | **Flow control** | None (UDP) | HTTP/2流控制 |
> | **Head-of-line blocking** | No (UDP independent) | Yes (TCP stream) |
> | **Firewall traversal** | Poor (UDP often blocked) | Good (HTTP/2 over port 443) |
> | **Language support** | Limited (C, some others) | Wide (C++, Java, Go, Python, Rust, etc.) |
>
> **When to choose gRPC:**
> - Microservices (HTTP/2 friendly)
> - Need streaming (real-time updates)
> - Multiple languages (Protobuf code generation)
> - Firewalls/NATs (port 443 works)
>
> **When to choose Sun RPC style:**
> - Low-latency requirement (UDP has no setup cost)
> - Simple request-response
> - Single language (C)
> - Controlled network environment

> [!question] You are designing a distributed file system. Compare three communication models: (1) raw message passing (send/recv), (2) RPC, (3) distributed shared memory (DSM). Which would you choose for a system like GFS? For a system like NFS? For a system like MPI? Justify each choice.
>
> **GFS (Google File System) choice: RPC**
>
> | Why RPC | Why not others |
> |---------|----------------|
> | Master-chunkserver communication is request-response | DSM would be too heavy (page faults over network) |
> | Client-chunkserver reads are simple: "give me bytes X-Y" | Message passing would expose network details to application |
> | Clear operation semantics (Open, Read, Write, Append) | RPC abstraction fits file operations naturally |
> | GFS already has leases and replication; RPC simpler | |
>
> **NFS (Network File System) choice: RPC**
>
> | Why RPC | Why not others |
> |---------|----------------|
> | NFS is built on RPC (Sun RPC originally) | DSM doesn't work across WAN |
> | Stateless protocol fits RPC model | Message passing would require each application to implement NFS protocol |
> | LOOKUP, READ, WRITE map directly to RPC calls | |
>
> **MPI (Message Passing Interface) choice: Message passing**
>
> | Why message passing | Why not others |
> |--------------------|----------------|
> | MPI is explicitly about sending/receiving messages | RPC hides network; MPI programmers need explicit control |
> | Collective operations (broadcast, scatter, gather) are natural as messages | DSM has false sharing, performance unpredictable |
> | HPC workloads need predictable latency/bandwidth | RPC's at-least-once semantics cause duplicates (bad for numerics) |
> | Non-blocking operations require message passing API | |
>
> **Summary:**
>
> | System | Communication Model | Rationale |
> |--------|---------------------|-----------|
> | GFS | RPC | Request-response fits file operations |
> | NFS | RPC | Built on RPC from day 1 |
> | Lustre | RPC + custom | HPC needs performance, but uses RPC-like |
> | MPI | Message passing | Explicit control for performance |
> | DSM research | DSM | Academic curiosity; not practical |

## QUICK REFERENCE CARD

| Concept | Key Points |
|---------|-----------|
| **UDP** | Unreliable, no ordering, no connection, fast |
| **TCP** | Reliable, ordered, connection setup, congestion control |
| **RPC** | Makes remote call look local; marshaling; timeout + retry |
| **gRPC** | Protobuf + HTTP/2; streaming; language-neutral |
| **DSM** | Shared memory across machines; false sharing; not popular |
| **At-least-once** | May execute 1+ times; requires idempotency |
| **At-most-once** | Executes 0 or 1 times; needs request tracking |
| **Exactly-once** | Very hard; requires persistent state + coordination |
| **Failure detection** | Heartbeats, timeouts, leases |

**The Two Hard Problems in Distributed Systems:**
1. **Distinguishing failure from slowness** (timeout dilemma)
2. **Ordering events without a global clock** (Lamport clocks, vector clocks)
