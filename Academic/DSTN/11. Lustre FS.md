## Core Design Problem

How do you build a single POSIX-compliant file system that scales to thousands of clients and petabytes of storage? (HPC supercomputers)

## Key Concepts

- **Separate metadata (MDT) and data (OST) servers**: Ensures metadata ops don't block data transfers.
    
- **Striping**: File split across multiple OSTs in round-robin (stripe_count, stripe_size).
    
- **Progressive File Layout (PFL)**: Different stripe counts for different file regions (e.g., first 128MB: 1 stripe, rest: 16 stripes).
    
- **FID (File IDentifier)** : 128-bit identifier (SEQ + OID + version).
    
- **Failover pairs**: Active/passive or active/active for high availability.
    

---

> [!question] Lustre separates metadata (MDT) from data (OST). How is this similar to GFS's master/chunkserver separation? How is it different? Why does Lustre still need distributed namespace (DNE with multiple MDTs) while GFS works with a single master?
> 
> - Similar: Control path separate from data path.
>     
> - Difference: GFS master stores all metadata in memory (limited by RAM). Lustre MDT stores on disk (ext4/lustre) and can scale via DNE (multiple MDTs).
>     
> - GFS single master works because Google uses full paths (no directory listings). Lustre supports POSIX directory operations (ls, find) → single MDT becomes bottleneck for billions of files → need DNE.
>     

> [!question] Compare Lustre striping (round-robin across OSTs) with RAID 0 striping (slide 17). A 1TB file with stripe_count=4 and stripe_size=1MB is written. How many OSTs are involved? If one OST fails, how much data is lost? How does this compare to RAID 0 failure?
> 
> - 4 OSTs involved.
>     
> - Lost data: 1/4 to 1/2 of file (depending on which OST fails). File cannot be recovered.
>     
> - RAID 0 with 4 disks: identical failure mode (any disk lost → entire array lost). Both have no redundancy.
>     
> - Lustre relies on backing RAID (RAID 6 on OST) for redundancy, not filesystem-level.
>     

> [!question] Progressive File Layout (PFL) changes striping parameters as file grows (e.g., first 128MB: 1 stripe; next 512MB: 3 stripes; rest: 16 stripes). What workload benefits from PFL? When would PFL hurt performance?
> 
> - Benefits: Small files (first portion) avoid overhead of many OSTs (less network, fewer locks). As file grows (large sequential) → more stripes → higher bandwidth.
>     
> - Hurts: Random access to middle region (different stripe counts cause non-uniform latency). Metadata more complex.
>     

> [!question] Connect Lustre to NFS's stateless design. Lustre clients cache locks and data. If an OST crashes and recovers, how does the client know whether its cached data is still valid? Compare to NFS's GETATTR validation.
> 
> - Lustre uses locks (stateful) from OST. After crash, locks are lost. Client must reacquire locks. OST may have stale data if client buffered writes.
>     
> - NFS stateless: No locks to lose. Client revalidates with GETATTR.
>     
> - Trade-off: Lustre better performance (caching, locks). NFS simpler recovery.

## 5. File Identifiers (FIDs)

### What is a FID?
> 128-bit identifier used internally for identifying files or objects (similar to inode numbers in local file systems)

### FID Structure

```
┌─────────────────────────────────────────────────────────────────┐
│                      128-bit FID                                │
├─────────────────────────────┬───────────────┬───────────────────┤
│        64-bit SEQ           │  32-bit OID   │ 32-bit VER        │
│   (Sequence Number)         │ (Object ID)   │ (Version)         │
├─────────────────────────────┼───────────────┼───────────────────┤
│ Identifies the MDT/OST      │ Unique within │ For stale         │
│ that owns this object       │ the SEQ       │ detection         │
└─────────────────────────────┴───────────────┴───────────────────┘
```

### Why FIDs Instead of Traditional Inodes?

| Traditional Inode | Lustre FID |
|------------------|------------|
| 32-bit (limited to 4B files) | 128-bit (essentially unlimited) |
| Unique per file system | Globally unique across clusters |
| No location information | SEQ encodes which MDT/OST |
| No versioning | VER detects stale handles |
| Reused after deletion | Never reused (with version increment) |

## 6. File Striping (The Core Feature)

### What is Striping?
> Lustre has the ability to stripe data across multiple OSTs in a **round-robin** fashion.

### Striping Parameters

| Parameter | Meaning | Default |
|-----------|---------|---------|
| **stripe_count** | Number of OSTs a file is striped across | 1 |
| **stripe_size** | Amount of data written to one OST before moving to next | 1 MB |
| **stripe_offset** | First OST to use (usually -1 for dynamic) | -1 (pick any) |

### Visual Example

```
File: 10 MB, stripe_count = 4, stripe_size = 1 MB

┌─────────────────────────────────────────────────────────────┐
│                      Logical File                            │
├───────┬───────┬───────┬───────┬───────┬───────┬───────┬─────┤
│ 0-1MB │ 1-2MB │ 2-3MB │ 3-4MB │ 4-5MB │ 5-6MB │ 6-7MB │ ... │
└───┬───┴───┬───┴───┬───┴───┬───┴───┬───┴───┬───┴───┬───┴─────┘
    │       │       │       │       │       │       │
    ▼       ▼       ▼       ▼       ▼       ▼       ▼
┌───────┐ ┌───────┐ ┌───────┐ ┌───────┐ ┌───────┐ ┌───────┐
│ OST 0 │ │ OST 1 │ │ OST 2 │ │ OST 3 │ │ OST 0 │ │ OST 1 │ ...
│ 1 MB  │ │ 1 MB  │ │ 1 MB  │ │ 1 MB  │ │ 1 MB  │ │ 1 MB  │
└───────┘ └───────┘ └───────┘ └───────┘ └───────┘ └───────┘

After 10 MB: OST0=3MB, OST1=3MB, OST2=2MB, OST3=2MB
```

### Striping Formulas

```
OST index for byte offset B = floor(B / stripe_size) % stripe_count

Example: stripe_size=1MB, stripe_count=4
- Byte 0-1MB: OST 0
- Byte 1-2MB: OST 1
- Byte 2-3MB: OST 2
- Byte 3-4MB: OST 3
- Byte 4-5MB: OST 0 (wraps)
```

## 7. Progressive File Layout (PFL)

### The Problem with Fixed Striping

| Small file | Large file |
|------------|------------|
| Stripe_count=16 wastes resources | Stripe_count=1 limits bandwidth |
| Too many OSTs involved | Only one OST used |
| Network overhead high | Sequential bandwidth capped |

### PFL Solution
> Different stripe counts for different regions of the same file.

### PFL Layout Example

```bash
lfs setstripe -E 128M -c 1 -E 512M -c 3 -E 2G -c 8 -E -1 -c 16 /mnt/lustre/a.txt
```

```
File Regions:
┌─────────────────────────────────────────────────────────────────────┐
│ 0-128MB    │ 128-512MB   │ 512MB-2GB    │ 2GB to end               │
│ stripe=1   │ stripe=3    │ stripe=8     │ stripe=16                │
│ (1 OST)    │ (3 OSTs)    │ (8 OSTs)     │ (16 OSTs)                │
└─────────────────────────────────────────────────────────────────────┘

Benefit:
- Small start: No overhead for small files
- Gradual increase: Bandwidth grows with file size
- Large end: Full parallelism for large sequential reads
```

### PFL vs Fixed Striping

| Workload | Fixed Striping (c=16) | PFL |
|----------|----------------------|-----|
| 1KB file | Wastes 16 OSTs, high overhead | Uses 1 OST (efficient) |
| 10GB file | Uses 16 OSTs (good) | Uses 1→16 OSTs (better for small initial reads) |
| Random access in middle | Always 16 OSTs | Region-dependent |
| Metadata overhead | Higher (16 objects) | Lower for small files |

## 8. Distributed Namespace Environment (DNE)

### The Problem
> Single MDT becomes bottleneck for metadata operations at very large scale (billions of files).

### DNE Solution
> Distribute the directory tree across multiple MDTs.

```
Without DNE (Single MDT):
┌─────────────────────────────────────┐
│              MDT 0                   │
│  / (root)                            │
│  ├── home/                           │
│  │   ├── user1/ (1M files)          │  ← All metadata on one MDT
│  │   ├── user2/ (1M files)          │     Bottleneck!
│  │   └── user3/ (1M files)          │
│  └── scratch/ (10M files)           │
└─────────────────────────────────────┘

With DNE (Multiple MDTs):
┌──────────────┐ ┌──────────────┐ ┌──────────────┐
│    MDT 0     │ │    MDT 1     │ │    MDT 2     │
│ / (root)     │ │ /home/user1/ │ │ /home/user2/ │
│ ├── home/    │ │ (1M files)   │ │ (1M files)   │
│ └── scratch/ │ └──────────────┘ └──────────────┘
│ (10M files)  │
└──────────────┘
```

### DNE Directory Striping
- Can stripe a directory across multiple MDTs
- Files in that directory distributed round-robin
- Improves create/lookup performance for large directories

## 9. Backend Storage: ldiskfs

### What is ldiskfs?
> Performance-enhanced ext4 file system used as the backend for MDT and OST storage.

### Features
- Based on ext4 (mature, stable)
- Performance optimizations for Lustre workloads
- Supports large files (up to 2TB on 32-bit, much larger on 64-bit)
- Supports extended attributes (for storing FIDs, layout)

### Why not use ext4 directly?
- ext4 doesn't understand Lustre striping
- ext4 doesn't support distributed transactions
- ldiskfs adds Lustre-specific features while maintaining ext4 compatibility

## 10. High Availability and Failover

### Data Redundancy
> Lustre does NOT provide data redundancy at the file system level. It depends on backing storage redundancy.

| Component | Recommended RAID |
|-----------|-----------------|
| OST storage | RAID 5 or RAID 6 |
| MDT storage | RAID 10 (metadata is critical) |

### Failover Configurations

**Active/Passive Pair:**
```
        Active                    Passive
    ┌───────────┐              ┌───────────┐
    │   Node A  │◄───Heartbeat──│   Node B  │
    │  (MDS/OSS)│              │  (Standby)│
    └───────────┘              └───────────┘
         │                           │
         └───── Failover ────────────┘
- One node active, one idle
- On failure, passive takes over
- Simple, 50% resource waste
```

**Active/Active Pair:**
```
    ┌───────────┐              ┌───────────┐
    │   Node A  │◄───Heartbeat──│   Node B  │
    │ (OSTs 1-4)│              │ (OSTs 5-8)│
    └───────────┘              └───────────┘
         │                           │
         └───── Both active ─────────┘
- Both nodes serve different OSTs
- On failure, one node takes over other's OSTs
- Better resource utilization
- More complex failover logic
```

## HARD DESIGN QUESTIONS

---

> [!question] You have a Lustre file system with 100 OSTs, each capable of 200 MB/s sequential bandwidth. A single client reads a 10 GB file striped across all 100 OSTs with stripe_size = 1 MB. What is the maximum theoretical read bandwidth? What if stripe_size = 100 MB? What real-world factors would reduce bandwidth in each case?
>
> **Maximum theoretical bandwidth:**
> - 100 OSTs × 200 MB/s = 20,000 MB/s (20 GB/s)
> - Perfect striping can saturate all OSTs in parallel
>
> **stripe_size = 1 MB:**
> - Each 1 MB chunk is read from a different OST
> - Client must issue 10,000 read requests (10 GB / 1 MB)
> - Overhead per request: network RTT + Lustre RPC (~50-100µs)
> - Overhead total: 10,000 × 75µs = 0.75 seconds
> - Data transfer: 10 GB / 20 GB/s = 0.5 seconds
> - Total: ~1.25 seconds (8 GB/s effective)
> - **Bottleneck: Request overhead, not bandwidth**
>
> **stripe_size = 100 MB:**
> - Each 100 MB chunk from one OST
> - Only 100 read requests (10 GB / 100 MB)
> - Overhead: 100 × 75µs = 7.5ms (negligible)
> - Data transfer: 0.5 seconds
> - Total: ~0.5 seconds (20 GB/s effective)
> - **Bottleneck: Network or client memory bandwidth**
>
> **Real-world factors:**
> - 1 MB stripe: Network RPC overhead dominates
> - 100 MB stripe: Alignment issues, some OSTs may be busy with other clients
> - Both: Network topology (not all OSTs equally distant), client CPU for data movement

> [!question] Your Lustre system has MDT on RAID 10 (4 disks) and OSTs on RAID 6 (8+2). A metadata-heavy workload creates 1 million 4KB files per hour. After 100 hours, performance degrades. What is the bottleneck? How does DNE help? Would GFS's single master design have this problem?
>
> **Bottleneck analysis:**
> - 100 hours × 1M files = 100M files
> - Each file: inode + filename + layout + permissions
> - Single MDT with RAID 10: ~4 disks, each ~200 IOPS = 800 metadata IOPS
> - 1M files/hour = 278 files/second
> - 278 IOPS < 800 IOPS → CPU/buffer cache may be bottleneck, not disk
> - Performance degradation: Directory size grows, linear scans slow down
>
> **DNE solution:**
> - Distribute directories across multiple MDTs
> - 4 MDTs × 800 IOPS = 3200 metadata IOPS
> - Can handle >1M files/hour
> - Each MDT's directory smaller → faster lookups
>
> **GFS comparison:**
> - GFS single master would have worse problem
> - Master in memory, but directory lookups still O(directory size)
> - GFS assumes full path lookups, not directory listings
> - GFS would need multiple masters (which it doesn't have)
> - **Conclusion:** DNE is necessary for POSIX directory semantics at scale

> [!question] A user runs `ls -l` on a directory with 10 million files in Lustre. Walk through the step-by-step operation from client to MDT to OSTs. How many RPCs? How does Lustre optimize this? What happens if the directory is striped across multiple MDTs (DNE)?
>
> **Step-by-step for single MDT:**
> ```
> 1. Client: readdir() system call
> 2. VFS: calls Lustre client
> 3. LMV: routes to appropriate MDC
> 4. MDC: sends MDS_READDIR RPC to MDT
> 5. MDT: reads directory entries from disk (ldiskfs)
> 6. MDT: returns first batch (default 1000 entries)
> 7. Client: for each entry, needs stat info (size, owner, etc.)
> 8. For each file: another RPC to MDT for getattr? (inefficient!)
> ```
>
> **Optimization:**
> - Lustre uses `readdir` + `getattr` in single compound request
> - MDT returns name AND attributes in one RPC
> - Attribute data from MDT only (size, owner, timestamps)
> - File data blocks NOT accessed (no OST involved)
>
> **Number of RPCs:**
> - Without optimization: 10M files → 10M RPCs (unacceptable)
> - With 1,000 entries per RPC: 10,000 RPCs
> - Each RPC: network round trip (~100µs) → 1 second total (acceptable)
>
> **With DNE (multiple MDTs):**
> - Directory striped across MDT0, MDT1, MDT2
> - Client sends parallel readdir to all MDTs
> - Client merges results (sorted by name)
> - RPC count same, but parallel → 3x faster
> - **Challenge:** Consistent snapshot across MDTs requires coordination

> [!question] Compare Lustre's striping with RAID 0 (Slide 17). Both distribute data across multiple disks. What are the key differences in failure handling, flexibility, and use cases?
>
> | Aspect | Lustre Striping | RAID 0 |
> |--------|----------------|--------|
> | **Level** | File system level | Block level (disk array) |
> | **Granularity** | File configurable (1MB default) | Fixed chunk size |
> | **Per-file control** | Yes (different files can have different stripe counts) | No (all files same) |
> | **Redundancy** | None at Lustre level (relies on OST RAID) | None at RAID level |
> | **Failure impact** | Lose one OST → lose data on that OST for ALL striped files | Lose one disk → lose ALL files |
> | **Recovery** | Re-replicate missing objects from other OSTs (if replication used) | Rebuild from parity (if RAID 5/6) |
> | **Scalability** | OSTs can be added online | Array size fixed |
> | **Use case** | HPC with many clients | Single server with local storage |
>
> **Why Lustre's approach wins for HPC:**
> - Different files have different access patterns (checkpoints vs logs)
> - Can increase stripe count for large files without reformatting
> - OST failure only affects subset of files (not entire file system)
> - But requires backup/replication for fault tolerance

> [!question] You have a Lustre system with 10 OSTs. A 100-process MPI job writes checkpoints every 10 minutes. Each process writes 10 MB (1 GB total). Currently using stripe_count=10, stripe_size=1MB. Performance is poor (50 MB/s). You change stripe_count=1. Performance improves (500 MB/s). Why did reducing striping improve performance? When would higher striping be better?
>
> **Analysis of current behavior (stripe_count=10):**
> - 100 processes write 1 GB total, striped across 10 OSTs
> - Each OST receives 100 MB (10 processes × 10 MB)
> - Problem: Write is 10 MB × 100 processes = 1 GB file created simultaneously
> - File system must allocate objects on 10 OSTs for EACH process write
> - Metadata: 100 processes × 10 OSTs = 1000 object creations (slow)
> - Network: 100 simultaneous connections to 10 OSTs (contention)
>
> **Why stripe_count=1 is faster:**
> - Each file uses only 1 OST
> - 100 processes × 1 OST = 100 object creations (10x fewer)
> - No cross-OST coordination
> - Each process writes sequentially to its own OST
> - Metadata server less loaded
>
> **When higher striping is better:**
> - Single client reading/writing a very large file (>10 GB)
> - Multiple clients reading the same large file (shared checkpoint)
> - Sequential I/O that can saturate multiple OSTs
> - Example: 1 client writing 100 GB file with stripe_count=10 → each OST writes 10 GB in parallel → 10x faster than stripe_count=1
>
> **Rule of thumb:**
> - Many small files: low stripe_count (1-4)
> - Few large files: high stripe_count (up to OST count)
> - Checkpoint files: depends on whether all processes write to same file or separate files

> [!question] Progressive File Layout (PFL) allows stripe_count to increase as file grows. A file starts with stripe_count=1, then at 1GB changes to stripe_count=8. What happens to the first 1GB of data? Is it moved to new OSTs? What are the implications for read performance of the entire file?
>
> **What happens:**
> - First 1GB stays on original OST (no data movement)
> - New writes beyond 1GB go to 8 OSTs (original + 7 new)
> - File layout metadata stored in MDT
> - Client reads first 1GB from 1 OST (slow), reads rest from 8 OSTs (fast)
>
> **Read performance implications:**
> ```
> File: 2GB total
> Region 0-1GB: 1 OST at 200 MB/s = 5 seconds
> Region 1-2GB: 8 OSTs at 200 MB/s each = 125 MB/s? Actually 8×200=1600 MB/s theoretical, but limited by client
> Total sequential read: ~5 seconds for first half + 0.625 seconds for second half = 5.625 seconds
> Average: 2GB / 5.625s = 355 MB/s
> ```
>
> **If file had stripe_count=8 from start:**
> - Both halves at 1600 MB/s → 1.25 seconds total
> - 4.5x faster for this file
>
> **Trade-off decision:**
> - PFL trades small-file efficiency for large-file performance
> - First 1GB (small file case) efficient (1 OST)
> - Beyond 1GB, not as fast as always-striped, but better than never-striped
> - **Optimal when:** Most files are small, but some grow large
> - **Not optimal when:** All files are large from the start

> [!question] In Lustre's active/active failover configuration, two OSS nodes share 8 OSTs (4 each). Node A fails. Describe the recovery process. How long does failover take? What happens to clients that were writing to Node A's OSTs?
>
> **Recovery process timeline:**
> ```
> Time 0: Node A fails (power loss, crash, network partition)
>    │
>    ▼ (0-5 seconds)
> Heartbeat timeout: Node B detects A not responding
>    │
>    ▼ (5-10 seconds)
> Node B: Acquires storage locks for OSTs 1-4 (formerly A's)
>    │
>    ▼ (10-15 seconds)
> Node B: Replays recovery logs for OSTs 1-4
>    │      - Any pending transactions from A?
>    │      - Client eviction for disconnected clients
>    │
>    ▼ (15-20 seconds)
> Node B: Exports OSTs 1-4 (now serving 8 total OSTs)
>    │
>    ▼
> Clients: Receive EAGAIN on old requests, reconnect to Node B
>    │
>    ▼
> Recovery complete: All 8 OSTs available via Node B
> ```
>
> **What happens to clients writing to failed OSTs:**
> 1. Write request times out (no response from Node A)
> 2. Client receives -EIO or -ENOTCONN
> 3. Client reconnects to MGS to get new OST mapping
> 4. MGS reports OSTs 1-4 now on Node B
> 5. Client re-issues writes to Node B
> 6. **Data in flight may be lost** (if not acknowledged by Node A)
>
> **Failover time:** Typically 20-60 seconds
> - Depends on heartbeat interval, recovery log size
> - Clients see pause in I/O during failover
> - Application must handle EIO/ENOTCONN and retry

> [!question] A Lustre client caches file data and locks. Compare this caching model to NFS (Slide 13) and GFS (Slide 14). What consistency guarantees does Lustre provide? What happens if another client modifies a file that the first client has cached?
>
> **Caching Comparison:**
>
> | Aspect | NFS | GFS | Lustre |
> |--------|-----|-----|--------|
> | **Data caching** | Yes (with close-to-open) | No | Yes (with lock revocation) |
> | **Cache coherence** | Attribute revalidation | N/A (no cache) | Lock-based |
> | **Write buffering** | Yes (delayed flush) | No | Yes (with lock) |
> | **Consistency model** | Close-to-open | Defined regions | POSIX (strict with locks) |
>
> **Lustre's lock-based coherence:**
> - Client acquires lock on file region before reading/writing
> - Locks are granted by MDT/OST
> - If another client wants to write, MDT revokes first client's lock
> - First client flushes dirty data and releases lock
>
> **Scenario:**
> ```
> Client A: open file, get read lock on [0-1MB], read data, cache it
> Client B: open same file for write
> Client B: request write lock on [0-1MB]
> MDT: sends lock revocation to Client A
> Client A: flushes any dirty data, releases lock, invalidates cache
> MDT: grants lock to Client B
> Client B: writes
> ```
>
> **What happens if Client A ignores revocation?**
> - MDT evicts Client A
> - Client A's future I/O fails
> - This is why Lustre requires reliable network and clients
>
> **vs GFS (no caching, no problem)** : GFS avoids this entirely
> **vs NFS (weaker)** : NFS allows stale caches (close-to-open is weaker)

> [!question] Connect Lustre's striping to LFS segment cleaning (Slide 11) and RAID small-write penalty (Slide 17). When a Lustre file with stripe_count=10, stripe_size=1MB receives a 4KB write, how many OSTs are involved? What is the write amplification? How does Lustre optimize small writes?
>
> **Small write on striped file:**
> - 4KB write to offset 2.5MB
> - Which OSTs? offset 2.5MB is in 3rd stripe (2-3MB range)
> - Only ONE OST involved (not all 10!)
> - Because stripe_size=1MB, small writes don't span multiple OSTs (unless crossing stripe boundary)
>
> **If offset spans stripe boundary (e.g., 2.999MB write of 4KB):**
> - Writes to OST2 (2-3MB region) AND OST3 (3-4MB region)
> - 2 OSTs involved for a 4KB write
> - Write amplification: 2x (same as RAID 1, less than RAID 5's 4x)
>
> **Lustre's optimization for small writes:**
> 1. Buffer small writes in client cache (write-back)
> 2. Combine multiple small writes into larger chunks
> 3. Align writes to stripe boundaries when possible
> 4. Use lockless I/O for non-overlapping regions
>
> **Comparison:**
> | System | Write amplification (4KB random write) |
> |--------|----------------------------------------|
> | RAID 5 | 4x (2 reads + 2 writes) |
> | LFS | 1x (new segment) + cleaning overhead |
> | Lustre (aligned) | 1x (1 OST) |
> | Lustre (misaligned) | 2x (2 OSTs) |

> [!question] You are designing a Lustre-based storage system for an AI training cluster. The workload: 1000 GPUs reading 1TB of training data (1000 files, 1GB each) repeatedly for 100 epochs. What striping configuration would you choose? Why? How would your answer change if the cluster had 1000 CPU nodes doing random 4KB reads from a single 10TB file (database workload)?
>
> **AI Training Workload (1000 GPUs, 1000×1GB files):**
> - Pattern: Sequential reads of entire files
> - Each GPU reads different files (or same files at different times)
> - Goal: Maximize aggregate bandwidth
>
> **Recommended configuration:**
> - stripe_count = OST_count (use all OSTs)
> - stripe_size = 1MB (or match GPU memory page size)
> - Each 1GB file striped across all OSTs
> - 1000 GPUs × (all OSTs) = maximum parallelism
>
> **Why:** Training reads entire files; striping gives highest bandwidth per file. GPUs can saturate network.
>
> **Database Workload (1000 CPUs, single 10TB file, random 4KB):**
> - Pattern: Random small reads throughout file
> - Goal: Minimize latency, maximize IOPS
>
> **Recommended configuration:**
> - stripe_count = 4 to 8 (not all OSTs)
> - stripe_size = 4KB (match access size)
> - Keep file on fewer OSTs to reduce network fan-out
>
> **Why:** High striping for random reads increases network overhead (each 4KB read may hit different OST). Better to keep file on fewer OSTs and let OST RAID handle parallelism.
>
> **Trade-off table:**
> | Workload | Stripe count | Stripe size | Rationale |
> |----------|-------------|-------------|-----------|
> | AI training (sequential) | Max | 1MB | Aggregate bandwidth |
> | Database (random) | Low (4-8) | 4KB | Reduce network RPCs |
> | Checkpoint (large files) | High | 4MB | Fast writes, infrequent |
> | Home directory (many small) | 1 | 1MB | Reduce metadata overhead |
