# 14 - Google File System (GFS)

## Core Design Problem (Recap)

Component failures are normal. Files are huge (GB-TB). Writes are mostly appends. High bandwidth > low latency. POSIX is too restrictive.

## Key GFS Features

- **Single master**: Stores metadata. Clients talk to chunkservers directly for data.
    
- **64MB chunks**: Reduces metadata size, reduces master interactions.
    
- **3-way replication**: Not RAID; across racks for availability.
    
- **Record append**: Atomic at-least-once semantics.
    
- **No data caching**: Working sets too large.
    
- **Shadow masters**: Read-only access during master recovery.
    

---

> [!question] GFS master stores all metadata in memory (file names → chunk handles → chunk locations). Why does GFS NOT persist chunk location metadata to disk? How does the master rebuild chunk locations after crash? What is the trade-off of this design?
> 
> - Chunk locations change constantly (chunkservers join/leave, disk failures, re-replication). Persisting would cause huge write traffic.
>     
> - Rebuild: Master polls all chunkservers at startup and via heartbeats.
>     
> - Trade-off: Recovery time proportional to number of chunkservers (minutes) not file system size. But master can't answer queries during rebuild. Simpler code, no sync overhead.
>     

> [!question] Compare GFS chunk replication (3-way, whole-file) with RAID 1 (mirroring, block-level). Under what failure scenarios does GFS provide higher availability than RAID 1? Under what scenarios is RAID 1 better? (Connect to slide 17)
> 
> - GFS: Replicas across racks → tolerates entire rack power loss. RAID 1: replicas on same array → tolerates disk failure but not enclosure failure.
>     
> - RAID 1 better for: Single-server crash (RAID 1 still works; GFS master needed for metadata). Lower latency (no network). Simpler consistency.
>     
> - GFS better for: Datacenter-wide failures, network partitions, rolling upgrades.
>     

> [!question] GFS does not cache file data at clients or chunkservers. NFS does cache aggressively. Why the difference? Under what workload would GFS benefit from caching? Under what workload would NFS's caching cause problems?
> 
> - GFS: Working sets are TB-PB, larger than client RAM. Caching would just churn. Applications (MapReduce) stream through data once anyway.
>     
> - GFS benefit: Repeated random reads to popular small files (rare in Google workloads).
>     
> - NFS problem: Stale caches cause consistency issues. Attribute revalidation adds overhead. Write buffering delays visibility.
>     

> [!question] Connect GFS's chunk lease mechanism to NFS's stateless design. GFS master grants a 60-second lease to one chunkserver (primary) for each chunk. Why can't GFS be fully stateless like NFS? What would break if the master didn't manage leases?
> 
> - Without leases: Multiple clients or chunkservers would write concurrently without ordering → replicas diverge irreconcilably.
>     
> - Leases give a single primary to serialize writes. Master revokes/extends leases.
>     
> - NFS gets away stateless because writes are idempotent (offset-based). GFS appends have no fixed offset → need primary to choose offset.
>     

> [!question] In your midsem Q3, you calculated HDD latency for journaling (T, R, D). If GFS runs on HDDs (original GFS did), how does the 64MB chunk size affect the T, R, D components compared to a 4KB block size? Why does GFS still achieve high sequential throughput despite using HDDs?
> 
> - 4KB: Seek (T) + rotation (R) dominate. Transfer (D) tiny.
>     
> - 64MB: Seek + rotation still paid once, then 64MB of sequential transfer at full bandwidth. Cost per byte is (T+R)/64MB, which is tiny.
>     
> - GFS achieves high throughput by amortizing T+R over huge chunks.


# GOOGLE FILE SYSTEM (GFS) - COMPLETE NOTES

Based on the SOSP 2003 paper and your course slides (14 - Google File System.pdf)

## 1. Core Philosophy: Why GFS Exists

### The Fundamental Observation
> Component failures are the **norm**, not the exception.

At Google scale (thousands of commodity machines):
- A disk fails every day
- Memory corrupts, connectors loosen, power supplies die
- Human errors, OS bugs, application bugs are constant

### Workload Characteristics That Drove Design

| Observation | Implication |
|-------------|-------------|
| Files are huge (100MB to multi-GB) | Metadata must scale, 64MB chunks |
| Two read types: large streaming + small random | Optimize both, but streaming is priority |
| Writes are mostly **appends**, not overwrites | Remove POSIX overwrite support entirely |
| Multiple clients append to same file | Need atomic record append semantics |
| High bandwidth > low latency | Amortize seek costs over large transfers |
| Working sets too large to cache | No client-side or chunkserver data caching |

---

## 2. Architecture Overview

### Component Hierarchy

```
┌─────────────────────────────────────────────────────────────┐
│                         Clients                              │
└────────────┬────────────────────────────────┬───────────────┘
             │                                │
             ▼ (metadata ops)                 ▼ (data ops)
┌────────────────────────┐        ┌──────────────────────────┐
│      SINGLE MASTER      │        │    CHUNKSERVERS (many)   │
│  - Stores all metadata  │◄──────►│  - Store 64MB chunks     │
│  - In memory            │        │  - As Linux files        │
│  - Manages leases       │        │  - 3-way replication     │
└────────────────────────┘        └──────────────────────────┘
```

### Key Design Decision
> **Master handles ONLY metadata. Data flows directly between clients and chunkservers.**

This avoids the master becoming a bottleneck.

---

## 3. The Master Node: Detailed Breakdown

### Three Types of Metadata Stored in Master Memory

| Metadata Type | Stored persistently? | How recovered after crash? |
|---------------|---------------------|---------------------------|
| **File and chunk namespaces** | Yes (operation log) | Replay operation log |
| **File-to-chunk mappings** | Yes (operation log) | Replay operation log |
| **Chunk replica locations** | **NO** | Poll chunkservers at startup + heartbeats |

### Why Chunk Locations Are NOT Persisted

| Pro | Con |
|-----|-----|
| No sync overhead as nodes join/leave | Recovery takes minutes (polling) |
| Simpler code (no distributed consensus) | Master can't answer during recovery |
| Works despite frequent failures | Shadow masters lag slightly |

### Master Memory Capacity
- Each chunk's metadata: **< 64 bytes**
- With 64MB chunks, metadata for 1PB of storage: ~1GB RAM
- **Memory is cheap** → entire metadata fits in RAM

### Checkpointing for Fast Recovery
- Master periodically checkpoints operation log (B-tree format)
- Checkpoint can be directly mapped into memory
- Created without delaying incoming requests
- ~1 minute for a cluster with millions of files

### Shadow Masters (Read-Only Availability)
- Replica of operation log (not active master)
- Lag primary master by fractions of a second
- Provide **read-only access** even when primary master is down
- Not mirrors; they don't process writes

---

## 4. Chunks and Chunkservers

### Chunk Properties

| Property | Value |
|----------|-------|
| Size | **64 MB** (key design parameter) |
| Handle | 64-bit globally unique ID |
| Replication | Default 3-way, configurable |
| Storage | As ordinary Linux files on chunkserver |
| Replica placement | Across racks for availability |

### Why 64MB? (Trade-off Analysis)

| Advantage | Disadvantage |
|-----------|--------------|
| Fewer chunks → less metadata → fits in RAM | Internal fragmentation (small files waste space) |
| Client interacts less with master | Small files become hotspots |
| Keep persistent TCP connection to chunkserver | Lazy space allocation mitigates waste |
| Amortize network overhead | Increase replication factor for hot files |

---

## 5. Read Path: Step-by-Step

### How a Client Reads a File

```
Client application calls read()
         │
         ▼
┌─────────────────────────────────────────┐
│ Client: translates filename + offset    │
│         to chunk index                  │
└─────────────────────────────────────────┘
         │
         ▼ (Request to master)
┌─────────────────────────────────────────┐
│ Master: replies with chunk handle +     │
│         locations of all replicas       │
└─────────────────────────────────────────┘
         │
         ▼ (Client caches this info)
┌─────────────────────────────────────────┐
│ Client: sends request to closest        │
│         replica (chunk handle + range)  │
└─────────────────────────────────────────┘
         │
         ▼
┌─────────────────────────────────────────┐
│ Chunkserver: returns data               │
└─────────────────────────────────────────┘
```

### Optimization
> Master may provide **additional chunk locations** (prefetch) to reduce future round trips.

### No Caching of File Data
> "Working sets are usually too large to be cached"

Neither clients nor chunkservers cache file data. Only metadata (chunk locations) is cached at clients, and it's **invalidated by master** when leases expire.

---

## 6. Write Path: The Lease Mechanism

### Why Leases Instead of Locks?

| Traditional Locks | GFS Leases |
|------------------|------------|
| Require distributed lock manager | Master grants lease to one chunkserver |
| Heavyweight, slow | Lightweight, piggybacked on heartbeats |
| Deadlock detection needed | Lease expires automatically (60s) |
| Revocation complex | Master can revoke (e.g., on rename) |

### Lease Properties
- **Timeout**: 60 seconds
- **Extension**: Indefinite, piggybacked on heartbeat messages
- **Primary chunkserver**: The one holding the lease decides write order
- **Revocation**: Master can revoke (e.g., when rename operation occurs)

---

## 7. Write Path: Step-by-Step (Control + Data Flow Decoupled)

### Phase 1: Control Flow (Establish Order)

```
1. Client asks master for:
      - All replica locations
      - Identity of primary (lease holder)

2. Master replies. Client caches this info.

3. Client pre-pushes data to ALL replicas (in any order)
      (Data flow separate from control flow)
```

### Phase 2: Data Flow (Chain Replication)

Data is **pipelined** for efficiency:
- Client pushes data to **closest** chunkserver
- That chunkserver forwards as soon as it receives (doesn't wait for full block)
- Next closest forwards further
- Maximizes network bandwidth utilization

### Phase 3: Write Execution

```
4. After all replicas acknowledge data receipt,
   client sends WRITE request to PRIMARY only

5. Primary assigns sequential offsets to all mutations
   (even from concurrent clients)

6. Primary forwards write request to ALL secondaries

7. Secondaries execute write and signal completion to primary

8. Primary replies to client
```

### On Failure
- Client retries the whole sequence
- Different replicas may end up with different sequences of bits
- On success: data written at **same offset** everywhere

---

## 8. Record Append (The Unique GFS Feature)

### The Problem
Multiple clients want to append to the same file concurrently. POSIX requires locks, which don't scale.

### The GFS Solution: Record Append

```
Client pushes data to all replicas.
        │
        ▼
Client sends request to primary.
        │
        ▼
If record does NOT fit in current chunk:
        Primary PADS the current chunk
        Tells client to RETRY with new chunk
        │
        ▼
If record fits:
        Primary writes data at its chosen offset
        Tells replicas to do the same
        │
        ▼
If any replica fails → client retries
```

### Semantics
- **At least once** (not exactly once)
- May have **duplicates** (if retry after partial success)
- May have **padding gaps** (when switching chunks)
- Applications must handle duplicates (e.g., by including unique IDs)

### Comparison: NFS Append vs GFS Record Append

| NFS Append | GFS Record Append |
|------------|-------------------|
| Requires locks | No locks |
| POSIX-compliant | Not POSIX |
| Exactly once (with locks) | At least once |
| Slow under contention | Fast, highly concurrent |
| Application writes at fixed offset | Primary chooses offset |

---

## 9. Snapshot (Copy-on-Write)

### Use Case
- Create copies of large data sets
- Save state before applying tentative updates

### Implementation Steps

```
1. Master revokes outstanding leases on chunks to be snapshotted

2. Master logs operation to disk (durability)

3. Master duplicates metadata (NOT data blocks)
      New snapshot points to same chunks as original

4. When client writes to snapshot:
      Master allocates NEW chunk handle
      Copy created on same chunkserver as old one (bandwidth optimization)
```

### Copy-on-Write in Action
- Snapshots are **instantaneous** (metadata only)
- First write to snapshot triggers actual copy
- Bandwidth saved by copying within same chunkserver

---

## 10. Namespace Management

### No Directories, No Inodes
- GFS has **no directories** as first-class objects
- No hard links, no symbolic links
- Namespace is a **lookup table** (full path → metadata)

### Implementation
- Logically: `Map<full_path, metadata>`
- With **prefix compression** for efficiency
- Entire namespace fits in master memory

### Locking in Namespace
- Each path has a **read-write lock**
- To access `/d1/d2/leaf`:
  - Acquire read lock on `/d1`
  - Acquire read lock on `/d1/d2`
  - Acquire write lock on `/d1/d2/leaf`
- **Totally ordered** locking to prevent deadlocks

---

## 11. Replica Management

### Creation Policy
- Prefer **underutilized** chunkservers
- Limit number of new chunks per chunkserver (why? → prevents write hotspot on one server)
- Spread replicas across racks (for rack-level fault tolerance)

### Re-replication
- When replica count falls below target
- Prioritize chunks with **lowest replication factor**
- Highest priority: chunks with 0 valid replicas

### Rebalancing
- Periodically move replicas from high-utilization to low-utilization servers
- Also balances disk space and I/O load

---

## 12. Garbage Collection (Lazy Deletion)

### Traditional Approach Problems
- Explicit deletion is hard to implement reliably
- Messages can be lost, masters can fail

### GFS's Lazy Approach

```
File deleted by user:
        │
        ▼
File is "hidden" (rename to hidden name)
        │
        ▼
Hidden file stays for 3 days
        │
        ▼
After 3 days, master removes in-memory metadata
        │
        ▼
Regular scan detects orphaned chunks
        │
        ▼
Orphaned chunks are deleted
```

### Stale Replica Detection (Version Numbers)

```
Every time master grants a lease:
        Chunk version number INCREASES
        Version logged by master AND replicas

When chunkserver recovers:
        Reports its version to master
        Master compares with its own version
        If version is older → replica is STALE
        Stale replicas never served to clients
```

---

## 13. Fault Tolerance Mechanisms Summary

| Component Fails | Recovery Mechanism |
|----------------|-------------------|
| **Chunkserver down** | Re-replicate chunks from other replicas |
| **Stale replica** | Version number mismatch; never served |
| **Master down** | Shadow master (read-only) + operation log replay |
| **Corrupt operation log** | Checkpoint + log replicas |
| **Network partition** | Leases expire, client retries elsewhere |
| **Data corruption** | Checksums, fallback to other replicas |

## DESIGN QUESTIONS & SCENARIOS

---

> [!question] What happens if the master crashes **after** sending chunk locations to a client but **before** updating its operation log for a file creation? The client has a chunk handle that doesn't exist in the recovered master's log. How does the client discover this, and what happens to the data?
> - Client's chunk handle points to a chunk ID that master doesn't recognize.
> - On next read/write, client asks master for chunk location. Master replies "chunk not found".
> - Client retries file creation from scratch.
> - Data already written to chunkservers becomes orphaned.
> - Periodic master scan (garbage collection) will delete orphan chunks after 3 days.

> [!question] The master maintains chunk locations in memory and rebuilds from chunkservers on startup. What happens if a chunkserver's disk fails **during** master startup polling? The chunkserver reports its chunks, but some are now unreadable. How does master know a chunk is lost versus the chunkserver just not reporting it yet?
> - Master compares reported chunks against expected replicas from operation log.
> - Missing chunk from one chunkserver with other replicas alive → trigger re-replication.
> - Chunkserver reports bad disk → master marks that replica as dead.
> - Master doesn't trust absence until heartbeat timeout. Only after 60 seconds of no heartbeat does it declare chunkserver dead.

> [!question] Record append guarantees "at least once" semantics. Walk through a scenario where a client gets a **duplicate** record. Then walk through a scenario where a client gets **no record** (lost). Which is more common, and why?
> - **Duplicate scenario**: Client pushes data to all replicas (success). Sends write request to primary. Primary writes, tells secondaries. One secondary fails. Primary replies success to client (since at least primary + one secondary succeeded). Client thinks done. But failed secondary never wrote. Client retries after timeout → same record written again to all replicas. Now duplicate exists.
> - **Lost scenario**: Client pushes data to all replicas. One replica fails before acknowledging. Client aborts and retries entire operation. If all retries fail, record lost.
> - Duplicates more common because partial success triggers retries.

> [!question] Suppose the master grants a 60-second lease to primary chunkserver P1 for chunk C. P1 fails after 30 seconds but doesn't crash; it just stops responding. A client sends a write request to P1. Will the master know P1 is dead? How does the write proceed?
> - Master doesn't know. No heartbeat from P1 after ~60 seconds → master declares it dead.
> - But the 60-second lease is still active for another 30 seconds from P1's perspective.
> - Client's write to P1 will timeout. Client asks master for new lease holder.
> - Master sees P1 not heartbeating → grants lease to P2.
> - Client retries write with P2 as primary.
> - Potential issue: P1 may come back before lease expires and still think it's primary → split brain.
> - Solution: P1's lease extension requires heartbeat. No heartbeat → lease expires on P1's side too after 60s.

> [!question] A client writes 100MB of data to a file. The file is striped across 10 chunks (each 64MB, so two full chunks + partially third). The client fails after writing only the first two chunks. Another client reads the file. What does it see? Is the file in a consistent state?
> - File size in master metadata is still the old size (no commit for third chunk).
> - Second client reads only first two chunks. Third chunk not yet referenced in file's chunk list.
> - Data in third chunk exists on chunkservers but is ORPHANED.
> - No inconsistency; third chunk will be garbage collected after 3 days.
> - This is GFS's "visible only after commit" approach.

> [!question] GFS has no data caching at clients. But chunk location caching is allowed. If a client's cached chunk location is stale (chunkserver holding that replica has died), what happens when the client tries to read? Does it ask master again? Does master know the chunkserver died?
> - Client sends read request to stale chunkserver → connection fails/timeout.
> - Client evicts that location from cache.
> - Client asks master for updated replica locations.
> - Master may not yet know chunkserver died (heartbeat hasn't timed out).
> - Master returns all replicas, including dead one. Client tries next replica.
> - On next heartbeat timeout, master removes dead chunkserver from replica maps.

> [!question] Multiple clients simultaneously append to the same file using record append. Client A's record doesn't fit in current chunk. Primary pads the chunk and tells A to retry with new chunk. Meanwhile, Client B's record fits in the same chunk's remaining space. Does B's record get written before A's retry? Who decides ordering?
> - Primary decides order of all mutations, per the lease.
> - Primary buffers all incoming append requests.
> - Primary may process B's request (which fits) before sending A's retry.
> - Order: A arrives first but requires new chunk. Primary says "retry". B arrives, fits, writes. A retries, writes to new chunk.
> - Result: B's record appears before A's record in the file, even though A started first.

> [!question] Compare GFS's lazy deletion (3-day hidden files) with a traditional file system's unlink(). A user accidentally deletes a 1TB file. In traditional FS, recovery requires immediate stop and fsck. In GFS, what are the options? What's the trade-off?
> - GFS: File is hidden but still exists for 3 days. Admin can "unhide" by renaming back.
> - No immediate data loss. No need to stop system.
> - Trade-off: Storage space not reclaimed for 3 days. If disk is full, this is problematic.
> - Solution: Admin can manually trigger early garbage collection.

> [!question] The master uses prefix compression for the namespace lookup table. A path `/home/user/data/file.txt` and `/home/user/data/file2.txt` share prefix `/home/user/data/`. How many bytes are saved? What happens to compression efficiency if paths are completely random UUIDs?
> - First path: stores full string. Second path: stores only "file2.txt" + pointer to previous node's prefix.
> - Savings: length of shared prefix bytes per file.
> - Random UUIDs (like GUIDs) have no common prefixes → compression yields near-zero savings.
> - GFS relies on hierarchical naming (directories) for compression efficiency.

> [!question] What happens if the operation log (only persistent metadata) becomes corrupt on all replicas? Master can't replay. Shadow masters also corrupted. Is all data lost?
> - Chunk data is still on chunkservers (but no mapping from filenames to chunks).
> - Data is recoverable but requires forensic scan of all chunkservers.
> - Chunks have chunk handles but not filenames. Directory structure lost.
> - Would need to rebuild namespace by scanning all chunks and guessing file boundaries.
> - Extremely painful, but not total data loss. Google had procedures for this (rare).

> [!question] GFS doesn't support random overwrites. But what if an application does a small overwrite (4KB) to a 64MB chunk? Walk through what happens at the chunkserver level, including any FTL/disk behavior. Why is this slow?
> - GFS doesn't prevent overwrites; it just doesn't optimize them.
> - Chunkserver must read entire 64MB chunk (or at least the 4KB region) into memory.
> - Modify 4KB. Write back entire 64MB chunk (LFS/SSD may write new location, HDD overwrites same location).
> - On HDD: 64MB write = ~0.64 seconds at 100MB/s, plus seek+rotate.
> - On SSD: Write amplification (WAF = 64MB/4KB = 16,000x worst case! Actually mitigated by FTL).
> - This is why Google workloads avoid overwrites entirely.

> [!question] The master is a single point of failure (SPOF). Shadow masters provide read-only access during master recovery. What operations are impossible during master failover? How long does write unavailability last?
> - Impossible: Any metadata mutation (file creation, deletion, rename, chunk allocation).
> - Also impossible: Opening new files (requires master to get chunk handles).
> - But reads to already-open files continue (clients have cached chunk locations).
> - Write unavailability: Time to promote shadow master to primary + replay pending logs. Typically seconds to minutes.
> - Google's design decision: Brief write unavailability acceptable given master's simplicity.

## COMPLETE PATH TRACE: Reading a File

### Scenario
Client wants to read `/user/arnab/research/gfs.pdf`, size 200MB, chunk size 64MB → chunks: 0, 1, 2 (partially), 3 (partially? 200MB = 3 full chunks + 8MB fourth chunk)

### Step-by-Step

| Step | Who | Action | Network RTTs | Disk I/Os |
|------|-----|--------|--------------|-----------|
| 0 | Client | Application calls `open("/user/arnab/research/gfs.pdf")` | - | - |
| 1 | Client | Parses path, needs root inode | - | - |
| 2 | Client | Sends lookup request to master: `/user` | 1 RTT | - |
| 3 | Master | Looks up in namespace table: `/user` → inode/user file handle | - | - |
| 4 | Master | Returns file handle for `/user` | 1 RTT | - |
| 5 | Client | Sends lookup: `/user/arnab` | 1 RTT | - |
| 6 | Master | Returns handle for `/user/arnab` | 1 RTT | - |
| 7 | Client | Sends lookup: `/user/arnab/research` | 1 RTT | - |
| 8 | Master | Returns handle for `/user/arnab/research` | 1 RTT | - |
| 9 | Client | Sends lookup: `gfs.pdf` | 1 RTT | - |
| 10 | Master | Returns: inode for file, list of chunk handles [ch0, ch1, ch2, ch3] | 1 RTT | - |
| 11 | Client | For each chunk, asks master: locations of replicas | 4 RTTs (or batched) | - |
| 12 | Master | Returns for each chunk: list of 3 chunkservers | 4 RTTs | - |
| 13 | Client | Caches: chunk handle → [server1, server2, server3] | - | - |
| 14 | Client | For chunk 0: sends read request to closest chunkserver | - | - |
| 15 | Chunkserver | Reads chunk 0 from local disk (as Linux file) | - | 1 read I/O |
| 16 | Chunkserver | Returns 64MB data | Network transfer | - |
| 17-20 | Client | Repeats for chunks 1, 2, 3 | - | 3 more read I/Os |
| 21 | Client | Buffers all data, returns to application | - | - |
| Close | Client | close() → sends no RPC (master doesn't track open files) | - | - |

### Total Cost for First Read (Cold Cache)
- **Metadata RPCs**: 10 round trips (lookups + chunk locations)
- **Data RPCs**: 4 reads
- **Disk I/Os**: 4 (one per chunk)
- **Total RTTs**: ~14 (with batching optimizations, master can send chunk locations in same response as lookup)

### Second Read of Same File (Cached Chunk Locations)
- **Metadata RPCs**: 0 (client cached chunk handle → server mapping)
- **Data RPCs**: 4 reads
- **Disk I/Os**: 4 (unless chunkserver has its own cache, but GFS doesn't do that intentionally)
- **Total RTTs**: 4

## COMPLETE PATH TRACE: Appending with Record Append

### Scenario
100 clients concurrently appending to the same shared log file `/shared/log.txt`

### Step-by-Step for One Client (Client A)

| Step | Who | Action |
|------|-----|--------|
| 1 | Client A | Pushes 4KB record data to ALL 3 replicas (pipelined chain replication) |
| 2 | Replicas | Each acknowledges receipt of data (not written yet) |
| 3 | Client A | Sends write request to PRIMARY (only primary gets this) |
| 4 | Primary | Checks if 4KB fits in current chunk (offset 64MB - 2KB remaining? No) |
| 5 | Primary | PADS current chunk to 64MB boundary (writes zeros) |
| 6 | Primary | Tells Client A: "RETRY with new chunk" |
| 7 | Client A | Repeats from step 1 with new chunk handle obtained from master |
| 8 | Client A | Pushes data to replicas (again) |
| 9 | Primary | Now record fits. Primary assigns offset = next available |
| 10 | Primary | Writes data at that offset |
| 11 | Primary | Forwards write to all secondaries |
| 12 | Secondaries | Execute write at SAME offset |
| 13 | Secondaries | Signal completion to primary |
| 14 | Primary | Replies SUCCESS to Client A |

### Concurrent Clients

| Time | Primary Action |
|------|----------------|
| t=0 | Receives A's request (needs new chunk). Queues it. |
| t=1 | Receives B's request (fits in current chunk). Processes B immediately. |
| t=2 | Receives C's request (fits). Processes C. |
| t=3 | Receives D's request (fits). Processes D. |
| t=4 | Current chunk now full (pad to 64MB). |
| t=5 | Processes A's retry → new chunk, writes to offset 0 of new chunk. |

### Order in File
B, C, D, (padding zeros from previous chunk), A

| **Consistency** | Defined (before crash) + undefined (after failure) |
| **Writes** | Append-only (no POSIX overwrites) |
| **Concurrent appends** | Record append (at least once) |
| **Caching** | No data caching |
| **Deletion** | Lazy (3-day hide) |
| **Snapshot** | Copy-on-write |
| **Namespace** | Lookup table (no directories) |
| **Lease** | 60 seconds, primary determines order |

## MODEL ANSWER

### (a) Why Leases? What Problem Do They Solve?

**Problem that stateless retry cannot solve: ordering of concurrent appends.**

In NFSv3, writes specify an offset. If two clients write to same file, they must coordinate offsets externally. GFS supports **record append** where the file system chooses the offset. Without a primary to choose offsets, appends from different clients could interleave or corrupt data.

**What leases provide:**

| Problem | How Leases Solve It |
|---------|---------------------|
| Multiple clients appending | Primary assigns sequential offsets |
| No distributed lock manager | Lease grants temporary authority to one chunkserver |
| Server failures | Lease expires automatically (60s), master grants to another |
| Need for ordering | All mutations go through primary; primary decides order |

**Why not use NFSv3 style (client-specified offset):**
- GFS workloads are append-heavy, not overwrite-heavy
- Clients don't know the current end of file
- Having clients coordinate offsets would require locks (worse than leases)

**Why not use distributed locks:**
- Locks require a lock manager (another centralized service)
- Locks have deadlock detection overhead
- Leases are simpler: "you are primary until time expires"

### (b) Complete Lease Lifecycle

**Step 1: Lease Grant (Primary Election)**

```
Client wants to write to chunk C.
        │
        ▼
Client asks master: "Who is primary for chunk C?"
        │
        ▼
Master checks in-memory table:
        │
        ├── If lease exists and valid → return primary P to client
        │
        └── If no lease or lease expired:
                │
                ▼
                Master selects primary from 3 replicas
                (chooses least loaded chunkserver)
                │
                ▼
                Master increments version number for chunk C
                (persisted in operation log)
                │
                ▼
                Master sends lease grant message to chosen P
                (piggybacked on heartbeat)
                │
                ▼
                Master records: (chunk C, primary=P, expiry=now+60s)
                │
                ▼
                Master returns P to client
```

**Step 2: Lease Operation**

```
Primary P receives lease grant.
        │
        ▼
P records: "I am primary for chunk C until time T"
        │
        ▼
P serves all write requests for chunk C.
        │
        ▼
Every few seconds, P sends heartbeat to master.
        │
        ▼
Master piggybacks lease extension on heartbeat response.
        │
        ▼
P extends lease expiry by 60 seconds from current time.
```

**Step 3: Lease Expiration**

```
Primary P stops receiving heartbeats (network partition or crash).
        │
        ▼
Master waits 60 seconds without heartbeat.
        │
        ▼
Master marks P as dead in its in-memory table.
        │
        ▼
Master grants lease to another chunkserver Q for chunk C.
        │
        ▼
Master increments version number again.
        │
        ▼
P's lease expires naturally at time T (no renewal).
```

**Visual Timeline:**

```
Time ──────────────────────────────────────────────────────────►

t=0      Master grants lease to P (expiry t=60)
         │
t=10     P sends heartbeat → master extends lease (expiry t=70)
         │
t=20     P sends heartbeat → master extends lease (expiry t=80)
         │
t=30     P crashes
         │
t=40     Master misses heartbeat
         │
t=50     Master misses heartbeat
         │
t=60     Master misses heartbeat, declares P dead
         │
t=60     Master grants lease to Q (expiry t=120)
         │
t=70     P's original lease would have expired anyway
```

### (c) Concurrent Appends Through Primary

**Scenario:** Two clients, X and Y, simultaneously append to same chunk C. Primary P holds lease.

**Step-by-step:**

```
Client X: pre-pushes data to all 3 replicas
Client Y: pre-pushes data to all 3 replicas

(Data now at all chunkservers but not yet written)

Client X: sends write request to primary P
Client Y: sends write request to primary P

Primary P receives both requests (order determined by arrival)
        │
        ▼
P checks: Does X's record fit in current chunk?
        │
        ├── If YES: P assigns offset = current_offset
        │          P advances current_offset by record size
        │          P writes X's data at that offset
        │
        └── If NO: P pads current chunk, tells X to retry with new chunk

P does same for Y's request (in arrival order)

Primary P forwards both writes to all secondaries
        │
        ▼
Secondaries execute writes at same offsets
        │
        ▼
Secondaries acknowledge to primary
        │
        ▼
Primary acknowledges to clients
```

**If primary crashes during this process:**

| Crash Point | What Happens | Client Sees |
|-------------|--------------|-------------|
| Before assigning offsets | No writes committed. Clients timeout. Master grants lease to new primary. Clients retry. | Retry success (eventually) |
| After assigning offsets, before forwarding to secondaries | Only primary has written. Replicas inconsistent. | Clients timeout. Retry may cause duplicates |
| After forwarding, before all secondaries ack | Some replicas have data, some don't. | Primary may ack partial success. Client retries → duplicate |
| After ack to clients | All replicas have data. Crash is fine. | Success |

**GFS semantics:** "At least once" for record append. Duplicates possible on retry.

### (d) Split-Brain Scenario with Clock Skew

**Setup:**
- Master clock: correct
- P's clock: 10 seconds ahead
- Lease granted at master time t=0, expiry t=60
- P believes expiry at its local time t=70 (but master thinks t=60)

**Timeline:**

```
Master time:    0    10    20    30    40    50    55    60    65
P's local time: 10    20    30    40    50    60    65    70    75
                │     │     │     │     │     │     │     │     │
P crashes at P-local time 65 (master thinks 55)
                │
Master detects P dead at master time 65
                │
Master grants lease to Q at master time 65
                │
P's lease would expire at P-local time 70 (master time 60)
```

**Is there split-brain?**

P crashed at master time 55. It cannot serve requests after crashing. There is **no split-brain** because P is dead.

**If P was not dead but just partitioned:**

Scenario: Network partition prevents master from reaching P, but P can still reach clients.

```
Master time: P cannot send heartbeats.
        │
Master waits 60 seconds, declares P dead.
        │
Master grants lease to Q.
        │
But P still thinks it is primary (lease not expired on P's side if its clock is ahead).
        │
NOW: Two primaries for same chunk! (Split-brain)
```

**How GFS prevents this:**

| Mechanism | How it works |
|-----------|--------------|
| **Lease expiry on P** | P cannot extend lease without heartbeat. After 60 seconds of no heartbeat from master, P's lease expires locally. |
| **Version numbers** | Master increments version when granting new lease. P has old version. Client requests include version. |
| **Client validation** | Client caches (chunk, version, primary). If client sends request to P with old version, P rejects. |

**In the partitioned scenario:**
- P stops receiving heartbeats from master
- After 60 seconds, P's local lease expires
- Even if P's clock is ahead, it still times out after 60 seconds of no heartbeat
- Maximum split-brain window = clock skew (10 seconds) + heartbeat timeout

### (e) GFS Leases vs NFSv4 Leases

| Aspect | GFS Leases | NFSv4 Leases |
|--------|------------|--------------|
| **What is leased** | Chunk (64MB unit) | File byte ranges |
| **Lease holder** | Chunkserver (primary) | Client |
| **Purpose** | Determine write order for appends | Cache coherence, file locking |
| **Lease duration** | 60 seconds (extendable) | Configurable (typically 30-60s) |
| **State on server** | Master stores lease info | Server stores lease info (stateful!) |
| **Recovery on crash** | Master grants to new primary | Client must reacquire leases |
| **What NFS gains** | Stronger cache consistency, byte-range locking | NFSv3 had no leases; v4 added them |
| **What GFS loses** | Simplicity of stateless protocol | Must manage lease state, handle expiry, version numbers |

**What NFS gains by adding leases (NFSv4 vs NFSv3):**

| NFSv3 Problem | How NFSv4 Leases Help |
|---------------|----------------------|
| Stale client caches | Leases allow server to recall cached data |
| No byte-range locks | Leases enable lock management |
| Client crash leaves state | Leases expire automatically |
| No delegation | Server can delegate authority to client |

**What GFS loses by using leases instead of being stateless:**

| Loss | Explanation |
|------|-------------|
| **Complexity** | Master must track lease state, version numbers, heartbeats |
| **Failover time** | 60 seconds of write unavailability during master failover |
| **Split-brain risk** | Must carefully handle clock skew and network partitions |
| **State on master** | Lease table in memory (but small: <64 bytes per chunk) |

**Why GFS accepts these losses:** The benefit of ordered appends outweighs the complexity. Google's workloads are append-heavy, not read-heavy.

### (f) Network Partition with Version Numbers

**Scenario:**

```
Initial state:
    Chunk C, version = 5
    Primary = A, Secondaries = B, C

Network partition:
    A can talk to clients and master
    Master cannot talk to A (heartbeats lost)
    B and C can talk to master, but not to A
```

**Timeline:**

```
t=0:  Partition occurs. Master stops receiving heartbeats from A.
t=0:  A still thinks it is primary.

t=60: Master declares A dead. Master increments version to 6.
      Master grants lease to B as new primary.

t=60: B becomes primary for chunk C (version 6).
      B and C are still partitioned from A.

t=65: Client X sends write request to A (old primary).
      A still thinks it is primary (version 5).

t=65: Client Y sends write request to B (new primary, version 6).

NOW: Two primaries for same chunk! Inconsistency possible.
```

**How version numbers prevent inconsistency:**

```
Client X sends write to A:
    Request includes chunk handle and version number
    A checks: My version = 5, client's version = 5 → matches
    A writes data (but B and C cannot be reached because of partition)
    A's write only applies to itself (not to B, C)

Client Y sends write to B:
    Request includes version = 6
    B checks: My version = 6, client's version = 6 → matches
    B writes to itself and C (both in same partition)

Later, partition heals:
    A reconnects to master
    Master sees A's version = 5 (stale!)
    Master never serves A's replica to clients
    A's stale data is garbage-collected
```

**What prevents A from accepting writes with stale version?**

Nothing during the partition! A will accept writes. But those writes:
- Only go to A (not to B or C)
- Are lost when partition heals (A's replica marked stale)
- Clients may have received ACK but data disappears

**GFS semantics:** GFS accepts this as "undefined region." Applications that require consistency must use record append (at least once) or handle retries.

**Role of version numbers:**

| Phase | Version Number Role |
|-------|---------------------|
| Lease grant | Master increments version, sends to new primary |
| Client request | Client includes version from master |
| Primary validation | Primary rejects requests with wrong version |
| Stale detection | Master compares versions during heartbeat |
| Garbage collection | Stale replicas (wrong version) are deleted |

### (g) Optimization: Reducing Failover Time

**Goal:** Reduce worst-case failover from 60 seconds to 5 seconds without increasing heartbeat traffic.

**Heartbeat traffic constraint:** Currently, each chunkserver sends heartbeat every ~1 second. Increasing frequency would increase network and CPU overhead.

**Proposed optimization: Speculative lease handoff**

Idea: Master maintains a **backup primary** for each chunk. The backup primary is kept ready to take over.

**How it works:**

```
Normal operation:
    Primary P holds lease for chunk C (expiry 60s)
    Backup B is notified by master: "You are backup for C"
    B does NOT serve writes, but has latest data from replicas

Failure detection:
    Master misses 2 heartbeats from P (2 seconds, not 60)
    Master immediately promotes B to primary
    Master increments version number
    Total failover time: ~3-5 seconds
```

**Heartbeat traffic impact:**

| Approach | Heartbeats per chunkserver | Total cluster heartbeats (1000 chunkservers) |
|----------|---------------------------|---------------------------------------------|
| Original | 1 per second | 1000 per second |
| Speculative | 1 per second + extra for backup info | ~1100 per second (10% increase) |

**Trade-offs:**

| Pro | Con |
|-----|-----|
| Failover time: 60s → 5s | Master must track backup for every chunk (2x metadata) |
| Clients experience less write blocking | Backup must be kept consistent (more replica synchronization) |
| No increase in primary's work | More complex failover logic (promote backup, not just any chunkserver) |

**Alternative optimization: Lease shortening during idle**

If chunk C has not been written to recently, master grants shorter leases (e.g., 10 seconds). When writes start, master extends lease to 60 seconds.

**Trade-off of lease shortening:**

| Pro | Con |
|-----|-----|
| Cold chunks fail over faster (10s vs 60s) | More frequent lease grants for hot chunks (overhead) |
| Reduces split-brain window | Master does more work for active chunks |

**Which is better for Google workloads?**
- Google's workloads: Many chunks are written to frequently (hot)
- Lease shortening doesn't help hot chunks
- Speculative handoff helps both hot and cold
- Google chose simplicity: fixed 60-second leases were acceptable
