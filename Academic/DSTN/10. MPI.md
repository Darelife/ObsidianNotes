# Message Passing Interface

Basically for parallel programming, for inter process communication. (often for distributed systems)

MPI processes have unique ranks, to identify themselves, and based on those ranks, the task for each process is defined. (usually in MPI_COMM_WORLD, 0 based indexing)

`mpirun -np 4 ./a.out`
This will spawn 4 processes, running `./a.out`
Then based on the rank logic, they will all differ, but the code running will be the same.

# Communicators

`MPI_COMM_WORLD` is the default communicator. Has all the processes, and ranks

Anyone can then make their own subsets.
Only members of the group can communicate using that group.

In MPI_COMM_WORLD
Rank 0 = P0
Rank 1 = P1
Rank 2 = P2
Rank 3 = P3

In COMM_A, (Only has P0 and P1),
Rank 0 = P0
Rank 1 = P1

In COMM_B, (Only has P2 and P3),
Rank 0 = P2
Rank 1 = P3

P2: `MPI_Send(..., dest=1, COMM_B);`
(P2 sends to P3)

# MPI Calls

We can do point to point communication. (as shown above..`MPI_Send(..., dest = 1, COMM_B)`, and `MPI_Recv`)

We can also do collective communication.
`MPI_Bcast`: One to All
`MPI_Reduce`: All to one (every process in the group must call it. If any one fails to call it, the program will hang. All the processes will send it to a root process, and then, MPI will combine them using SUM, MAX, XOR, etc.)
`MPI_Barrier` : Sync. (All the processes must call it, and it will basically block the processes that have reached it, until all of them call it)

Blocking Calls: 
1. MPI_Send (Blocks till MPI has copied the data out of the buffer) (Non blocking: MPI_Isend)
   `MPI_Send(buf, count, type, dest, tag, comm);`
2. MPI_Ssend (Blocks till the receiver actually starts receiving)
3. MPI_Bsend (Blocks till the data is copied into a user provided buffer)
4. MPI_Rsend (Assumes that the receiver is already waiting...minimal blocking)
5. MPI_Recv (Blocks till the data arrives into the buffer) (Non blocking: MPI_Irecv)
6. MPI_Wait(&request, &status); (blocks until the operation completes)
7. MPI_Test(&request, &flag, &status); flag = 1 (done), flag = 0 (still running)

```c
MPI_Init(&argc, &argv);
MPI_Comm_rank(MPI_COMM_WORLD, &rank);
MPI_Comm_size(MPI_COMM_WORLD, &size);
// code
MPI_Finalize(); // exiting
```

`MPI_Abort(MPI_COMM_WORLD, rank);`

# 15 - MPI, MPI-IO, Darshan

## Core Design Problem

HPC applications run on thousands of processes. If each process reads/writes its own small file, storage system collapses. How do you coordinate parallel I/O efficiently?

## Key Concepts

- **MPI**: Message passing, rank-based identifiers, communicators.
    
- **Collective I/O**: Processes cooperate to merge small requests into large sequential accesses.
    
- **MPI-IO**: Standard interface for parallel file access. Supports non-contiguous access via derived datatypes.
    
- **Darshan**: I/O characterization tool that captures access patterns without instrumenting application code.
    

---

> [!question] In MPI-IO, what is the "small write problem" in parallel file systems? How does collective I/O (using MPI_File_write_all) solve it? Give a concrete example with 1000 processes each writing 4KB to interleaved offsets.
> 
> - Small writes: 1000 processes × 4KB random offsets = file system sees 1000 tiny random I/Os. Seeks dominate.
>     
> - Collective I/O: MPI-IO layer sorts and merges requests. P0: read-modify-write for chunks. Process 0 gathers writes, writes large sequential block, then scatters.
>     
> - 1000×4KB interleaved: Collective I/O may write 4MB sequentially (one I/O) instead of 1000 I/Os.
>     

> [!question] Compare MPI-IO's collective I/O to Linux I/O scheduling (slide 5). Both reorder/merge requests. What does MPI-IO know that the OS scheduler doesn't? What does the OS scheduler know that MPI-IO doesn't? Which one can better handle non-contiguous access patterns from multiple processes?
> 
> - MPI-IO knows application's logical access pattern across processes (e.g., every process writes a 4KB stripe). OS only sees individual requests as they arrive.
>     
> - OS scheduler knows physical disk geometry, track skew, current head position.
>     
> - MPI-IO better for complex non-contiguous patterns (derived datatypes). OS only sees LBAs, loses higher-level structure.
>     

> [!question] Darshan captures I/O access patterns without modifying application code (it uses LD_PRELOAD to intercept MPI-IO calls). How is this similar to the VFS/vnode layer in NFS (slide 13)? Why can't Darshan capture patterns from direct-IO or mmap?
> 
> - VFS intercepts file operations at kernel-user boundary. Darshan intercepts MPI functions at library boundary.
>     
> - Direct-IO bypasses page cache but still goes through VFS. Darshan can capture it (if intercepting at higher level).
>     
> - mmap: Memory accesses don't go through file operations. Darshan cannot see them without page fault interception (costly).
>     

> [!question] Connect MPI-IO to LFS's segment cleaner. Both deal with "garbage" or "disorganized" data. In LFS, the cleaner consolidates live blocks. In MPI-IO, collective I/O consolidates scattered requests. What is analogous to the "segment summary block" in MPI-IO? How does MPI-IO know which process's data belongs where?
> 
> - Segment summary block: (inumber, offset) per block. MPI-IO file view: (offset in file, datatype, extent) per process.
>     
> - MPI-IO uses derived datatypes to describe layout: each process knows its mapping. Collective I/O builds a global mapping from per-process requests.

## 1. What is MPI?

### Definition
> MPI is a **message-passing library interface specification**, not an implementation. It defines *how* parallel processes communicate, not *what* the underlying hardware is.

### Key Insight
> MPI addresses the **message-passing parallel programming model**, where data moves from one process's address space to another's through **cooperative operations**.

### Why Not Shared Memory?
| Shared Memory | Message Passing (MPI) |
|---------------|----------------------|
| Single machine only | Works across clusters |
| Cache coherence overhead | No coherence needed |
| Programmer uses loads/stores | Programmer explicitly sends/receives |
| Hard to scale beyond ~64 cores | Scales to millions of processes |

## 3. Point-to-Point Communication

### Blocking vs Non-Blocking

| Type | Behavior | When to Use |
|------|----------|-------------|
| **Blocking** | Function returns only after operation completes (data has been sent or received) | Simple code, debugging |
| **Non-blocking** | Function returns immediately; operation continues in background | Overlap communication with computation |

### Blocking Send Variants

| Function | Behavior |
|----------|----------|
| `MPI_Send` | Standard send; may buffer or block depending on implementation |
| `MPI_Ssend` | Synchronous send; blocks until receive started |
| `MPI_Bsend` | Buffered send; uses user-provided buffer |
| `MPI_Rsend` | Ready send; assumes receive already posted (unsafe if wrong) |

### Blocking Receive
```c

         int source, int tag, MPI_Comm comm, MPI_Status *status)
```

| **Buffer** | Where data lives |
| **Count + Datatype** | How much data |
| **Destination/Source** | Which process |
| **Tag** | Distinguish between different messages |

## 4. Collective Communication

### Types of Collective Operations

| Operation | Description | Example |
|-----------|-------------|---------|
| **Barrier** | All processes wait until everyone arrives | Synchronization point |
| **Broadcast** | One process sends same data to all | Configuration parameters |
| **Scatter** | One process distributes *different* data to all | Distribute input array |
| **Gather** | All processes send data to one process | Collect results |
| **Reduce** | All processes send data; one process combines (sum, max, etc.) | Global sum, max value |
| **All-to-All** | Every process sends to every other | Matrix transpose |

### Visualization

```
BROADCAST:                    SCATTER:
    [0] has A                    [0] has [A,B,C,D]
     │                            │
     ├──→ [1] gets A              ├──→ [1] gets A
     ├──→ [2] gets A              ├──→ [2] gets B
     └──→ [3] gets A              └──→ [3] gets C
                                  └──→ [4] gets D

GATHER:                       REDUCE (SUM):
    [0] collects                  [0] gets sum of all
     ↑                              ↑
     │                              │
    [1]→A   [2]→B   [3]→C         [1]→2  [2]→3  [3]→5
```

## 5. MPI-IO: Parallel File I/O

### The Problem MPI-IO Solves

**Without MPI-IO (naive approach):**
```
1000 processes each writing 4KB to separate files:
- 1000 file creations
- 1000 metadata operations
- 1000 small writes (each with seek+latency)
- Result: Terrible performance
```

**With MPI-IO:**
```
1000 processes writing 4KB each to ONE file:
- Collective I/O: MPI library merges requests
- Result: 4MB sequential write (ONE I/O operation)
```

### Collective I/O

> All processes call the **same** collective I/O function. The MPI-IO layer sees the "big picture" and optimizes.

```c
// Collective write - all processes call this together
MPI_File_write_all(fh, buf, count, datatype, MPI_STATUS_IGNORE);
```

### How Collective I/O Works

```
Without Collective I/O:
    Process 0: write 4KB at offset 0
    Process 1: write 4KB at offset 4096
    Process 2: write 4KB at offset 8192
    ...
    File system sees: 1000 random writes (TERRIBLE)

With Collective I/O:
    MPI library sorts all requests:
        ┌────────────────────────────────────┐
        │ [0:4096] [4096:8192] [8192:12288] │  Sequential!
        └────────────────────────────────────┘
    One process (or library) writes 4MB sequentially
    File system sees: 1 large sequential write (EXCELLENT)
```

## 6. Non-Contiguous I/O: Derived Datatypes

### The Problem
Application data is often **not contiguous** in memory (e.g., array of structures, strided access).

### Without Derived Datatypes
```c
// Write every 2nd element of an array
for (int i = 0; i < N; i += 2) {
    MPI_File_write(fh, &array[i], 1, MPI_INT, ...);  // 500 I/Os!
}
```

### With Derived Datatypes
```c
// Describe the pattern once
MPI_Datatype filetype;
MPI_Type_vector(N/2,      // count
                1,        // block length
                2,        // stride
                MPI_INT, 
                &filetype);
MPI_Type_commit(&filetype);
MPI_File_set_view(fh, disp, MPI_INT, filetype, ...);
MPI_File_write(fh, array, 1, filetype, ...);  // ONE I/O!
```

### Resized Datatypes (For File Views)
```c
// File has: data (4 bytes), gap (8 bytes), data (4 bytes), gap (8 bytes)...
MPI_Type_contiguous(2, MPI_INT, &contig);
MPI_Datatype filetype;
MPI_Type_create_resized(contig, 0, 6 * sizeof(int), &filetype);
// Now each "chunk" is 2 ints followed by 4 ints gap
```

## 7. Darshan: I/O Characterization

### What is Darshan?
> A **lightweight, scalable I/O characterization tool** that captures I/O access patterns from production HPC applications WITHOUT modifying application code.

### How It Works
```
Application calls MPI_File_write()
         │
         ▼
┌─────────────────────────────────────────┐
│ Darshan (LD_PRELOAD intercept)          │
│   - Record: offset, size, timestamp     │
│   - Aggregate counters per process      │
│   - Pass call to actual MPI-IO          │
└─────────────────────────────────────────┘
         │
         ▼
Actual MPI-IO → File System
```

### What Darshan Captures

| Category | Metrics |
|----------|---------|
| **Access patterns** | Sequential vs random, strided vs contiguous |
| **I/O size distribution** | 4KB vs 1MB vs 100MB |
| **Per-process stats** | Bytes read/written, time spent |
| **File-level aggregates** | Total I/O, open/close counts |
| **POSIX vs MPI-IO** | Which interface used |

### Why Darshan is Important for Supercomputers

> "I don't know what my I/O looks like" is a common problem. Darshan gives answers:
> - "90% of reads are 4KB random" → Bad for HDDs, restripe Lustre
> - "All processes write same file at same offset" → Collective I/O can merge
> - "55 GB of data written but only 5 GB read" → Wasted writes

> [!question] You have a cluster with 10,000 MPI processes. Each process generates 1MB of results that must be written to a single shared file. Compare three approaches: (1) Each process calls `fopen()` + `fwrite()` to its own file, (2) Each process calls `MPI_File_write_at()` to offset = rank * 1MB, (3) Collective `MPI_File_write_all()` with merged requests. Quantify the number of I/O operations and metadata operations for each.
> 
> **Approach 1 (Separate files):**
> - Metadata ops: 10,000 file creations (inode alloc, directory updates)
> - Data ops: 10,000 writes (each 1MB sequential)
> - Total I/Os: ~10,000 data + 20,000 metadata = 30,000 I/Os
> - Problem: Metadata server becomes bottleneck
> 
> **Approach 2 (Independent writes to same file):**
> - Metadata ops: 1 file creation
> - Data ops: 10,000 writes (but each at DIFFERENT offsets)
> - File system sees: 10,000 random writes across 10GB file
> - Result: On HDD, each small write requires seek (8-12ms) → 100 seconds just for seeks
> 
> **Approach 3 (Collective MPI-IO):**
> - Metadata ops: 1 file creation
> - Data ops: Library merges 10,000 × 1MB into 10GB sequential write
> - Result: 1 large write (or few large writes)
> - Time: 10GB at 100MB/s = 100 seconds of transfer, NO seeks
> - **Winner: Approach 3 by ~100x for HDDs**

> [!question] Explain the "small write problem" in parallel file systems. Why does MPI-IO's collective I/O solve it? What happens if processes write to interleaved offsets (e.g., process 0 writes to offsets 0, 1000, 2000... process 1 writes to 1, 1001, 2001...)? Can collective I/O still merge these?
> 
> **Small write problem:** Multiple processes each writing small amounts (4KB) to random offsets. File system sees many tiny random I/Os. On HDD: each requires seek (slow). On Lustre: each may go to different OSTs (network overhead).
> 
> **Collective I/O solution:** MPI library sorts all requests by offset. Even if interleaved, library can:
> 1. Read the missing chunks from file (read-modify-write if alignment issues)
> 2. Assemble full stripe in memory
> 3. Write large contiguous block
> 
> **For interleaved example:**
> - Without collective: 1000 processes × 100 writes each = 100,000 random I/Os
> - With collective: Library sees 100,000 writes to 1000 offsets. Can merge into 1000 sequential writes (one per offset range) if pattern repeats. Or if offsets truly interleaved every byte, cannot merge beyond page/block size.
> - **Limitation:** Collective I/O works best when writes are aligned to file system block size.

> [!question] In MPI, what is the difference between blocking and non-blocking sends? Give a concrete example where non-blocking send improves performance. What new correctness problems does non-blocking introduce?
> 
> **Blocking send (`MPI_Send`):**
> ```c
> MPI_Send(data, size, MPI_INT, dest, tag, comm);
> // Function returns ONLY after data can be safely reused
> compute();  // Cannot overlap with communication
> ```
> 
> **Non-blocking send (`MPI_Isend`):**
> ```c
> MPI_Request req;
> MPI_Isend(data, size, MPI_INT, dest, tag, comm, &req);
> compute();  // Runs WHILE data is being sent
> MPI_Wait(&req, MPI_STATUS_IGNORE);  // Wait for completion
> ```
> 
> **Performance improvement example:**
> - Process 0 sends 1GB to Process 1. Send takes 10 seconds.
> - Process 0 must compute for 10 seconds anyway.
> - Blocking: 10 sec send + 10 sec compute (serial) = 20 seconds
> - Non-blocking: 10 sec (send + compute overlap) = 10 seconds
> 
> **New correctness problems:**
> - Must not modify `data` buffer until `MPI_Wait()` completes
> - Must eventually `MPI_Wait()` or `MPI_Test()` (else resource leak)
> - Deadlock possible if everyone waits before receiving
> - Completion order not guaranteed (can request completion in any order)

> [!question] Compare MPI collective I/O (`MPI_File_write_all`) with GFS's record append. Both handle multiple clients writing to the same file concurrently. What are the key differences in semantics, performance, and use cases?
> 
> | Aspect | MPI Collective I/O | GFS Record Append |
> |--------|-------------------|-------------------|
> | **Who calls** | ALL processes must call together | Any client independently |
> | **Synchronization** | Implicit barrier at call | No barrier |
> | **Write order** | Merged, but order not guaranteed across processes | Primary chooses order |
> | **Semantics** | Exactly once (if no failure) | At least once (duplicates possible) |
> | **Failure handling** | Call fails if any process fails | Retry, may cause duplicates |
> | **Use case** | HPC simulations (tightly synchronized) | Web-scale logging (loose synchronization) |
> | **Performance** | Optimized for merging | Optimized for low latency |
> 
> **Key difference:** MPI collective I/O assumes processes are already synchronized (barrier at compute step). GFS record append assumes processes are independent and can't coordinate.

> [!question] You are analyzing an HPC application with Darshan. The report shows: 1,000,000 reads, average size 4KB, 95% sequential (same file, monotonically increasing offsets). But throughput is only 5 MB/s on a Lustre system capable of 10 GB/s. What is the likely problem? How would you fix it?
> 
> **Problem diagnosis:**
> - 4KB reads are too small. For 1M reads × 4KB = 4GB total data.
> - Time if 4KB reads were sequential: 4GB at 10GB/s = 0.4 seconds.
> - But 5 MB/s = 4GB takes 800 seconds. Ratio = 2000x slowdown.
> - **Likely cause:** Each 4KB read is being sent as an individual I/O request through the entire stack. Even though offsets are sequential, small request size dominates.
> 
> **Fix options:**
> 1. Increase read size: Read 1MB chunks instead of 4KB (250x fewer I/Os)
> 2. Use MPI collective I/O: Library can merge 250 sequential 4KB reads into one 1MB read
> 3. Use POSIX `readahead()` or `fadvise()` to prefetch
> 4. Restructure application to read/write in file system block-aligned chunks
> 
> **Expected improvement:** 5 MB/s → 5,000 MB/s (ideal) or at least 500 MB/s (realistic)

> [!question] A derived datatype describes a non-contiguous pattern in memory (e.g., every 4th element of a 2D array). When this datatype is used with `MPI_File_write`, does the MPI library actually gather the non-contiguous pieces into a contiguous buffer before writing? What are the performance implications of each strategy?
> 
> **Two strategies:**
> 
> **Strategy 1: Gather-then-write**
> - MPI allocates temporary buffer
> - Copies all non-contiguous pieces into it
> - Issues ONE `write()` of contiguous buffer
> - Pro: Single system call, good for file system
> - Con: Extra memory copy, extra memory allocation
> 
> **Strategy 2: Scatter-gather I/O (writev)**
> - MPI calls `writev()` (POSIX scatter-gather)
> - Kernel receives list of (buffer, length) segments
> - Kernel writes directly from original segments
> - Pro: No extra copy, no temporary buffer
> - Con: Requires kernel support, more system call overhead per segment (but one call with many segments)
> 
> **Which is better?**
> - Small segments (< 10): writev ≈ gather-then-write
> - Many segments (> 100): gather-then-write may be faster (one large write vs many small segments in page cache)
> - MPI implementations may choose strategy based on datatype complexity and size
> 
> **For file I/O specifically:** File system prefers large sequential writes. Gather-then-write often wins because it creates one large sequential request.

> [!question] MPI-IO allows both independent writes (`MPI_File_write_at`) and collective writes (`MPI_File_write_all`). Give a scenario where independent writes are **faster** than collective writes. Give a scenario where collective writes are **faster**. Explain why.
> 
> **Independent writes faster:**
> - Scenario: Processes write to **completely different files** (not the same file)
> - Example: Each process writes its own checkpoint file: `checkpoint_rank_123.dat`
> - Parallel file system can stripe each file independently
> - Collective I/O would force unnecessary synchronization (barrier)
> - Independent writes proceed without coordination
> 
> **Collective writes faster:**
> - Scenario: All processes write to **same shared file** with non-contiguous patterns
> - Example: Each process writes 4KB to offset = rank * 1MB (1MB spacing)
> - Without collective: 1000 random 4KB writes → 1000 seeks
> - With collective: Library merges into 1MB sequential writes (if aligned)
> - Result: 1 I/O vs 1000 I/Os
> 
> **Why collective wins for same file:**
> ```
> Without collective:
> Process 0: write 4KB at 0
> Process 1: write 4KB at 1MB
> Process 2: write 4KB at 2MB
> 
> With collective:
> Library reads 1MB at 0 (if needed), merges, writes 1MB at 0
> ```

> [!question] Connect MPI collective I/O to LFS segment cleaning (Slide 11). Both involve garbage collection/merging of data. What is the analogous concept? How does the "cost-benefit" policy of LFS cleaning compare to MPI's decision to merge requests?
> 
> **Analogy:**
> - LFS cleaner: Merges live blocks from multiple segments into new segment
> - MPI collective I/O: Merges requests from multiple processes into larger I/O
> 
> **LFS Cost-Benefit Policy:**
> - Benefit = bytes saved (dead blocks that become free)
> - Cost = bytes read (live blocks that must be copied)
> - Clean segments with high dead bytes (benefit >> cost)
> 
> **MPI Merge Decision:**
> - Benefit = Seek avoidance (large sequential I/O vs many random ones)
> - Cost = Extra memory copies, read-modify-write overhead
> - Merge when (benefit >> cost): Many small writes, HDD backend
> - Don't merge when (cost >> benefit): Already large writes, SSD backend
> 
> **Key difference:** LFS cleaning is background (idle time). MPI collective I/O is synchronous (barrier). If decisions wrong, MPI pays cost immediately.

> [!question] You have a Lustre file system (Slide 16) with 10 OSTs. An MPI application writes a 10GB file with 1000 processes, each writing 10MB. Without collective I/O, each write goes to a single OST (striping). With collective I/O, all writes are merged. Compare the load on OSTs, metadata servers, and network in both cases.
> 
> **Without Collective I/O (independent writes):**
> - Each process writes 10MB directly
> - Lustre striping: Each 10MB file chunk goes to one OST (round-robin)
> - With 1000 processes, OSTs receive ~100 chunks each (10MB × 100 = 1GB per OST)
> - Metadata server: 1000 file open calls, 1000 lock requests
> - Network: 1000 simultaneous connections to OSTs
> - **Result:** OSTs balanced (good), but MDS overloaded, network contention
> 
> **With Collective I/O (merged):**
> - MPI library merges 1000×10MB = 10GB in a single write request
> - Lustre sees: One 10GB file write
> - Striping distributes 10GB across 10 OSTs → 1GB per OST
> - Metadata server: 1 file open, 1 lock request
> - Network: One aggregated stream (or few streams)
> - **Result:** MDS load reduced 1000x, network less congested
> 
> **Winner:** Collective I/O for metadata server. But both balance OSTs equally because striping works regardless.

> [!question] Darshan can capture that an application does 1 million 4KB reads (total 4GB) but throughput is only 100 MB/s on a system capable of 10 GB/s. What is the maximum possible throughput for 4KB reads on this system if each read incurs 50µs of software overhead? What is the bottleneck?
> 
> **Calculation:**
> - Overhead per 4KB read: 50µs (MPI+library+syscall)
> - Throughput if overhead dominated: 1 / 50µs = 20,000 reads/sec
> - 20,000 reads/sec × 4KB = 80 MB/s
> 
> **Result:** 80 MB/s maximum even if hardware is 10 GB/s
> 
> **Bottleneck:** Software overhead, not hardware
> 
> **Solutions:**
> - Increase read size to 1MB → 1,000 reads for same 4GB → 1,000 × 50µs = 0.05 seconds overhead → 4GB/0.05s = 80 GB/s (theoretically)
> - Use collective I/O (amortize overhead across many reads)
> - Use larger blocks in application
> 
> **Lesson:** Small I/O size kills performance regardless of hardware. Darshan helps identify this.

> [!question] Compare the failure model of MPI (process fails, job crashes) with GFS (chunkserver fails, continues). Why can't MPI have the same fault tolerance as GFS? What would be required to make MPI fault-tolerant?
> 
> | Aspect | MPI | GFS |
> |--------|-----|-----|
> | **Failure detection** | Typically none; process hangs | Heartbeats (seconds) |
> | **State** | Each process has private state | State replicated 3x |
> | **Recovery** | Job restarts from checkpoint | Automatic, no restart |
> | **Design assumption** | Failures are rare | Failures are normal |
> 
> **Why MPI isn't fault-tolerant:**
> 1. **Shared nothing:** Each process has private memory. Can't restore from others.
> 2. **Non-idempotent operations:** If process 0 crashes after sending half the messages, state inconsistent.
> 3. **No replication:** No redundant copies of process state.
> 4. **Barrier dependence:** Missing one process blocks all.
> 
> **What would be required:**
> - Checkpoint-restart (save state to parallel file system)
> - ULFM (User Level Fault Mitigation) extension to MPI
> - Process replication (redundant processes)
> - Idempotent communication (hard in message passing)
> 
> **Current solution:** Application-level checkpointing to Lustre (Slides 15-16). Use Darshan to optimize checkpoint writes.

> [!question] You are designing a new parallel file system for an MPI-focused HPC cluster. Based on what you learned from GFS, LFS, and Lustre, what three features would you include? What three features from GFS would you NOT include? Justify each.
> 
> **Would include:**
> 
> 1. **Lustre-style striping (Slide 16):** Multiple OSTs per file, configurable stripe count. MPI applications can tune for their access pattern.
> 
> 2. **MPI-IO collective I/O support (Slide 15):** Library-level merging of requests. Critical for small I/O from many processes.
> 
> 3. **Darshan-style introspection (Slide 15):** Built-in I/O profiling. Operators need to see what applications are doing.
> 
> **Would NOT include from GFS:**
> 
> 4. **64MB chunks:** Too large for HPC checkpoints (many small files). HPC needs tunable stripe size (Lustre's 1MB default is better).
> 
> 5. **At-least-once append semantics:** HPC needs exactly-once (simulations can't have duplicates). Would break many applications.
> 
> 6. **Single master with shadow read-only replicas:** HPC metadata operations are heavier (directory listings, stat). Needs distributed metadata (Lustre DNE).
> 
> **Why GFS doesn't fit HPC:** HPC workloads have different patterns (checkpoint/restart, many small files, POSIX expectations). GFS optimized for web-scale append workloads.
