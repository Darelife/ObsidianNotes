## Core Design Problem

Random writes kill HDD performance (seeks dominate). Since RAM caches reads, the bottleneck becomes writes. What if we make _all_ writes sequential and never overwrite?

## Key Concepts

- **Segment-based writing**: Buffer updates in memory, write entire segment sequentially.
    
- **Inode Map (imap)**: Indirection layer so inodes move without updating directories recursively.
    
- **Checkpoint Region (CR)**: Fixed location pointing to current imap pieces.
    
- **Segment Cleaner**: Garbage collector that reads partially-used segments, copies live blocks, erases rest.
    
- **Segment Summary Block**: Stores (inode #, offset) for each block to determine liveness.
    

---

> [!question] In LFS, when a file's data block is overwritten, why must the file's inode also be written to a new location? Why can't LFS just update the existing inode in place? What structure solves the "recursive update problem" that would otherwise require updating the entire directory path to the root?
> 
> - LFS never overwrites → inode must move with data block.
>     
> - Recursive update: Without indirection, moving inode changes its disk address → directory mapping must update → parent directory inode moves → parent's parent updates → up to root (O(path length) writes).
>     
> - Solution: imap. Directory stores (name → inumber). imap stores (inumber → disk address). Only imap needs updating.
>     

> [!question] Compare LFS with a journaling file system (ext3). Both write sequentially to a log/journal. What is the fundamental difference in how they use the log? Which one has faster crash recovery and why?
> 
> - ext3: Journal is temporary staging area. Final data lives elsewhere. Checkpoint copies from journal to final location.
>     
> - LFS: The log IS the filesystem. No second copy.
>     
> - Recovery: LFS < ext3. LFS: read CR → imap → done. ext3: replay journal (potentially large if uncheckpointed) → then possibly fsck if journal corrupted.
>     

> [!question] LFS's segment cleaner must determine which blocks are live. It uses a segment summary block storing (inumber, offset) for each block. Walk through the liveness check for a block at disk address A. Could a race condition occur if the file is updated while the cleaner is running? How does LFS handle this?
> 
> - Step 1: Read summary block → get (inumber N, offset T).
>     
> - Step 2: Look in imap → get disk address of inode N.
>     
> - Step 3: Read inode → follow pointer for offset T → get current disk address.
>     
> - Step 4: If current address == A → live; else dead.
>     
> - Race: Cleaner may copy a block just as new write updates same offset. LFS uses block-level locks or ensures cleaner runs when file system is quiescent (idle time). Some versions use "write barrier" before cleaning.
>     

> [!question] Connect LFS to SSD write behavior (from slide 7). SSDs also do out-of-place writes and have garbage collection. Is an SSD effectively an LFS in hardware? If so, why would you still want an LFS on top of an SSD? What's the double-garbage-collection problem?
> 
> - Yes, FTL in SSD does exactly what LFS does: out-of-place writes + garbage collection.
>     
> - LFS on SSD: LFS's segment cleaning becomes GC on already-GC-ed data. Write amplification multiplies (WAF_LFS × WAF_FTL).
>     
> - Double GC: Host writes 1 block → LFS writes 1 block (WAF 1) → FTL may write 1.1-4 blocks. If LFS also does cleaning, FTL sees more writes. Modern advice: Use LFS only on raw flash (without FTL) or use FTL directly.
>     

> [!question] In your midsem Q4, you worked with a page-mapped FTL on an SSD. How is the FTL's mapping table conceptually similar to LFS's imap? How is the FTL's garbage collector similar to LFS's segment cleaner? If you had to choose one to implement in software vs hardware, which makes more sense and why?
> 
> - Imap: (inumber → disk address of inode). FTL: (LBA → page address). Both are indirection tables.
>     
> - GC: Both copy live data from victim block/segment and erase.
>     
> - Software LFS + hardware FTL is redundant. Better: Raw flash with host-side FTL (Open-channel SSD) → host controls GC, avoids double mapping. Hardware FTL is simpler for legacy OS; software LFS on raw flash gives more control to applications.

# LOG-STRUCTURED FILE SYSTEM (LFS) - COMPLETE NOTES

Based on your course slides (11 - Log Structured File System.pdf) and the Rosenblum & Ousterhout SOSP 1991 paper

---

## 1. What is LFS?

### Definition
> A log-structured file system writes **all modifications** (data and metadata) to disk **sequentially** in a log-like structure. The log is the **only structure on disk**; there is no separate data region or inode table in fixed locations.

### The Core Insight
> **System memories are growing.** More data can be cached in RAM. Therefore, **disk traffic becomes dominated by WRITES**, not reads. If writes are the bottleneck, optimize writes.

### The Fundamental Assumption
> As memory sizes increase, the read cache becomes so effective that **most reads are served from memory**. The disk is primarily used for **writes**.

### The Key Observation (from the paper)
> "A log-structured file system writes all new information to disk in a sequential structure called the log. This approach increases write performance dramatically by eliminating almost all seeks."

---

## 2. The Problem: Why Traditional File Systems Are Bad for Writes

### The Gap Between Random and Sequential I/O

| Metric | HDD Performance |
|--------|-----------------|
| Sequential write | 100-200 MB/s |
| Random write (4KB) | 1-2 MB/s (due to seeks) |
| **Performance gap** | **100-200x** |

### What Traditional File Systems Do

When you write to a file in FFS/ext2/ext3:
1. Write the data block (maybe)
2. Write the inode (updates file size, timestamps, block pointers)
3. Write the data bitmap (mark block allocated)
4. Write the inode bitmap (mark inode allocated if new file)
5. Write directory entries if creating new file

Each of these writes goes to a **different location** on disk. Each write requires a **seek** (10ms). Result: **Slow!**

### The Small Write Problem on RAID (Connection to Slide 17)

> RAID has its own small-write problem. LFS was designed before RAID was common, but the same principle applies: small random writes kill performance.

---

## 3. The LFS Solution: Write Everything Sequentially

### The Basic Idea

```
Traditional FS:                    LFS:
Write data block → seek           Buffer writes in memory
Write inode → seek                 When buffer full:
Write bitmap → seek                 Write ALL updates sequentially
Write directory → seek              to free disk space in ONE go

Random writes (slow)               Sequential write (fast!)
```

### Visual Representation

```
Traditional File System (FFS):
┌─────┐ ┌─────┐ ┌─────┐ ┌─────┐
│Inode│ │Data │ │Bitmap│ │Indirect│  ← All over disk
└─────┘ └─────┘ └─────┘ └─────┘

LFS:
┌─────────────────────────────────────────────┐
│ Segment: [Inode][Data][Bitmap][Indirect][...]│  ← Sequential!
└─────────────────────────────────────────────┘
```

---

## 4. Segment-Based Writing

### What is a Segment?
> A large contiguous region of disk (typically a few MB) that LFS writes in one sequential operation.

### How Segments Are Written

```
1. LFS buffers all updates (data blocks, inodes, bitmaps, directories)
   in an in-memory segment buffer.

2. When the segment buffer is full (or a timer expires),
   LFS writes the entire segment to a FREE region of disk.

3. The write is a single sequential transfer.
   No seeks! No rotational delays!

4. LFS never overwrites existing data.
   Always writes to free space.
```

### Segment Size Calculation (From Slide 9)

**Problem:** How much must be buffered to achieve high effective bandwidth?

**Formula:**
```
R_effective = D / (T_position + D / R_peak)

Where:
    D = segment size
    T_position = seek time + rotational latency
    R_peak = peak transfer rate

To achieve F fraction of peak (e.g., F = 0.9 for 90%):
    D = (F / (1 - F)) × R_peak × T_position
```

**Example from slide:**
```
T_position = 10 ms
R_peak = 100 MB/s
F = 0.9 (want 90% of peak)

D = (0.9 / 0.1) × 100 MB/s × 0.01 s
D = 9 × 1 MB
D = 9 MB
```

**Interpretation:** Need to buffer 9 MB of updates before writing to achieve 90% of peak disk bandwidth.

---

## 5. The Inode Location Problem

### The Problem
In traditional file systems, inodes are at **fixed locations** on disk (inode table). LFS writes inodes **everywhere** (wherever the log writes them). How do you find an inode?

### The Solution: Inode Map (imap)

> A level of indirection that maps **inode number → disk address of the inode**.

```
LFS Directory Entry:              imap (in memory, also on disk):
┌─────────────────┐              ┌─────────────────────────┐
│ filename: "foo" │              │ inode 1 → disk addr 1000 │
│ inumber: 42     │              │ inode 2 → disk addr 5234 │
└─────────────────┘              │ inode 42 → disk addr 7890│
                                 └─────────────────────────┘
```

### How to Find a File (Walking Through)

```
1. User: open("/home/user/foo.txt")

2. Start at root directory (inumber = 2 known)
   Look in imap: inode 2 is at disk address A3

3. Read inode 2 (directory inode) from A3
   Inode points to directory data block at A2

4. Read directory data from A2
   Find entry "home" → inumber = 20

5. Look in imap: inode 20 is at disk address X

6. Repeat until "foo.txt" found
   Final entry gives inumber = 102

7. Look in imap: inode 102 is at disk address Y

8. Read inode 102 from Y → now have file's data block pointers
```

### The Recursive Update Problem (Solved!)

In a traditional system without imap:
- Moving an inode requires updating the directory that points to it
- That directory's inode moves → must update parent directory
- Chains all the way to root! (O(path length) writes)

**With imap:**
- Directory stores (name → inumber), NOT disk address
- Inode moves → only imap entry changes
- Directories unchanged!

## 6. Checkpoint Region (CR)

### The Problem
imap itself must be persistent. But imap is large (4 bytes per inode). Where to store it?

### The Solution: Checkpoint Region

> A **fixed location** on disk (at a known address) that contains pointers to the **current imap pieces**.

```
Disk Layout:
┌─────────────────────────────────────────────────────────────┐
│ CR │ Segment 0 │ Segment 1 │ Segment 2 │ ... │ Segment N-1 │
└─────────────────────────────────────────────────────────────┘
  │
  └──► points to imap pieces scattered in segments
```

### Checkpoint Region Contents

```
┌─────────────────────────────────────┐
│ Timestamp                           │
│ Pointer to imap piece 0 (addr, len) │
│ Pointer to imap piece 1 (addr, len) │
│ ...                                 │
│ Pointer to last segment written     │
│ (head of log)                       │
└─────────────────────────────────────┘
```

### How Often is CR Updated?
> Every ~30 seconds (or when segment cleaner runs). Less frequent = less performance impact.

### Two Checkpoint Regions (Crash Safety)

```
Disk has TWO checkpoint regions (at both ends of disk)
    CR0 at start of disk
    CR1 at end of disk

Updating CR:
    1. Write CR header with timestamp
    2. Write CR body
    3. Write CR footer with timestamp

If crash during update:
    Timestamps won't match → system knows CR is corrupt
    Use the other CR (still valid)
```

---

## 7. Reading from LFS

### Steps to Read a File

```
1. Read Checkpoint Region from known disk address
2. CR points to imap pieces
3. Read imap pieces into memory (cached!)
4. To read file with inumber N:
   - Look in cached imap → get disk address of inode N
   - Read inode N from disk
   - Inode contains direct/indirect pointers
   - Follow pointers to read data blocks
```

### Why This Works

| Component | Where it lives | How accessed |
|-----------|---------------|--------------|
| Checkpoint Region | Fixed address | Direct read at mount time |
| imap | Scattered in log | Read via CR, then cached in memory |
| Inodes | Scattered in log | Found via imap |
| Data blocks | Scattered in log | Found via inode pointers |

---

## 8. The Garbage Collection Problem: Segments Fill Up

### The Problem
LFS never overwrites. It always writes to free space. Eventually, disk fills up. Need to **reclaim space** from segments that contain old (dead) data.

### Why Garbage is Created

```
File foo.txt: blocks [10, 11, 12] in Segment A

User appends to foo.txt:
    New block 13 written to Segment B
    Inode updated (new version) written to Segment B
    Old inode in Segment A is now DEAD

Segment A still contains:
    Old inode (dead)
    Old data blocks 10,11,12 (if file was overwritten, these could be dead too)
```

### What Needs to Happen
> Segments must be cleaned: dead blocks removed, live blocks compacted into new segments, old segments erased.

---

## 9. Segment Cleaning: Determining Liveness

### The Challenge
How does LFS know which blocks in a segment are **live** (still in use) vs **dead** (garbage)?

### Solution: Segment Summary Block

> At the head of each segment, store a summary block containing:
> - For each data block D: (inumber N, offset T)
> - For each inode block: (inumber N)

```
Segment Layout:
┌─────────────────────────────────────────────────────────────┐
│ Summary Block │ Block 0 │ Block 1 │ Block 2 │ ... │ Block N │
│ (inumber,offset)│         │         │         │     │         │
└─────────────────────────────────────────────────────────────┘
```

### Liveness Check Algorithm

```
To check if block at disk address A is live:

1. Read segment summary block (at segment head)
   Find entry for block A → (inumber N, offset T)

2. Look in imap to find disk address of inode N

3. Read inode N (may be in memory cache)

4. Follow inode's pointer for offset T
   (may go through indirect blocks)
   Get current disk address CUR

5. If CUR == A:
        Block is LIVE
   Else:
        Block is DEAD (a newer version exists elsewhere)
```

### Example

```
Block A is at disk address 5000
Summary block says: inumber=42, offset=3

imap says inode 42 is at address 8000
Read inode 42 from 8000
Offset 3 points to address 9000

5000 != 9000 → Block at 5000 is DEAD!
(Superseded by newer version at 9000)
```

---

## 10. Segment Cleaning: Which Segments to Clean?

### Cost-Benefit Analysis

**Benefit** = Amount of free space reclaimed = dead blocks in segment

**Cost** = Amount of live data that must be copied

**Cleaning policy:**
> Clean segments with **high benefit** (many dead blocks) and **low cost** (few live blocks).

### Hot vs Cold Segments

| Segment Type | Characteristics | Cleaning Strategy |
|--------------|-----------------|-------------------|
| **Hot segment** | Frequently overwritten; many dead blocks quickly | Wait longer to clean (more dead blocks accumulate) |
| **Cold segment** | Stable data; few dead blocks | Clean sooner (live data small, compact easily) |

### The Cleaner Algorithm

```
1. Select victim segment(s) with highest (dead_bytes / total_bytes)
2. For each block in victim segment:
       if block is LIVE:
           copy to current segment buffer
3. Erase the victim segment (free entire segment)
4. Write new segment containing live blocks
5. Update imap entries for moved blocks
```

---

## 11. Crash Recovery in LFS

### Two Crash Scenarios

**Scenario 1: Crash during segment write**

```
Segment write in progress:
    Some blocks written, some not

Recovery:
    Checkpoint region points to last COMPLETE segment
    Incomplete segment is ignored
    Last few seconds of updates lost (acceptable)
```

**Scenario 2: Crash during checkpoint region update**

```
Updating CR in progress:
    CR0 partially written

Recovery:
    Check timestamps in CR0 and CR1
    If mismatched, use the good one
    BAD CR is overwritten next checkpoint
```

### Recovery Steps (at mount time)

```
1. Read both checkpoint regions
2. Pick the one with valid timestamps (most recent)
3. Follow pointers to imap pieces
4. Load imap into memory
5. File system is now consistent!
   (Last few uncheckpointed segments may be ignored)
```

### Recovery Time Comparison

| System | Recovery Time (for 1TB FS) |
|--------|---------------------------|
| fsck (ext2) | Hours |
| Journal replay (ext3) | Seconds to minutes |
| **LFS** | **Seconds** (just load CR + imap) |

## 12. LFS vs Traditional File Systems

| Aspect | Traditional (FFS/ext2) | LFS |
|--------|----------------------|-----|
| **Write pattern** | Random (many seeks) | Sequential (no seeks) |
| **Overwrite** | In-place | Never (always new location) |
| **Inode location** | Fixed in inode table | Scattered; found via imap |
| **Free space** | Bitmaps | Segments (cleaning needed) |
| **Crash recovery** | fsck (slow) | Checkpoint region (fast) |
| **Space overhead** | Low | Higher (cleaning needs free space) |
| **Write performance** | Poor (seeks dominate) | Excellent (sequential) |
| **Read performance** | Good (direct pointers) | Good (same as traditional) |

## 13. LFS Performance Claims (from the paper)

### What LFS Achieves

> "Sprite LFS outperforms current Unix file systems by an order of magnitude for small-file writes while matching or exceeding Unix performance for reads and large writes."

### Disk Bandwidth Utilization

| System | Disk bandwidth used for writes |
|--------|-------------------------------|
| Traditional Unix | 5-10% |
| **Sprite LFS** | **70%** (even with cleaning overhead) |

### Why Such a Difference?

Traditional FS: Write 1MB of small files = many seeks (10ms each) → each seek wastes 10ms of potential transfer time

LFS: Write 1MB of updates = one sequential write → no seeks → full bandwidth used

## 14. LFS vs Journaling (Connection to Slide 10)

| Aspect | Journaling (ext3) | LFS |
|--------|------------------|-----|
| **Log purpose** | Temporary staging area | The entire file system |
| **Writes to log** | Metadata (or data+metadata) | Everything |
| **Final location** | Separate (checkpoint) | Log IS final location |
| **Recovery** | Replay journal | Load CR + imap |
| **Space reclamation** | Circular journal | Segment cleaning |
| **Write amplification** | Data written twice | Data written once (plus cleaning) |

**Key difference:** Journaling is a **bolt-on** for crash consistency. LFS is a **ground-up redesign** where logging is the primary storage paradigm.

> [!question] Compare crash recovery in LFS vs ext3 journaling. Which recovers faster? Which loses less data in a crash? Under what circumstances would ext3 lose more data than LFS?
>
> **Recovery Process Comparison:**
>
> | Phase | ext3 Journaling | LFS |
> |-------|-----------------|-----|
> | **Mount** | Read journal superblock | Read checkpoint region |
> | **Check for transactions** | Scan journal for committed transactions | Check CR timestamps |
> | **Replay** | Replay committed transactions | None (unless CR corrupt) |
> | **Recovery time** | Proportional to journal size | Constant (load CR + imap) |
>
> **Data loss on crash:**
>
> | Crash Timing | ext3 loses | LFS loses |
> |--------------|-----------|----------|
> | Before transaction commit | Nothing (not committed) | Segment buffer (in memory) |
> | After commit, before checkpoint | Data safe (in journal) | Segment written? Depends |
> | During checkpoint write | May lose checkpointed data | May lose last segment |
> | During journal write | Transaction may be corrupt | N/A |
>
> **Which recovers faster?** LFS (constant time) beats ext3 (depends on journal size)
>
> **Which loses less data?** Depends on workload:
>
> ```
> ext3: Data loss window = time between fsync() calls
> LFS: Data loss window = time since last segment write (typically 1-5 seconds)
>
> If application fsync() every write:
>     ext3 loses less (each write durable individually)
>     LFS may still lose buffered writes
>
> If application never fsync():
>     Both lose similar amount (last few seconds of writes)
> ```
>
> **When ext3 loses MORE data:**
> - Journal corruption (checksum failure) → may lose whole journal
> - Power failure during journal write → transaction lost
> - LFS's multiple checkpoint regions are more robust

> [!question] Connect LFS segment cleaning to SSD garbage collection (from Slide 7). Both perform out-of-place writes and need garbage collection. If you run LFS on top of an SSD, what happens? Estimate the write amplification factor (WAF) when LFS cleaning and SSD GC both operate.
>
> **The Double GC Problem:**
>
> ```
> Application writes 4KB
>         │
>         ▼
> LFS: writes to new segment location (4KB written to SSD)
>         │
>         ▼
> LFS segment cleaner: reads live blocks, writes new segment
>         │
>         ▼
> SSD FTL: out-of-place write (WAF_SSD = 2-4x)
>         │
>         ▼
> SSD GC: reads live pages, writes to new block (more amplification)
>
> Total WAF = WAF_LFS × WAF_SSD
> ```
>
> **Estimation:**
>
> | Layer | Typical WAF | Explanation |
> |-------|-------------|-------------|
> | LFS cleaning | 1.1 - 2.0 | Depends on fragmentation |
> | SSD FTL | 1.5 - 3.0 | Depends on workload |
> | **Combined** | **1.65 - 6.0** | Multiplicative! |
>
> **Example calculation:**
> ```
> Application writes 4KB
> LFS cleaning WAF = 1.5 (50% overhead)
> → SSD sees 6KB of writes
> SSD FTL WAF = 2.0
> → NAND sees 12KB of writes
>
> Effective WAF = 12KB / 4KB = 3.0
> ```
>
> **Is this a problem?** Yes! SSD lifetime reduces by factor of 3-6x.
>
> **Solution:** Don't run LFS on raw SSDs. Use:
> - LFS on raw flash (no FTL) → Open-channel SSD
> - SSD with native LFS (F2FS - Flash-Friendly File System)
> - Traditional file system with TRIM support
>
> **Lesson:** LFS's design assumption (disk seeks are slow, writes are sequential) doesn't match SSD characteristics (no seeks, erase-before-write). What was optimal for HDDs is suboptimal for SSDs.

> **Additional information LFS would need (not in midsem checker):**
>
> | Information | Why needed |
> |-------------|-----------|
> | **Segment summary block** | Maps each block to (inumber, offset) |
> | **Indirect block pointers** | For files larger than direct pointers |
> | **imap persistence** | Must survive reboots |
> | **Checkpoint region** | To locate imap after crash |
> | **Multiple versions** | LFS has multiple versions of same inode; need to find latest |
>
> **Connection:** The midsem checker is essentially the same liveness algorithm LFS uses, just simplified (no indirect blocks, fixed segment size).

---

> [!question] A file in LFS is modified many times (e.g., appending 1GB in 4KB increments). Where are the old versions of the file's blocks? What happens to them? If you wanted to implement a versioning file system that keeps ALL old versions, what would you change in LFS? What would be the storage overhead?
>
> **Where old versions go:**
>
> ```
> File foo.txt:
>     Version 1: blocks [100, 101] in Segment A
>     Version 2: blocks [200, 101] (second block unchanged) in Segment B
>     Version 3: blocks [200, 300] in Segment C
>
> Segments A, B, C all contain old versions.
> ```
>
> **Standard LFS (no versioning):**
> - Segment cleaner eventually recognizes old blocks as DEAD
> - Dead blocks are NOT copied during cleaning
> - Old versions are PERMANENTLY LOST when segment erased
>
> **To implement versioning file system:**
>
> | Change | Purpose |
> |--------|---------|
> | **Never clean** (or clean only when space exhausted) | Preserve old versions |
> | **Keep backward pointers** | Navigate to previous versions |
> | **Version number in inode** | Distinguish versions |
> | **Time-based checkpoint region** | Access old snapshots |
> | **Separate cleaner for old segments** | Don't delete historical data |
>
> **Storage overhead for versioning:**
>
> ```
> File modified M times, each modification changes fraction f of file
> Storage = (1 + f×M) × file_size
>
> Example: 1GB file, 1000 modifications, each changes 4KB:
>     f = 4KB / 1GB = 0.000004
>     Storage = (1 + 0.000004 × 1000) × 1GB = 1.004 GB
>
> But if each modification changes entire file (f=1):
>     Storage = (1 + 1000) × 1GB = 1 TB!
> ```
>
> **Trade-off:** Versioning is cheap for small changes (appends, small edits) but expensive for heavy overwrites. LFS's natural append-only nature makes it ideal for versioning, but standard LFS chooses to garbage collect for space efficiency.

## QUICK REFERENCE CARD

| Concept | LFS Implementation |
|---------|-------------------|
| **Core principle** | Write all updates sequentially to log |
| **Segment** | Large contiguous region (MBs) written at once |
| **Segment size formula** | D = (F/(1-F)) × R_peak × T_position |
| **imap** | Inode number → disk address of inode |
| **Checkpoint region (CR)** | Fixed address pointing to imap pieces |
| **CR update frequency** | Every ~30 seconds |
| **Segment summary block** | (inumber, offset) for each block in segment |
| **Liveness check** | Compare block's address with inode's current pointer |
| **Cleaning policy** | Clean segments with high dead block ratio |
| **Hot vs cold** | Hot segments wait longer to accumulate dead blocks |
| **Crash recovery** | Load CR → read imap → done (seconds) |
| **vs Journaling** | LFS log is the FS; journaling log is temporary |
| **vs SSD** | Double GC problem; don't run LFS on raw SSD |

**Key Formulas:**
- Segment size for target efficiency: `D = (F/(1-F)) × R_peak × T_position`
- Effective bandwidth: `R_effective = D / (T_position + D/R_peak)`
