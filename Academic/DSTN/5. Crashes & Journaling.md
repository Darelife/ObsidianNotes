[[6. Log File System]]

## Core Design Problem

A single file system operation (like appending to a file) requires multiple disk writes (inode, bitmap, data block). A crash between these writes leaves the disk in an inconsistent state. How do we fix this without scanning the whole disk (fsck)?

## Key Concepts

- **The 6 crash scenarios** (from your midsem Q2)
- **fsck**: Scan entire disk, fix inconsistencies. Too slow for large disks.
- **Journaling (Write-Ahead Logging)**: Write intent to a log _before_ executing the operation. On crash, replay the log.
- **Data Journaling vs Metadata Journaling**: Write both data+metadata to log vs write only metadata.
- **Checksums & Atomic Transactions**: Ensure TxE is ≤512 bytes or use checksums to detect partial writes.    
- **Circular Log & Checkpointing**: Reuse log space after updates are safely on disk.

> [!question] A file system appends a 4KB block to an existing file. List all on-disk structures that must be updated. If a crash occurs after the inode is written but before the data bitmap is updated, which of the 6 crash scenarios from your midsem does this correspond to, and what inconsistency results?
> 
> - Scenario 5: Inode and data block written, bitmap not written.
>     
> - Inode points to the new block, but bitmap says block is free → future allocations may reuse the block, causing two files to claim the same block.
>     

> [!question] Compare fsck and journaling as crash recovery mechanisms. Under what conditions would fsck be _faster_ than journal replay? Why did modern file systems abandon fsck as the primary recovery method?
> 
> - fsck is faster only if very few writes occurred before crash (journal still has replay work) OR disk is tiny.
>     
> - Abandoned because fsck time grows with disk size (O(disk capacity)), while journal replay time grows with uncheckpointed writes (O(work since last checkpoint)). At PB scale, fsck takes days; replay takes seconds.
>     

> [!question] In ext3's data journaling, why does writing the data block twice (once to log, once to final location) create a performance problem? How does metadata journaling (ordered mode) solve this, and what new consistency risk does it introduce?
> 
> - Data journaling: Each logical write becomes 2 physical writes → 50% bandwidth loss.
>     
> - Metadata journaling writes data to final location first, then journals metadata. Risk: Crash after data write but before metadata commit → file system consistent but data belongs to wrong file (garbage in file). User must handle this.
>     

> [!question] Connect crash consistency to LFS (Log-Structured File System). LFS never overwrites—it always writes to a new location. How does this design choice affect crash recovery compared to a traditional in-place update file system? Does LFS need journaling? Why or why not?
> 
> - LFS writes sequentially to the log. A crash leaves the last segment partially written. Recovery: read checkpoint region, then scan only the last segment (not entire disk) to find incomplete writes.
>     
> - LFS does NOT need separate journaling because the log _is_ the filesystem. The "write-ahead" is inherent. Crash recovery is faster because only the tail needs checking.
>     

> [!question] The Linux kernel's I/O schedulers (from slide 5) reorder requests to optimize HDD performance. How does journaling interact with disk scheduling? If a file system issues a journal write followed by a checkpoint write, could the disk scheduler reorder them? What mechanism ensures the journal write reaches disk first?
> 
> - Yes, disk scheduler could reorder if not constrained.
>     
> - Barrier requests or ordered tags in the storage stack. In ext4, `journal_async_commit` vs ordered mode. Some rely on write barriers (flush cache before commit block). Failure to order → transaction written but commit block lost → replay may skip valid transaction.

## 1. The Problem: Why Do Crashes Cause Inconsistency?

### The Fundamental Issue

A single file system operation requires **multiple independent disk writes**. The disk processes **one write at a time**. A power loss or system crash between writes leaves the on-disk state **partially updated and inconsistent**.

### The Classic Example: Appending to a File

To append a single data block, the file system must write **three separate structures**:

|#|Structure|What it stores|
|---|---|---|
|1|**Inode (I)**|New pointer to data block, updated file size, timestamps|
|2|**Data bitmap (B)**|Marks the new data block as allocated|
|3|**Data block (Db)**|The actual user data|

These three writes happen **one at a time, in some order**. A crash can occur **between any two writes**.

## 2. The Six Crash Scenarios (From Your Midsem Q2)

Assume initial state: data block 5 is free. Operation: append data block 5 to file.

|Scenario|What was written|What was NOT written|Resulting State|Consistent?|
|---|---|---|---|---|
|1|Db only|I, B|Data written but nobody points to it. User data lost.|**Yes** (just data loss)|
|2|I only|B, Db|Inode points to block 5, but bitmap says free. Block may be reused → two files claim same block.|**No**|
|3|B only|I, Db|Bitmap says block 5 allocated, but no inode points to it. **Space leak** (block lost forever).|**No**|
|4|I + B|Db|Inode and bitmap agree (both say block 5 is file's). Data block contains garbage.|**Yes** (but garbage in file)|
|5|I + Db|B|Inode points to block 5, bitmap says free. Inconsistent.|**No**|
|6|B + Db|I|Bitmap says allocated, data written, but no inode points to it. Orphaned data block.|**No**|

### Key Insight:

> **Consistency** means inode and bitmap agree. **Correctness** (user data intact) is a separate concern.

## 3. Solution 1: fsck (File System Checker)

### How fsck Works

The UNIX tool that scans the entire disk and repairs inconsistencies.

|Step|What fsck checks|What it fixes|
|---|---|---|
|1|Superblock integrity|Restores from backup if corrupt|
|2|All inodes (valid type, links count)|Orphaned inodes → /lost+found|
|3|Inode vs bitmap mismatch|Trusts inode, updates bitmap|
|4|Duplicate block pointers|Copies valid inode to all|
|5|Bad blocks (out of range)|Removes from allocation|
|6|Directory validity (. and .., no loops)|Rebuilds directory structure|

### The Fatal Flaw

> **fsck time is proportional to disk capacity, not damage size.**

|Disk size|fsck time (approx)|
|---|---|
|500 GB HDD|30-60 minutes|
|4 TB HDD|4-8 hours|
|10 TB HDD|1-2 days|
|100 TB array|1+ weeks|

### Why fsck Became Unacceptable

- **RAID and large disks** make scans impossibly slow.
- To fix **3 corrupted blocks**, you scan **entire terabytes**.
- Data centers cannot afford hours of downtime.
- **Irrational trade-off**: tiny problem, huge recovery cost.

> **Connection to your midsem Q1**: Your inode checker in LFS only scans segments, not the whole disk. That's the key difference.

## 4. Solution 2: Journaling (Write-Ahead Logging)

### The Core Idea

> **Before making the actual updates, write a "little note" (the journal/log) describing what you're about to do.**

If a crash occurs, replay the journal instead of scanning the entire disk.

### History

- First implemented in **Cedar File System at Xerox PARC (1987)**.
- Now used in: ext3, ext4, reiserfs, JFS, XFS, NTFS.

---

## 5. Data Journaling (Full Journaling)

### Transaction Structure

A transaction (e.g., appending a block) is written to the journal as:

|Component|Contains|
|---|---|
|**TxB** (Transaction Begin)|Transaction ID (TID), addresses of inode, bitmap, data block|
|**I**|The entire inode (or just the updated parts)|
|**B**|The entire bitmap block|
|**Db**|The entire data block|
|**TxE** (Transaction End)|Transaction ID (TID)|

### The Two-Phase Protocol

|Phase|Action|After crash, if incomplete...|
|---|---|---|
|**Journal write**|Write TxB + I + B + Db to journal. Wait for completion.|Transaction not yet committed → skip|
|**Journal commit**|Write TxE to journal. Wait for completion. Transaction is now **committed**.|Transaction committed but not checkpointed → replay|
|**Checkpoint**|Write I, B, Db to their final disk locations.|After checkpoint, journal space can be freed|

### Why Two-Phase?

Without waiting for TxE, a crash during the journal write could leave a partial transaction that looks valid but has garbage data.

### The Atomic Commit Problem

The disk may break a single large write into smaller chunks. If TxB and TxE land in the same chunk but data in another, and power fails after first chunk:

text

Disk sees: \[TxB] \[I] \[B] \[TxE]  (looks valid!)
But data block Db was never written.

**Solution in ext4**: Checksums in TxB and TxE. If checksums mismatch, treat as invalid.

## 6. Metadata Journaling (Ordered Journaling)

### The Problem with Data Journaling

- Every logical write → **two physical writes** (one to journal, one to final location).
- **50% bandwidth loss** for writes.
- Particularly painful for sequential workloads.

### The Solution: Write Data Once, Journal Only Metadata

**Ordered Journaling Protocol:**

|Step|Action|
|---|---|
|1|Write **data block (Db)** to its **final location**. Wait for completion.|
|2|Write **TxB + I + B** (metadata only) to journal. Wait.|
|3|Write **TxE** to journal (commit). Wait.|
|4|Write metadata (I, B) to final locations (checkpoint).|

### Why This Works

- Data is already safely on disk before metadata points to it.
    
- If crash occurs after data but before metadata commit → data is unreachable (orphaned) but not corrupt.
    
- If crash occurs during checkpoint → replay writes metadata again (idempotent).
    

### The Consistency Risk

> After crash, data may be written but not referenced by any inode → **garbage in storage** but file system is **structurally consistent**.

Applications must handle this (e.g., use fsync, or tolerate transient garbage).

---

## 7. Performance Optimizations

### Batching Multiple Transactions

- Instead of committing each operation separately, buffer writes in memory.
    
- Wait **5-30 seconds** (ext3 default) to accumulate multiple transactions.
    
- Write all together as one large sequential journal write.
    

**Example**: Creating two files in the same directory would update parent inode twice. Batching eliminates one disk write.

### Circular Log (Reusing Journal Space)

- Journal has fixed size (ext3 default: 4MB to 400MB).
    
- After checkpoint, transaction is marked **free** in journal superblock.
    
- New transactions overwrite oldest freed space (circular buffer).
    

### Checksum Protection (ext4 improvement)

- Place checksums in TxB and TxE.
    
- Allows **single large journal write** instead of two-phase.
    
- On crash, checksum mismatch → skip transaction.
    

---

## 8. The Block Reuse Problem (Revoke Records)

### The Scenario

1. File A is deleted (blocks freed).
    
2. Journal hasn't yet checkpointed this deletion.
    
3. File B is created and reuses the same block.
    
4. Crash occurs.
    
5. Journal replay sees old transaction for File A and writes data to that block → **overwrites File B's data**.
    

### The Solution: Revoke Records

- When a block is reused, ext3 writes a **revoke record** to the journal.
    
- During replay, scan revoke records first; skip any transactions for revoked block addresses.
    

---

## 9. Comparison: Data Journaling vs Metadata Journaling

|Aspect|Data Journaling|Metadata Journaling (Ordered)|
|---|---|---|
|**Data written to journal?**|Yes|No|
|**Physical writes per logical write**|2x|1x for data + 2x for metadata (less total)|
|**Bandwidth**|50% of peak|~80-90% of peak|
|**Crash consistency guarantee**|Strong (no garbage data)|Weak (garbage data possible)|
|**fsync required for data safety?**|No|Yes|
|**Used in**|ext3 (optional)|ext3 (default), ext4|

---

## 10. Journaling vs fsck: The Trade-off Matrix

|Metric|fsck|Journaling|
|---|---|---|
|**Recovery time**|O(disk capacity) hours-days|O(uncheckpointed writes) seconds|
|**Recovery damage**|Entire disk scanned|Only replay log|
|**Write performance**|No overhead (no journal writes)|Overhead (journal + checkpoint writes)|
|**Implementation complexity**|Low (standalone tool)|High (integrated into FS)|
|**Downtime after crash**|High|Very low|
|**Used in**|Older FS (UFS, ext2)|Modern FS (ext4, NTFS, XFS)|

## 11. Connections to Other Topics in Your Course

### To Your Midsem Q1 (LFS Inode Checker)

- LFS avoids fsck entirely by using **segment cleaning** instead of journaling.
    
- The inode checker from Q1 is a **liveness check**, not a consistency check.
    
- LFS crash recovery: read checkpoint region → imap → done. No journal needed.
    

### To Your Midsem Q2 (Deletion Inconsistency)

- The 6 crash scenarios from Q2 are exactly what journaling solves.
    
- Your answer about "inode bitmap and data bitmap not in sync" is the definition of inconsistency.
    
- Journaling ensures that either both update or neither does.
    

### To Your Midsem Q3 (HDD Performance T, R, D)

- Journaling adds **extra writes** → more T, R, D.
    
- Data journaling: each write now has journal seek + rotation + transfer PLUS final location write.
    
- Metadata journaling: only metadata pays the journal penalty; data writes are single.
    

### To LFS (Slide 11)

- LFS is like **inverse journaling**: the log IS the filesystem.
    
- No separate checkpointing phase; writes go directly to log.
    
- Crash recovery in LFS is faster than journaling because the checkpoint region points directly to current imap.
    

### To SSD FTL (Slide 7, your midsem Q4)

- Journaling causes **write amplification** on SSDs (data written twice to NAND).
    
- On HDD, journaling is a performance optimization. On SSD, it's a **lifetime reduction**.
    
- Some SSD-optimized FS use **copy-on-write** (like ZFS) instead of journaling.
    

### To GFS (Slide 14)

- GFS uses **replication** (3 copies) for crash tolerance, not journaling.
    
- Master state recovered from operation log (journal-like).
    
- Chunk leases prevent write conflicts; no need for complex logging.
    

### To NFS (Slide 13)

- NFS is stateless → server crash doesn't require journal replay for clients.
    
- But the server's **local file system** (e.g., ext4) still uses journaling.
    
- Crash recovery for NFS server = journal replay + restart NFS service.
    

### To RAID (Slide 17-18)

- RAID controllers use **NVRAM** for journaling to solve the "write hole" problem.
    
- Without NVRAM, partial stripe writes + power failure = parity inconsistency.
    
- RAID journaling is **hardware-based**; file system journaling is software-based.

## 12. Exam-Style Questions & Answers

> [!question] A file system performs metadata journaling (ordered mode). A crash occurs after the data block is written to its final location but before the transaction commit block (TxE) is written to the journal. Is the file system consistent after recovery? Is the user's data correct? Justify your answer.
> 
> - File system consistent: No transaction committed, so journal replay skips this transaction. The data block is an orphan (not referenced by any inode) but no structural inconsistency.
>     
> - User data not correct: The data the user wrote is present on disk but unreachable. From user's perspective, the write never happened.
>     
> - This is the trade-off offmetadata journaling: performance vs durability guarantee.
>     

> [!question] Why does ext3 use a two-phase commit (journal write then journal commit) instead of writing TxB, I, B, Db, TxE as a single large sequential write? What problem does the two-phase approach solve?
> 
> - Single large write: Disk firmware may break it into smaller chunks. Crash after first chunk leaves a transaction with valid TxB and TxE but missing data.
>     
> - Two-phase: The commit block (TxE) is written only after all transaction data is safely on journal. Even if crash during commit, transaction is either fully present or fully absent.
>     
> - ext4 adds checksums to TxB and TxE, allowing single large write with crash detection.
>     

> [!question] Compare the recovery time of fsck vs journal replay for a 10TB file system that had 100MB of writes before crashing. Assume fsck scans at 200MB/s and journal replay processes at 500MB/s. Calculate both.
> 
> - fsck time = 10TB / 200MB/s = 50,000 seconds ≈ 13.9 hours.
>     
> - Journal replay time = 100MB / 500MB/s = 0.2 seconds.
>     
> - This is why modern file systems abandoned fsck.
>     

> [!question] You are designing a file system for an SSD. Should you use data journaling? Why or why not? What alternative consistency mechanism might work better?
> 
> - Not recommended: Data journaling writes each block twice to NAND. Doubles write amplification, halves lifetime.
>     
> - Better alternatives: Copy-on-write (ZFS, Btrfs) or LFS-style logging where the log is the filesystem.
>     
> - Metadata journaling only (like ext4 default) is acceptable if application uses fsync properly.
>     
> - For pure SSD workloads, consider F2FS (Flash-Friendly File System) designed without journaling.
